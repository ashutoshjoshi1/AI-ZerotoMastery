Session 1 of 3First calls: messages, system prompts, multi-turn conversations and parameters

The shape of every chat API#

From here on you build with models rather than build models. Almost every LLM provider exposes the same shape of API: you send a list of messages, each with a role and content, plus settings, and you get back the next assistant message along with token counts.

  • System prompt: standing instructions and context for the whole conversation ("You are a support assistant for...").
  • User messages: what the person (or your program) says.
  • Assistant messages: what the model said earlier. The API is stateless: the model remembers nothing between calls, so to continue a conversation you send the whole history every time.

This lesson uses the Anthropic Python SDK for the main examples, with the OpenAI-style equivalent alongside, because that second format is also what most local and open-model servers speak. The concepts transfer to any provider.

Terminal
uv add anthropic openai pydantic python-dotenv

Model names change

Providers release new models every few months. The examples use claude-sonnet-5-5 as a capable default and claude-haiku-5-5 as a fast, cheap one. Check your provider's model list and keep the name in one configuration constant so swapping models is a one-line change.

First calls#

Python
import anthropic
from dotenv import load_dotenv

load_dotenv()                                   # ANTHROPIC_API_KEY from .env
client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"

resp = client.messages.create(
    model=MODEL,
    max_tokens=2000,                            # upper bound on the reply length
    system="You are a concise teaching assistant for an AI engineering course.",
    messages=[{"role": "user", "content": "Explain overfitting in two sentences."}],
)
for block in resp.content:                      # a list of blocks: text, tool calls, thinking...
    if block.type == "text":
        print(block.text)
print(resp.stop_reason)                         # "end_turn", or "max_tokens" if it was cut off
print(resp.usage.input_tokens, resp.usage.output_tokens)

from dotenv import load_dotenv

load_dotenv()                                   # OPENAI_API_KEY from .env
client = OpenAI()

    model="YOUR_MODEL_NAME",

Note the small differences: Anthropic takes the system prompt as a separate argument and returns a list of content blocks; the OpenAI format puts the system prompt in the message list and returns choices. Wrapping these differences in one small function of your own keeps the rest of your code provider-neutral.

Read the response by block type#

The content of an Anthropic response is a list of blocks. Today it holds one text block; tomorrow it may hold a tool call (lesson 15) or a thinking block from a reasoning model (lesson 12) in front of the text. Code that reads resp.content[0].text breaks the day that happens. Read by type, and keep the helper around for the rest of the course:

Python
def text_of(resp) -> str:
    """Join the text blocks of a response. Never rely on resp.content[0]."""
    return "".join(b.text for b in resp.content if b.type == "text")

Multi-turn conversations#

Because the API is stateless, a conversation is a list you keep appending to.

Python
history = []

def chat(user_text: str) -> str:
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(model=MODEL, max_tokens=2000, messages=history,
                                  system="You are a helpful tutor.")
    reply = text_of(resp)
    history.append({"role": "assistant", "content": reply})
    return reply

print(chat("What is a learning rate?"))
print(chat("What happens if mine is too high?"))   # "mine" is understood because history was resent

Appending the reply text is enough for a plain chat. When the reply contains tool calls or thinking blocks, append resp.content itself (the whole list of blocks), so the model sees its own earlier turn exactly as it produced it.

Two consequences to remember: every turn re-sends (and re-bills) the whole history, and history eventually overflows the context window. Long-running chats need a strategy: drop old turns, summarise them, or store facts outside the conversation and retrieve them when needed. Lesson 16 is about exactly that; lessons 14 and 15 supply the retrieval and the tools.

The parameters that matter#

Parameter What it does Typical use
max_tokens Hard cap on output length. On models that think before answering, the thinking counts towards it Always set it, with room to spare. Check stop_reason to detect truncation
system Standing instructions Role, rules, context, output format
output_config.effort How much a reasoning model thinks before it answers (lesson 12) "low" for easy, high-volume calls; higher for hard problems
temperature Randomness of sampling (lesson 09) Many APIs and local servers take 0 to about 1. The current Claude models fix their sampling settings and reject other values, so steer with instructions and structured output instead
stop_sequences Strings that end generation early Stop at a delimiter in structured formats

Current Claude models reason before they answer by default, and the effort level is the dial. For a cheap classification you do not want a paragraph of thinking:

Python
resp = client.messages.create(
    model="claude-haiku-5-5", max_tokens=1000,
    output_config={"effort": "low"},            # little or no thinking: cheap and fast
    messages=[{"role": "user", "content": "One word, hardware or software: 'The fan is grinding.'"}],
)
print(text_of(resp), "|", resp.usage.output_tokens, "output tokens")

Hands-on: a provider-neutral ask() helper

At your computer 10-llm-apis.ipynb, cell “Hands-on: a provider-neutral ask() helper”

Build the small wrapper that the rest of your code will call, and test it without spending a token.

  1. Write ask(messages, system=None, max_tokens=1000, client=client) that calls the Anthropic API and returns a tuple (text, usage, stop_reason) where usage is a plain dict {"in": ..., "out": ...}.
  2. Write a FakeAnthropic class whose .messages.create(**kwargs) ignores the arguments and returns an object shaped like a real response (a list of blocks in .content, a .stop_reason, a .usage with token counts). types.SimpleNamespace is enough. Make the fake return two blocks, a thinking block and a text block, so your helper is forced to read by type.
  3. Add an ask_openai(...) twin for the OpenAI-compatible format, and a FakeOpenAI for it.
  4. You are done when both fakes make their helper return exactly ("Hello from the fake.", {"in": 12, "out": 5}, "end_turn"), and, if you have a key, the real client returns a sensible answer through the same ask().
Show a solution

Python
from types import SimpleNamespace as NS

def ask(messages, system=None, max_tokens=1000, client=client, model=MODEL):
    kwargs = {"model": model, "max_tokens": max_tokens, "messages": messages}
    if system:
        kwargs["system"] = system
    resp = client.messages.create(**kwargs)
    usage = {"in": resp.usage.input_tokens, "out": resp.usage.output_tokens}
    return text_of(resp), usage, resp.stop_reason

class FakeAnthropic:
    """Looks like anthropic.Anthropic() from the outside, costs nothing, works offline."""
    def __init__(self, reply="Hello from the fake."):
        self.messages = NS(create=self._create)
        self.reply = reply
    def _create(self, **kwargs):
        blocks = [NS(type="thinking", thinking=""), NS(type="text", text=self.reply)]
        return NS(content=blocks, stop_reason="end_turn", usage=NS(input_tokens=12, output_tokens=5))

def ask_openai(messages, system=None, max_tokens=1000, client=None, model="YOUR_MODEL_NAME"):
    msgs = ([{"role": "system", "content": system}] if system else []) + messages
    resp = client.chat.completions.create(model=model, max_tokens=max_tokens, messages=msgs)
    choice = resp.choices[0]
    usage = {"in": resp.usage.prompt_tokens, "out": resp.usage.completion_tokens}
    stop = {"stop": "end_turn", "length": "max_tokens"}.get(choice.finish_reason, choice.finish_reason)
    return choice.message.content, usage, stop

class FakeOpenAI:
    def __init__(self, reply="Hello from the fake."):
        self.chat = NS(completions=NS(create=self._create))
        self.reply = reply
    def _create(self, **kwargs):
        return NS(choices=[NS(message=NS(content=self.reply), finish_reason="stop")],
                  usage=NS(prompt_tokens=12, completion_tokens=5))

msgs = [{"role": "user", "content": "Say hello."}]
print(ask(msgs, client=FakeAnthropic()))
print(ask_openai(msgs, client=FakeOpenAI()))
assert ask(msgs, client=FakeAnthropic()) == ask_openai(msgs, client=FakeOpenAI())
The fake is not a toy: it is how you unit-test everything that sits around the model (prompt assembly, parsing, retries, history trimming) without network access or cost. Every later lesson reuses the trick.

Session 2 of 3Streaming, structured output with Pydantic, errors, retries and rate limits

Streaming#

A long answer can take many seconds. Streaming sends tokens as they are generated, so users see text appear immediately. The time to first token is what makes an app feel fast; lesson 20 explains where that first-token delay comes from (the prefill phase) and why later tokens arrive at a steady rate.

Python
with client.messages.stream(
    model=MODEL, max_tokens=2000,
    messages=[{"role": "user", "content": "Explain gradient descent to a new engineer."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()               # full message with usage after streaming
print("\n", final.usage.output_tokens, "tokens")

The OpenAI-style equivalent passes stream=True and iterates over chunks, reading chunk.choices[0].delta.content. Stream by default for anything long: besides the better experience, a streamed request cannot hit the HTTP timeout that a two-minute non-streamed reply might.

Structured output you can trust#

Programs need data, not prose. Asking "reply in JSON" works most of the time, and "most of the time" breaks production systems. Use the strongest mechanism the API offers, then validate the result.

Define the shape with Pydantic#

Python
from pydantic import BaseModel, Field
from typing import Literal

class Ticket(BaseModel):
    category: Literal["hardware", "software", "data", "other"]
    severity: int = Field(ge=1, le=5, description="1 = cosmetic, 5 = instrument down")
    instrument_id: str | None = Field(default=None, description="e.g. 'P-117' if mentioned")
    summary: str = Field(max_length=200)

Ask the API to fill it in#

Modern APIs accept a JSON schema as an output format and constrain generation so the reply is valid JSON that matches it (lesson 20 shows how constrained decoding does this at the token level). The Anthropic SDK's parse helper takes the Pydantic class, sends its schema, and validates the reply on the way back:

Python
def extract_ticket(email_text: str) -> Ticket:
    resp = client.messages.parse(
        model=MODEL,
        max_tokens=2000,
        output_format=Ticket,                                          # schema goes to the API
        messages=[{"role": "user", "content": f"Create a ticket from this email:\n\n{email_text}"}],
    )
    return resp.parsed_output                                          # a validated Ticket

t = extract_ticket("Hi, unit P-117 at the coastal site stopped logging overnight. "
                   "Power LED is on but no data since 02:00. Urgent, campaign starts Monday.")
print(t)
# category='hardware' severity=4 instrument_id='P-117' summary='Unit P-117 stopped logging ...'

Under the hood this is client.messages.create(..., output_config={"format": {"type": "json_schema", "schema": ...}}), which returns a text block containing JSON for you to parse yourself. The API guarantees the structure: field names, types, enums, required fields. Pydantic then enforces the rest, such as the 1 to 5 range on severity, and parse raises a pydantic.ValidationError if the reply breaks it. An older pattern declared a "tool" whose input schema was the data shape and forced the model to call it; the current Claude models no longer accept a forced tool choice, so prefer the output format.

OpenAI-style APIs offer the same idea through a JSON-schema response format (and the OpenAI SDK also accepts a Pydantic class directly). Whichever you use, keep the Pydantic validation: it catches the rare malformed result and gives you typed objects for the rest of your program.

Validate, then repair

If validation fails, send the error message back to the model ("Your output failed validation: severity must be at most 5. Fix it.") and retry once or twice. Libraries such as Instructor automate this loop.

Hands-on: validate, then repair

At your computer 10-llm-apis.ipynb, cell “Hands-on: validate, then repair”

Build the repair loop yourself, and test it against a scripted model so you can see it work without a key.

  1. Write extract_with_repair(email, llm, max_attempts=3) -> Ticket. llm(messages) -> str is any function that returns the model's text. Ask for JSON matching Ticket.model_json_schema(), parse it with Ticket.model_validate_json, and on failure append the assistant's reply and a user message quoting the validation error, then call again.
  2. Write scripted(replies), which returns an llm that hands out the given replies in order. Script a first reply with "severity": 9 and a second that is valid.
  3. You are done when the scripted run returns a valid Ticket after exactly one repair (count the calls), a script that always returns severity 9 makes the function raise after three attempts, and, with a key, the real model passes first time through the same function (use output_config with the schema, or just ask for JSON, and compare).
Show a solution

Python
import json
from pydantic import ValidationError

def scripted(replies):
    """An llm(messages) -> str that returns the scripted replies in order and counts calls."""
    replies = list(replies)
    def llm(messages):
        llm.calls += 1
        return replies.pop(0) if len(replies) > 1 else replies[0]
    llm.calls = 0
    return llm

def extract_with_repair(email: str, llm, max_attempts: int = 3) -> Ticket:
    schema = json.dumps(Ticket.model_json_schema())
    messages = [{"role": "user", "content": f"Return only JSON matching this schema:\n{schema}\n\nEmail:\n{email}"}]
    for attempt in range(max_attempts):
        reply = llm(messages)
        try:
            return Ticket.model_validate_json(reply)
        except (ValidationError, ValueError) as e:
            messages.append({"role": "assistant", "content": reply})
            messages.append({"role": "user", "content": f"Your output failed validation:\n{e}\nReturn corrected JSON only."})
    raise ValueError(f"no valid ticket after {max_attempts} attempts")

bad = '{"category": "hardware", "severity": 9, "instrument_id": "P-117", "summary": "stopped logging"}'
good = '{"category": "hardware", "severity": 4, "instrument_id": "P-117", "summary": "stopped logging"}'

llm = scripted([bad, good])
print(extract_with_repair("...", llm), "after", llm.calls, "calls")     # severity=4 after 2 calls
try:
    extract_with_repair("...", scripted([bad]))
except ValueError as e:
    print("gave up:", e)

def real_llm(messages):                                                 # Needs an API key
    return text_of(client.messages.create(model=MODEL, max_tokens=2000, messages=messages))
# print(extract_with_repair("Unit P-117 stopped logging overnight, urgent.", real_llm))
With a real model and the schema in the output format, the repair branch almost never runs. It is still worth having: it turns a rare crash into a rare extra call.

Errors, retries and rate limits#

Every network call can fail. Expect four kinds of trouble:

  • Rate limits (HTTP 429): too many requests or tokens per minute for your account tier.
  • Overload or server errors (5xx, including the provider's "overloaded" status): transient, retry later.
  • Timeouts and connection errors: transient.
  • Bad requests (400, 401, 404): a bug or bad key. Retrying will not help.

The official SDKs already retry transient errors with exponential backoff. Configure it, and handle what remains:

Python
client = anthropic.Anthropic(max_retries=4, timeout=60.0)

try:
    resp = client.messages.create(model=MODEL, max_tokens=1000,
                                  messages=[{"role": "user", "content": "Hello"}])
except anthropic.RateLimitError:
    ...   # back off further, queue the work, or route to another model
except anthropic.APIConnectionError:
    ...   # network trouble or timeout: alert if persistent
except anthropic.APIStatusError as e:
    print(e.status_code, e.message)   # bad request, auth, etc.: log and fix, do not retry blindly

A request can also succeed and still not give you an answer: stop_reason is "max_tokens" when the cap cut the reply short, and "refusal" when a safety system declined. Check it before you use the text.

For production, add a fallback: if the primary model keeps failing, try a second model or provider, and degrade gracefully (a cached answer, or a clear "try again shortly") rather than crashing.

Python
TRANSIENT = (anthropic.RateLimitError, anthropic.APIConnectionError, anthropic.InternalServerError)

def ask_with_fallback(messages, models=(MODEL, "claude-haiku-5-5"), **kwargs):
    last_error = None
    for model in models:
        try:
            return client.messages.create(model=model, max_tokens=1000, messages=messages, **kwargs)
        except TRANSIENT as e:            # the SDK already retried this model; move on
            last_error = e
    raise last_error

Session 3 of 3Tokens and cost, prompt caching, batches and concurrency, local models, and a CLI chatbot

Tokens, cost and speed#

Estimate before you build#

Providers price input and output tokens separately, and output tokens cost several times more than input tokens. A back-of-envelope calculation before you build saves surprises:

Python
def monthly_cost(requests_per_day, in_tokens, out_tokens, price_in_per_m, price_out_per_m):
    per_request = in_tokens / 1e6 * price_in_per_m + out_tokens / 1e6 * price_out_per_m
    return per_request * requests_per_day * 30

# 5,000 requests a day, 3,000 tokens of prompt (instructions + retrieved context), 400 tokens out.
# Illustrative prices for a mid-size model at the time of writing; plug in your provider's current list:
print(monthly_cost(5_000, 3_000, 400, price_in_per_m=2.0, price_out_per_m=10.0))   # 1500.0 per month

The example shows the usual pattern: the prompt dominates the bill when you stuff in lots of context. That is where caching, shorter prompts and smaller models pay off.

Count tokens exactly with the provider's counting endpoint rather than guessing. Tokenisers differ between providers, so a count from another vendor's tokeniser library is wrong for Claude:

Python
count = client.messages.count_tokens(model=MODEL, messages=[{"role": "user", "content": long_text}])
print(count.input_tokens)

Prompt caching#

If many requests share a long prefix (a big system prompt, a manual, a set of examples), providers can cache the processed prefix. Cached input tokens are billed at a fraction of the normal price and processed faster. With the Anthropic API you mark where the cacheable prefix ends:

Python
manual = open("instrument_manual.txt").read()          # thousands of tokens, the same every call

def ask_manual(question: str) -> str:
    resp = client.messages.create(
        model=MODEL, max_tokens=1000,
        system=[
            {"type": "text", "text": "Answer using only the manual below. Quote section numbers."},
            {"type": "text", "text": manual, "cache_control": {"type": "ephemeral"}},
        ],
        messages=[{"role": "user", "content": question}],
    )
    u = resp.usage
    print("cache write", u.cache_creation_input_tokens, "cache read", u.cache_read_input_tokens)
    return text_of(resp)

The first call writes the cache; calls within the cache lifetime (minutes by default) read it. Three rules make it work. The cache is a prefix match: the request is laid out as tools, then system prompt, then messages, and any byte that changes before the marker invalidates everything after it, so put stable content first and variable content last. Short prefixes are not cached at all (the minimum is model-dependent, from several hundred to a few thousand tokens). And always check cache_read_input_tokens: if it stays at zero, something is silently changing in your prefix, a timestamp or an unsorted dictionary being the usual culprits. Lesson 16 builds the full strategy, including how to lay out long conversations so the cache keeps hitting.

Choosing a model size#

Smaller models are several times cheaper and faster. A good habit is to start prototyping with a capable model to learn what "good" looks like, build an evaluation set (lesson 17), then test whether a smaller model passes it. Many production systems route: a cheap model handles easy requests and escalates hard ones (lesson 12 works through the economics).

Concurrency and batch processing#

To process thousands of documents, run requests concurrently, with a limit so you stay under your rate limits.

Python
import asyncio
from anthropic import AsyncAnthropic

aclient = AsyncAnthropic(max_retries=5)
sem = asyncio.Semaphore(8)                        # at most 8 requests in flight

async def summarise(doc: str) -> str:
    async with sem:
        r = await aclient.messages.create(model="claude-haiku-5-5", max_tokens=500,
                                          output_config={"effort": "low"},
                                          messages=[{"role": "user", "content": f"Summarise in one sentence:\n{doc}"}])
        return text_of(r)

async def main(docs):
    return await asyncio.gather(*(summarise(d) for d in docs))

# summaries = asyncio.run(main(docs))

For large jobs that do not need answers immediately, use the Batch API: submit thousands of requests at once, collect the results within hours (usually much sooner), at a substantial discount, typically half price. It is ideal for nightly classification, backfills and evaluation runs. Each request carries a custom_id, because results come back in any order:

Python
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

tickets = ["The fan in the enclosure is grinding loudly", "After updating to 2.4 the GUI crashes",
           "Yesterday's ozone values are all exactly zero"]

requests = [
    Request(custom_id=f"ticket-{i}", params=MessageCreateParamsNonStreaming(
        model="claude-haiku-5-5", max_tokens=300, output_config={"effort": "low"},
        messages=[{"role": "user", "content": f"One word, hardware/software/data/other: {t}"}]))
    for i, t in enumerate(tickets)
]
batch = client.messages.batches.create(requests=requests)
print(batch.id, batch.processing_status)          # "in_progress" until every request has run
Python
import time

while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    time.sleep(30)

results = {}
for item in client.messages.batches.results(batch.id):      # any order: key by custom_id
    if item.result.type == "succeeded":
        results[item.custom_id] = text_of(item.result.message)
    else:
        print(item.custom_id, "failed:", item.result.type)   # errored, canceled or expired
print(results)

Local and open models#

Many local servers (Ollama, vLLM, llama.cpp's server, LM Studio) expose an OpenAI-compatible endpoint, so the same client code works by changing the base URL.

Terminal

local = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")   # the key is ignored locally

Local models are free per call, private and work offline, but they are smaller and less capable than frontier APIs, and you own the hardware and operations. Lesson 20 explains what the server is doing (batching, the KV cache, quantisation) and lesson 21 covers serving them properly.

Hands-on: a streaming CLI chatbot

At your computer 10-llm-apis.ipynb, cell “Hands-on: a streaming CLI chatbot”

Build chat.py, a terminal chatbot that:

  1. Streams replies as they are generated.
  2. Keeps conversation history, and trims the oldest turns when the history exceeds about 20,000 tokens (estimate with count_tokens, or roughly 4 characters per token).
  3. Prints the running token usage and an estimated cost after each reply.
  4. Supports /reset to clear history, /system <text> to change the system prompt, and /quit.
  5. Survives a network error without losing the conversation.

Develop it against the FakeAnthropic from the first exercise (give it a messages.stream that yields a few words) and switch to the real client at the end. You are done when a ten-turn conversation shows the input-token count climbing each turn, and pulling the network cable mid-reply leaves the history intact.

Show a solution

chat.py
import anthropic
from dotenv import load_dotenv

load_dotenv()
client = anthropic.Anthropic(max_retries=3)
MODEL = "claude-sonnet-5-5"
PRICE_IN, PRICE_OUT = 2.0, 10.0          # per million tokens: set to your provider's current prices
MAX_HISTORY_CHARS = 80_000                # about 20k tokens

system = "You are a friendly, precise tutor for an AI engineering course."
history: list[dict] = []
spent_in = spent_out = 0

def trim(history):
    while sum(len(m["content"]) for m in history) > MAX_HISTORY_CHARS and len(history) > 2:
        history.pop(0); history.pop(0)     # drop the oldest user/assistant pair
    return history

while True:
    try:
        user = input("\nyou> ").strip()
    except (EOFError, KeyboardInterrupt):
        break
    if not user:
        continue
    if user == "/quit":
        break
    if user == "/reset":
        history.clear(); print("history cleared"); continue
    if user.startswith("/system "):
        system = user[len("/system "):]; print("system prompt updated"); continue

    history.append({"role": "user", "content": user})
    trim(history)
    print("bot> ", end="", flush=True)
    try:
        with client.messages.stream(model=MODEL, max_tokens=2000, system=system,
                                    messages=history) as stream:
            parts = []
            for piece in stream.text_stream:
                print(piece, end="", flush=True)
                parts.append(piece)
            final = stream.get_final_message()
        reply = "".join(parts)
    except anthropic.APIError as e:
        history.pop()                      # remove the unanswered user turn so history stays valid
        print(f"\n[request failed: {e.__class__.__name__}; your conversation is intact, try again]")
        continue
    history.append({"role": "assistant", "content": reply})
    spent_in += final.usage.input_tokens
    spent_out += final.usage.output_tokens
    cost = spent_in / 1e6 * PRICE_IN + spent_out / 1e6 * PRICE_OUT
    print(f"\n[{final.usage.input_tokens} in / {final.usage.output_tokens} out; session ≈ {cost:.4f} USD]")
Watch the input-token count climb every turn: that is the stateless API re-reading the whole history. It is the clearest demonstration of why long conversations get slow and expensive, and why trimming, summarising or caching matters.

Check yourself#

1. Your chatbot "forgets" what the user said two turns ago. What is the most likely cause?

The model sees only what you send in each request. Conversation state lives in your code.

2. What is the most reliable way to get structured data out of an LLM?

Constrain the output, validate it, and retry with the error message on the rare failure.

3. Which errors should your code retry automatically?

Transient errors deserve a retry; client errors mean a bug that retrying will not fix.

4. Many requests share a 30,000-token system prompt containing a manual. What most reduces cost?

Cached prefix tokens are billed at a fraction of the normal rate and processed faster.

5. Why does each turn of a long chat cost more than the previous one?

Input tokens grow with every turn. Trim, summarise or cache to control it.

Key takeaways

  • Chat APIs take a system prompt plus a list of role-tagged messages and are stateless: you resend history each turn.
  • Read responses by block type, always set max_tokens with room for thinking, and check the stop reason. Stream responses for a fast-feeling experience.
  • Get structured output by giving the API a JSON schema, then validate with Pydantic and repair on failure.
  • Retry transient errors with backoff, fail fast on client errors, and keep a fallback model.
  • Estimate costs up front; input context usually dominates. Use prompt caching, smaller models and low effort, routing, concurrency limits and the Batch API.
  • A fake client lets you test everything around the model offline. OpenAI-compatible endpoints let the same code talk to local open models.
