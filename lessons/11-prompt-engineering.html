11 Prompt engineering

Write prompts that work reliably, not just once, through clear instructions, context, examples and structure, along with reasoning and chaining techniques, and treat prompts as tested, versioned code.

Study plan: 3 sessions of about an hour

What prompt engineering really is#

Prompt engineering is writing a specification for a very capable colleague who knows a lot about the world and nothing about your situation. The model has no idea who your users are, what "good" looks like for your product, or which of several reasonable interpretations you meant. A prompt fills that gap.

It is less about magic phrases than about clear writing and disciplined testing. The most reliable test of a prompt: would a smart new hire, given only this text, do the task the way you want? If they would need to ask questions, so does the model, except it will not ask; it will guess.

Principles#

1. Be explicit about the task, the audience and the output#

Compare:

Vague
Summarise this incident report.
Specific
Summarise the incident report below for the on-call engineering manager, who will
decide within five minutes whether to wake up the hardware team.

Write at most 5 bullet points:
- what failed, where, and since when
- current impact on data collection
- what has already been tried
- the single most likely cause, if the report supports one
- the decision needed, phrased as a yes/no question

If the report does not say something, write "not stated" rather than guessing.

The second prompt says who the reader is, why they need it, the format, the length, and what to do when information is missing. Each of those removes a guess.

2. Give context and explain why#

Rules without reasons get applied rigidly or inconsistently. Reasons let the model generalise. "Never use abbreviations" is weaker than "Readers include non-specialist field staff, so spell out technical abbreviations the first time you use them."

3. Show examples#

A couple of well-chosen examples often beat a paragraph of description, especially for format and tone. Make examples diverse (cover different cases, including edge cases), or the model will copy their surface features too closely.

4. Structure the prompt#

Long prompts mix instructions, reference material and input data. Separate them clearly so the model never confuses data with instructions. XML-style tags work well and are easy to parse back out:

<instructions>
Classify the support email into exactly one category and explain briefly.
</instructions>

<categories>
hardware: physical faults, power, cables, sensors, enclosures
software: firmware, drivers, the acquisition application, updates
data: missing, corrupted or suspicious measurements, processing results
other: anything else, including billing and scheduling
</categories>

<email>
{email_text}
</email>

Answer in the form:
<category>...</category>
<reason>one sentence</reason>

Put long reference documents before the question; models tend to handle "documents first, question last" better, and it suits prompt caching (lesson 10).

5. Say what to do, not only what to avoid#

"Don't be verbose" leaves the target vague. "Answer in at most three sentences" is actionable. Negative instructions also tend to put the unwanted thing in the model's mind. Prefer positive, concrete instructions, and keep "never do X" for genuine hard limits.

Techniques#

Few-shot prompting#

Include worked input-output pairs. In a chat API you can write them as earlier conversation turns, which models treat as strong evidence of the desired behaviour.

messages = [
    {"role": "user", "content": "Reading: 'NO2 412 ppb at 03:00, all other hours 10-25 ppb'"},
    {"role": "assistant", "content": "SUSPECT: isolated spike roughly 20x the surrounding values."},
    {"role": "user", "content": "Reading: 'NO2 rises from 15 to 38 ppb between 07:00 and 09:00'"},
    {"role": "assistant", "content": "PLAUSIBLE: gradual morning increase consistent with traffic."},
    {"role": "user", "content": f"Reading: '{new_reading}'"},
]

Let the model reason before answering#

For multi-step problems, asking the model to work through the problem before giving the final answer improves accuracy, because each generated token is extra computation the model can build on. This is chain-of-thought prompting. Ask for the reasoning in a separate section so your code can discard it and keep only the answer:

Work out the answer step by step inside <thinking> tags.
Then give only the final number inside <answer> tags.

Reasoning models (lesson 09) do this internally, controlled by a thinking budget setting; with them, explicit "think step by step" instructions matter less, and over-prescribing the steps can even hurt. Either way, reasoning costs tokens and latency, so use it where accuracy on harder problems justifies it, not for simple lookups.

Control the output#

  • Specify the format exactly, with an example of it.
  • Use structured output features for machine-read results (lesson 10).
  • Prefill (where supported): with the Anthropic API you can end the message list with a partial assistant turn, for instance {"role": "assistant", "content": "<category>"}, and the model continues from there. This pins the format and skips preamble.
  • Stop sequences end generation at a delimiter such as </answer>.

Prompt chaining#

One giant prompt that researches, drafts, critiques and formats is hard to debug. Break the job into steps, each a separate call with a focused prompt, passing outputs forward:

def answer_with_review(question: str, document: str) -> str:
    quotes = llm(f"<doc>{document}</doc>\nList verbatim quotes relevant to: {question}")
    draft = llm(f"<quotes>{quotes}</quotes>\nAnswer '{question}' using only these quotes, citing them.")
    review = llm(f"<quotes>{quotes}</quotes>\n<answer>{draft}</answer>\n"
                 "List any claim in the answer not supported by the quotes, or reply NONE.")
    if review.strip() != "NONE":
        draft = llm(f"Rewrite the answer removing unsupported claims.\n<problems>{review}</problems>\n<answer>{draft}</answer>")
    return draft

Each step can be tested, logged, cached and given a different (cheaper or stronger) model. The extract-then-answer pattern above is also a strong defence against hallucination over long documents.

Self-consistency and verification#

For questions with a checkable answer, sample several responses at a moderate temperature and take the majority answer. Or have the model (or a second model) check the first answer against explicit criteria. Both trade cost for reliability.

Roles and personas#

A system prompt that sets a role ("You are an experienced field technician writing for colleagues") shifts vocabulary, assumptions and tone. It works best alongside concrete instructions, not as a substitute for them.

Prompts as code#

In a product, prompts are code: they need version control, review and tests.

Templates#

Keep prompts in files or constants, separate from logic, and fill them with variables. Escape or delimit user input so it cannot break your structure.

from string import Template

CLASSIFY_V3 = Template("""<instructions>
Classify the email into exactly one category: hardware, software, data or other.
</instructions>
<email>
$email
</email>
Reply with only the category name, in lower case.""")

def classify(email: str) -> str:
    prompt = CLASSIFY_V3.substitute(email=email.replace("</email>", ""))
    r = client.messages.create(model=MODEL, max_tokens=5, temperature=0,
                               messages=[{"role": "user", "content": prompt}])
    return r.content[0].text.strip().lower()

Test prompts against examples, not vibes#

A prompt that looks great on three examples you tried can fail on the fourth. Build a small labelled set (even 20 to 50 cases, including tricky ones), run every prompt version against it, and track the score. This is the seed of the evaluation discipline in lesson 15, and the single habit that most separates professionals from tinkerers.

cases = [
    ("The fan in the enclosure is grinding loudly", "hardware"),
    ("After updating to 2.4 the GUI crashes on start", "software"),
    ("Yesterday's ozone column values are all exactly zero", "data"),
    ("Can we move the calibration visit to March?", "other"),
    # ... at least 20, including ambiguous ones
]

def score(classify_fn):
    results = [(text, gold, classify_fn(text)) for text, gold in cases]
    acc = sum(g == p for _, g, p in results) / len(results)
    for text, gold, pred in results:
        if gold != pred:
            print(f"MISS  gold={gold:<9} pred={pred:<9} {text}")
    return acc

Read the misses. They tell you exactly what the prompt fails to specify.

Common failure modes#

Symptom Likely cause Fix
Inconsistent formats Format described, not shown Add an exact example; use structured output or prefill
Ignores an instruction in a long prompt Buried among many others or contradicted elsewhere Shorten, move key instructions to the end, remove conflicts
Makes up facts No source given, or no permission to say "unknown" Provide the source; instruct to answer "not stated" when absent
Overly long, hedged answers No length or audience specified State length and reader; give an example
Copies example content into new answers Examples too similar to each other Use diverse examples; label them clearly as examples
Agrees with whatever the user asserts Leading phrasing Ask neutrally; ask the model to evaluate claims critically
Follows instructions found inside the data Data and instructions not separated Delimit input; treat retrieved text as untrusted (lesson 18)

Let the model help#

Models are good at improving prompts. Paste your prompt and a few failing cases and ask: "Here is a prompt and examples where it produced the wrong output. Explain what in the prompt caused each failure and propose a revised prompt." Then test the revision on your full set; never accept it on the model's say-so.

Hands-on: iterate a classifier prompt to 90%+

  1. Write 30 short support messages across the four categories above. Make at least 8 deliberately ambiguous ones (a firmware update that bricked a sensor; a data gap caused by a power cut).
  2. Write the simplest possible classification prompt and score it with score().
  3. Iterate: add category definitions, add tie-break rules for the ambiguous cases ("classify by root cause if stated, otherwise by symptom"), add two or three examples. Score each version and keep a table in your log.
  4. Try a smaller, cheaper model with your best prompt. Is the accuracy loss acceptable for the cost saving?
Show what usually happens

A typical log looks something like this:

Version Change Accuracy
v1 "Classify into hardware, software, data or other" 70%
v2 Added one-line definitions of each category 80%
v3 Added tie-break rule: root cause if stated, else the symptom the user reports 90%
v4 Added three diverse examples, including one ambiguous case 93%
v4 on small model Same prompt, cheaper model 90%

Your numbers will differ. What matters is the pattern: the biggest jumps come from removing ambiguity (definitions, tie-break rules), not from clever wording, and the ambiguous cases decide the final score. The remaining misses are often cases where you are not sure of the right label either, which is a sign to clarify the labelling policy itself. The small-model result is a business decision: if 3 points of accuracy cost a fifth of the price, many teams take it, perhaps routing low-confidence cases to the larger model.

Check yourself#

1. What is the best quick test of whether a prompt is clear enough?

If a person would need clarification, the model will guess instead of asking.

2. Why use XML-style tags to separate instructions from input data?

Clear delimiters reduce confusion and make prompt injection harder (though not impossible).

3. Your prompt works on the three examples you tried but fails in production. What should you have done?

Prompts need tests just like code. Read the failures to learn what the prompt leaves unspecified.

4. When is asking the model to reason step by step most worthwhile?

Reasoning costs tokens and time. Use it where it buys accuracy.

5. What is the main advantage of prompt chaining over one large prompt?

Decomposition is software engineering applied to prompts.

Key takeaways

  • A prompt is a specification for a capable colleague who knows nothing of your situation: state the task, audience, format, length and what to do with missing information.
  • Give context and reasons, diverse examples and clear structure. Documents first, question last.
  • Use reasoning for hard multi-step problems, structured output and prefill for format control, chaining for complex jobs, and self-consistency where reliability matters.
  • Treat prompts as code: templates, version control and a labelled test set. Iterate on the misses.
