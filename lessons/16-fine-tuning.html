16 Fine-tuning language models

Learn when fine-tuning is the right tool and when it is not, understand LoRA and QLoRA down to the matrix shapes and memory budget, fine-tune a small open model on your own task, then go further with DPO, distillation and adapter serving.

Study plan: 4 sessions of about an hour

Tick a session when you finish it. Progress is saved in this browser only.

Code for this lesson: notebooks/16-fine-tuning.ipynb, with worked solutions in notebooks/solutions/.

When to fine-tune, and when not to#

Fine-tuning means continuing to train a pretrained model on your own examples so its weights change. It is powerful, and it is also the most over-prescribed technique in AI engineering. Work through the cheaper options first:

  1. Prompting (lesson 11): clear instructions and examples. Solves most problems.
  2. Retrieval (lesson 13): when the model lacks knowledge. Fine-tuning is a poor way to teach facts: it is expensive to update, hard to verify, and the model may still hallucinate around what it learned.
  3. Tools (lesson 14): when the model needs live data or exact computation.

Fine-tuning earns its place when you need to change behaviour in ways prompts cannot reliably achieve, or need the same behaviour cheaper or faster:

  • A consistent output format, style or tone across very high volume, without long prompts.
  • A small, cheap or on-premise model to do a narrow task as well as a large model does it (distillation).
  • Domain-specific language the base model handles poorly (specialised notation, a rare language, internal codes).
  • Lower latency and cost by removing thousands of tokens of instructions and examples from every prompt.
  • Classification or extraction at a scale where a fine-tuned small model beats a prompted large one on price.

Before you fine-tune, have an eval set

Without the evaluation discipline of lesson 15 you cannot tell whether fine-tuning helped, hurt, or just changed things. Measure the prompted baseline first. Fine-tuning that does not beat a well-prompted baseline on your eval set is wasted money.

Full fine-tuning versus parameter-efficient fine-tuning#

Full fine-tuning updates every weight. With the Adam optimiser in mixed precision, a common rule of thumb is about 16 bytes of GPU memory per parameter (weights, gradients, two optimiser moments and a full-precision master copy), before activations. For a 7-billion-parameter model that is over 110 GB: several data-centre GPUs. You also get a full-size copy of the model for every task.

Parameter-efficient fine-tuning (PEFT) freezes the pretrained weights and trains a small number of new parameters. Quality is close to full fine-tuning for most adaptation tasks, memory needs drop dramatically, and the trained result is a small file you can swap in and out. LoRA is the method nearly everyone uses.

LoRA: low-rank adaptation#

The idea#

Fine-tuning changes a weight matrix WWW (shape dout×dind_{\text{out}} \times d_{\text{in}}dout​×din​) by some update ΔW\Delta WΔW. The LoRA paper observed that these updates have low intrinsic rank: they can be well approximated by the product of two thin matrices (recall the SVD discussion in lesson 02). So instead of learning ΔW\Delta WΔW directly, learn

ΔW=BA,B∈Rdout×r,A∈Rr×din,r≪d \Delta W = B A, \qquad B \in \mathbb{R}^{d_{\text{out}} \times r},\quad A \in \mathbb{R}^{r \times d_{\text{in}}},\quad r \ll d ΔW=BA,B∈Rdout​×r,A∈Rr×din​,r≪d

and compute the layer as

h=Wx+αrBAx h = W x + \frac{\alpha}{r} B A x h=Wx+rα​BAx

with WWW frozen. BBB starts at zero, so training begins from exactly the original model. The scale α/r\alpha/rα/r keeps the update's size stable as you change the rank.

For a 4,096 × 4,096 attention projection, the full matrix has 16.8 million parameters; LoRA with r=16r = 16r=16 trains 16×(4096+4096)=131,07216 \times (4096 + 4096) = 131{,}07216×(4096+4096)=131,072, under 1%. Applied to every linear layer of a 7B model, LoRA at rank 16 trains roughly 40 million parameters, about 0.6% of the model.

LoRA from scratch#

import torch, torch.nn as nn

class LoRALinear(nn.Module):
    """Wrap a frozen nn.Linear with a trainable low-rank update."""
    def __init__(self, base: nn.Linear, r: int = 8, alpha: int = 16):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False                                       # freeze W and b
        self.A = nn.Parameter(torch.randn(r, base.in_features) * 0.01)    # (r, d_in)
        self.B = nn.Parameter(torch.zeros(base.out_features, r))          # (d_out, r): zero, so no change at start
        self.scale = alpha / r

    def forward(self, x):                                                 # x: (..., d_in)
        return self.base(x) + (x @ self.A.T @ self.B.T) * self.scale     # (..., d_out)

    @torch.no_grad()
    def merge(self) -> nn.Linear:
        """Fold the update into W for zero-overhead inference."""
        self.base.weight += (self.B @ self.A) * self.scale
        return self.base

layer = LoRALinear(nn.Linear(4096, 4096), r=16)
trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
total = sum(p.numel() for p in layer.parameters())
print(trainable, total, f"{100 * trainable / total:.2f}%")   # 131072 16912384 0.78%

Because BABABA can be merged into WWW after training, a LoRA-tuned model runs exactly as fast as the original. Or keep adapters separate and switch between them per request.

Hyperparameters that matter#

  • Rank rrr: 8 to 64 is typical. Higher ranks can learn more complex changes but need more data.
  • Alpha: often set to rrr or 2r2r2r.
  • Target modules: attention projections only is the classic setting; applying LoRA to all linear layers (including the MLP) usually works better.
  • Learning rate: much higher than for full fine-tuning, often around 10−410^{-4}10−4 to 2×10−42\times10^{-4}2×10−4.
  • Epochs: 1 to 3. More risks memorising the training set.

QLoRA: fine-tuning on one consumer GPU#

QLoRA stores the frozen base model in 4-bit precision (a format called NF4, designed for normally distributed weights) and trains LoRA adapters in 16-bit on top. Memory for the base model falls about fourfold: a 7B model's weights take roughly 4 to 5 GB instead of 14. With paged optimisers and gradient checkpointing, fine-tuning a 7B model fits on a single 16 to 24 GB GPU, and small models (0.5B to 3B) fit on a free Colab T4. Quality is close to 16-bit LoRA.

A memory budget, worked out#

What Full fine-tune, 7B LoRA, 7B base in 16-bit QLoRA, 7B base in 4-bit
Base weights 14 GB 14 GB about 4 GB
Gradients + optimiser + master weights about 98 GB under 1 GB (40M params) under 1 GB
Activations (batch-dependent) several GB several GB several GB (less with checkpointing)
Fits on multiple 80 GB GPUs one 24 to 40 GB GPU one 16 to 24 GB GPU

Hands-on: fine-tune a small model#

The task#

We will teach a small open model to turn free-text field-technician notes into a strict JSON record. This is a textbook fine-tuning case: narrow, high-volume, format-sensitive, and something a 0.5B to 1.5B model can learn well enough to run cheaply or on a laptop.

The data#

Training data for chat models is a list of conversations in the same chat format the model was instruction-tuned with:

train.jsonl (one example per line, shown pretty-printed)
{"messages": [
  {"role": "system", "content": "Convert the technician note to JSON with keys instrument_id, action, parts, duration_min, follow_up."},
  {"role": "user", "content": "P-117 coastal. swapped desiccant + new belt on filter wheel, 45 min. check again in 2 wks"},
  {"role": "assistant", "content": "{\"instrument_id\": \"P-117\", \"action\": \"maintenance\", \"parts\": [\"desiccant\", \"filter wheel belt\"], \"duration_min\": 45, \"follow_up\": \"recheck in 2 weeks\"}"}
]}

Where do hundreds of examples come from? Real historical records, labelled by hand, are best. A common practical shortcut is distillation: use a large model with a careful prompt to label a few hundred realistic inputs, review a sample (and fix errors), then fine-tune the small model on the result. Quality rules:

  • Quality beats quantity. A few hundred clean, consistent, diverse examples often beat thousands of noisy ones. The model learns your inconsistencies too.
  • Cover the real distribution: typos, abbreviations, missing fields, multiple instruments in one note, notes that should produce nulls.
  • Hold out 10 to 20% as a validation set, and keep your separate eval set untouched.

Training with Hugging Face TRL and PEFT#

Run this on a GPU (a free Colab T4 is enough for a 0.5B model). Library APIs evolve quickly; if an argument name has changed, check the TRL documentation for your installed version.

pip install -U transformers datasets peft trl accelerate bitsandbytes

import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import SFTConfig, SFTTrainer

model_id = "Qwen/Qwen2.5-0.5B-Instruct"         # small instruction-tuned open model
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype=torch.float16, device_map="auto")

data = load_dataset("json", data_files={"train": "train.jsonl", "validation": "val.jsonl"})

lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules="all-linear",                 # LoRA on every linear layer
    task_type="CAUSAL_LM",
)
args = SFTConfig(
    output_dir="notes-to-json-lora",
    num_train_epochs=3,
    per_device_train_batch_size=8,
    gradient_accumulation_steps=2,               # effective batch of 16
    learning_rate=2e-4,
    lr_scheduler_type="cosine",
    warmup_ratio=0.05,
    logging_steps=10,
    eval_strategy="epoch",
    save_strategy="epoch",
    fp16=True,                                   # use bf16=True instead on Ampere or newer GPUs
)
trainer = SFTTrainer(
    model=model,
    args=args,
    train_dataset=data["train"],
    eval_dataset=data["validation"],
    peft_config=lora,
    processing_class=tokenizer,
)
trainer.train()
trainer.save_model("notes-to-json-lora")         # saves only the adapter: a few MB

The trainer applies the model's chat template to each conversation, and by default computes the loss on the whole sequence; options exist to train only on the assistant's replies, which is usually what you want for instruction data.

For a larger model on limited memory, load it in 4-bit (QLoRA) instead:

from transformers import BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.float16, bnb_4bit_use_double_quant=True)
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct",
                                             quantization_config=bnb, device_map="auto")
# then the same LoraConfig / SFTConfig / SFTTrainer, typically with gradient_checkpointing=True in SFTConfig

Watch the curves#

Training loss should fall steadily. Validation loss should fall and then flatten; if it starts rising while training loss keeps falling, you are overfitting (lesson 03): fewer epochs, more data, or lower rank. A training loss near zero on a few hundred examples is a warning sign, not a triumph.

Use and evaluate the result#

from peft import PeftModel

base = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype=torch.float16, device_map="auto")
tuned = PeftModel.from_pretrained(base, "notes-to-json-lora")

def convert(note: str, m) -> str:
    msgs = [{"role": "system", "content": "Convert the technician note to JSON with keys "
                                          "instrument_id, action, parts, duration_min, follow_up."},
            {"role": "user", "content": note}]
    ids = tokenizer.apply_chat_template(msgs, add_generation_prompt=True, return_tensors="pt").to(m.device)
    out = m.generate(ids, max_new_tokens=200, do_sample=False)
    return tokenizer.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

print(convert("P-204: firmware 2.3->2.4, rebooted, all ok. 15min", tuned))
merged = tuned.merge_and_unload()                # fold LoRA into the weights for deployment
merged.save_pretrained("notes-to-json-merged")

Then run your lesson 15 harness on the held-out eval set, comparing three systems: the base small model with your best prompt, the fine-tuned small model, and the large model you distilled from. The question is never "did the loss go down" but "is the fine-tuned small model good enough on the eval set, at its cost and latency".

Beyond supervised fine-tuning#

Preference tuning with DPO#

SFT teaches by imitation. When it is easier to say which of two outputs is better than to write the perfect one (tone, helpfulness, conciseness, safety), use preference data: triples of a prompt, a chosen response and a rejected response. Direct preference optimisation (lesson 09) trains on these directly:

LDPO=−log⁡σ ⁣(β[log⁡πθ(yw∣x)πref(yw∣x)−log⁡πθ(yl∣x)πref(yl∣x)]) \mathcal{L}_{\text{DPO}} = -\log\sigma\!\left(\beta\left[\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\text{ref}}(y_w\mid x)} - \log\frac{\pi_\theta(y_l\mid x)}{\pi_{\text{ref}}(y_l\mid x)}\right]\right) LDPO​=−logσ(β[logπref​(yw​∣x)πθ​(yw​∣x)​−logπref​(yl​∣x)πθ​(yl​∣x)​])

In words: raise the probability of the chosen answer ywy_wyw​ relative to the rejected one yly_lyl​, measured against a frozen reference model so the tuned model does not drift too far; β\betaβ controls how far. It is usually run after SFT.

from trl import DPOConfig, DPOTrainer

prefs = load_dataset("json", data_files="prefs.jsonl")["train"]   # {"prompt", "chosen", "rejected"}
trainer = DPOTrainer(
    model=sft_model,                       # start from your SFT result
    args=DPOConfig(output_dir="dpo-out", beta=0.1, learning_rate=5e-6, num_train_epochs=1),
    train_dataset=prefs,
    processing_class=tokenizer,
    peft_config=lora,                      # with LoRA, the frozen base acts as the reference model
)
trainer.train()

Distillation#

Knowledge distillation trains a small "student" to imitate a large "teacher". The simplest version is what you did above: train on the teacher's outputs. The classic version also matches the teacher's full probability distribution over tokens (using a KL-divergence loss), which carries more information per example but requires access to the teacher's logits, so it is mostly done with open models. Distillation is how many small, fast production models get most of a big model's quality on a narrow task.

Hosted fine-tuning#

Several API providers offer fine-tuning of their own models: upload a JSONL file in their chat format, launch a job, get a model id. You give up control of the method and weights in exchange for zero infrastructure. The same rules apply: clean data, a held-out eval, and a comparison against a well-prompted baseline.

Serving adapters#

Because adapters are small, one base model can serve many of them. Servers such as vLLM can load multiple LoRA adapters and select one per request, so ten customer-specific fine-tunes cost little more than one base model to serve (lesson 17).

Things that go wrong#

  • Catastrophic forgetting: heavy fine-tuning on a narrow task degrades general abilities. LoRA, low learning rates and few epochs reduce it; mixing in some general instruction data helps.
  • Format mismatch: training with one chat template and serving with another silently ruins results. Always use apply_chat_template from the same tokenizer.
  • Data leakage between training and eval examples gives flattering scores (lesson 03 again).
  • Safety regressions: fine-tuning can weaken a model's refusal behaviour, even on benign data. Include safety cases in your eval set.

Hands-on: distil a large model into a small one

  1. Write 30 realistic technician notes by hand (vary style, typos, abbreviations, and include some notes with missing information).
  2. Use a large model via API to generate 400 more diverse notes and their JSON conversions. Review 40 at random and fix or drop bad ones.
  3. Fine-tune Qwen/Qwen2.5-0.5B-Instruct with LoRA as above.
  4. On your 30 hand-written notes (the eval set, never trained on), measure: JSON validity, exact match per field, and latency for the base small model with a few-shot prompt, the fine-tuned small model, and the large model.
  5. Write one paragraph recommending which to deploy, and why.
Show what to expect and how to grade it 

import json

FIELDS = ["instrument_id", "action", "parts", "duration_min", "follow_up"]

def grade(pred: str, gold: dict) -> dict:
    try:
        p = json.loads(pred)
    except json.JSONDecodeError:
        return {"valid": 0, **{f: 0 for f in FIELDS}}
    return {"valid": 1, **{f: int(p.get(f) == gold.get(f)) for f in FIELDS}}
Typical outcome: the base 0.5B model with a few-shot prompt produces valid JSON most of the time but gets fields wrong or invents values; the fine-tuned model is close to 100% valid and approaches the large model on instrument_id, duration_min and parts, while still trailing on free-text fields like follow_up. It runs on a laptop CPU at a fraction of the cost. A sound recommendation might be: deploy the fine-tuned small model, route notes it fails to parse (or flags as low confidence) to the large model, and keep adding corrected failures to the training set for the next round. The exact numbers matter less than having measured them on data the model never saw.

Check yourself#

1. Your assistant needs to know the contents of 2,000 frequently updated product documents. What is the best approach?

Knowledge that changes belongs in a retrieval index. Fine-tuning is for behaviour, format and efficiency.

2. Why does LoRA initialise B to zero?

The adapted model starts identical to the base model and changes gradually.

3. How many trainable parameters does LoRA with rank 8 add to a 1024 × 4096 linear layer?

A is r × d_in and B is d_out × r, so r × (d_in + d_out).

4. What does QLoRA change compared with LoRA?

Quantising the frozen base is what lets large models fine-tune on a single GPU.

5. Validation loss rises while training loss keeps falling during fine-tuning. What is happening?

The classic signature from lesson 03 applies to LLMs too.

Key takeaways

  • Try prompting, retrieval and tools first. Fine-tune to change behaviour or format reliably, or to make a small model do a narrow task cheaply, not to teach facts.
  • LoRA learns a low-rank update BABABA beside frozen weights, training under 1% of parameters; adapters are small, swappable and mergeable.
  • QLoRA keeps the base in 4-bit so large models fine-tune on one GPU.
  • Data quality, coverage and a held-out eval set decide success. Use the model's own chat template.
  • DPO tunes on preferences; distillation transfers a large model's skill to a small one. Watch for forgetting and safety regressions.
