13 Retrieval-augmented generation (RAG)

Make a model answer from your own documents, with citations, by building the full pipeline without a framework (parsing, chunking, hybrid retrieval, reranking and grounded generation), then measure it and fix what it gets wrong.

Study plan: 5 sessions of about an hour

Tick a session when you finish it. Progress is saved in this browser only.

Code for this lesson: notebooks/13-rag.ipynb, with worked solutions in notebooks/solutions/.

Why RAG#

An LLM knows what was in its training data, up to its cutoff date. It does not know your instrument manuals, last week's incident reports, your codebase or your customer contracts. You could paste documents into the prompt, but a document collection is usually far larger than any context window, and paying for a million tokens per question is wasteful.

Retrieval-augmented generation solves this: for each question, retrieve the few most relevant passages from your collection and give them to the model with instructions to answer from them and cite them. It is the most common LLM application pattern in industry because it:

  • grounds answers in your data, which reduces hallucination and enables citations users can check;
  • stays current: update the index, not the model;
  • respects access control: retrieve only what this user is allowed to see;
  • is far cheaper and simpler than fine-tuning a model to "know" facts (fine-tuning is for behaviour and format, not knowledge; lesson 16).

The architecture#

Frameworks such as LlamaIndex and LangChain package these steps. This lesson builds them by hand first, because when a RAG system gives a bad answer you need to know which box failed, and you cannot debug what you do not understand.

Ingestion: parsing and chunking#

Parsing: garbage in, garbage out#

Most retrieval failures start here. PDFs are layout instructions, not text: columns get interleaved, tables turn into number soup, headers and footers repeat on every page, scanned pages contain no text at all.

  • Text-based PDFs: pypdf or PyMuPDF for plain extraction; layout-aware tools such as Docling or Unstructured for headings, lists and tables.
  • Scanned documents: OCR (Tesseract, or a cloud OCR service), or send page images to a vision-capable model (lesson 19).
  • HTML, Markdown, Word: convert to clean text while keeping structure: headings, list items and table rows carry meaning.
  • Always look at the output. Print ten parsed pages before indexing a thousand.

Keep metadata with every piece of text: source file, page, section heading, date, product, access level. You will use it to filter, to cite, and to show users where an answer came from.

Chunking#

Documents are split into chunks that are embedded and retrieved individually. Chunk size is a real trade-off:

  • Too small (a sentence): precise matches, but the chunk lacks the context needed to answer ("Set it to 5" — set what?).
  • Too large (a whole chapter): the embedding becomes a blurry average of many topics, retrieval gets less precise, and you waste context tokens.
  • A common starting point is 200 to 800 tokens, split at natural boundaries (sections, then paragraphs, then sentences), with a little overlap so ideas spanning a boundary survive.
import re

def split_long(paragraph: str, max_chars: int) -> list[str]:
    """Split an over-long paragraph at sentence boundaries."""
    if len(paragraph) <= max_chars:
        return [paragraph]
    out, cur = [], ""
    for s in re.split(r"(?<=[.!?])\s+", paragraph):
        if cur and len(cur) + len(s) + 1 > max_chars:
            out.append(cur)
            cur = s
        else:
            cur = f"{cur} {s}".strip()
    return out + [cur] if cur else out

def chunk_text(text: str, max_chars: int = 2000, overlap_chars: int = 200) -> list[str]:
    """Pack paragraphs into chunks of about max_chars, carrying a little overlap forward."""
    paras = [piece for p in re.split(r"\n\s*\n", text) if p.strip()
             for piece in split_long(p.strip(), max_chars)]
    chunks, cur = [], ""
    for p in paras:
        if cur and len(cur) + len(p) + 2 > max_chars:
            chunks.append(cur)
            tail = cur[-overlap_chars:] if overlap_chars else ""
            cur = tail[tail.find(" ") + 1:] if " " in tail else tail   # start the overlap at a word boundary
        cur = f"{cur}\n\n{p}" if cur else p
    if cur:
        chunks.append(cur)
    return chunks

About 4 characters per token in English, so max_chars=2000 is roughly 500 tokens.

Give every chunk its context

A chunk saying "Tighten to 2 N·m" is useless if retrieval cannot tell it belongs to "Section 4.2: Replacing the filter wheel belt" of the model X manual. Prepend the document title and section path to each chunk's text before embedding. Going further, contextual retrieval asks an LLM to write one or two sentences situating each chunk within its whole document, and prepends that. Anthropic reported this substantially reduced retrieval failures, and it combines well with prompt caching to keep the cost down.

Retrieval#

Dense retrieval#

Embed the chunks and the question; take the nearest chunks by cosine similarity (lesson 12). Strong on paraphrase and meaning.

Keyword retrieval with BM25#

BM25 scores documents by how many query terms they contain, weighted by how rare each term is across the collection (rare terms such as error codes count for a lot), with diminishing returns for repeats and a correction for document length. It is decades old and still excellent for exact terms. Here it is from scratch:

import math
from collections import Counter

def tokenize(s: str) -> list[str]:
    return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", s.lower())     # keeps codes like "e-4071" whole

class BM25:
    def __init__(self, docs: list[str], k1: float = 1.5, b: float = 0.75):
        self.k1, self.b = k1, b
        self.toks = [tokenize(d) for d in docs]
        self.avgdl = sum(map(len, self.toks)) / len(docs)
        df = Counter(w for t in self.toks for w in set(t))           # in how many docs each word appears
        N = len(docs)
        self.idf = {w: math.log(1 + (N - n + 0.5) / (n + 0.5)) for w, n in df.items()}
        self.tf = [Counter(t) for t in self.toks]

    def scores(self, query: str) -> list[float]:
        q = tokenize(query)
        out = []
        for tf, toks in zip(self.tf, self.toks):
            norm = self.k1 * (1 - self.b + self.b * len(toks) / self.avgdl)
            out.append(sum(self.idf[w] * tf[w] * (self.k1 + 1) / (tf[w] + norm) for w in q if w in tf))
        return out

docs = ["Error E-4071 indicates a filter wheel position fault.",
        "Filter wheel faults are often caused by a slipping belt.",
        "Error E-2210 means the GPS has no fix.",
        "Replace the desiccant every six months."]
print([round(s, 2) for s in BM25(docs).scores("what does error E-4071 mean")])
# [1.9, 0.0, 0.69, 0.0]: the exact code dominates

In production use a library (rank_bm25, or the full-text search built into PostgreSQL, Elasticsearch or OpenSearch).

Hybrid search with reciprocal rank fusion#

Dense and keyword scores are on different scales, so do not add them. Reciprocal rank fusion (RRF) combines rankings instead: each document earns 1/(k+rank)1/(k + \text{rank})1/(k+rank) from each retriever, with k≈60k \approx 60k≈60, and the sums are re-sorted. Documents ranked well by both rise to the top.

def rrf(rankings: list[list[int]], k: int = 60) -> list[int]:
    scores = Counter()
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] += 1 / (k + rank + 1)
    return [doc_id for doc_id, _ in scores.most_common()]

print(rrf([[0, 1, 2, 3], [1, 0, 3, 2], [2, 1, 0, 3]]))   # [1, 0, 2, 3]

Reranking#

First-stage retrieval is built for speed: query and document are embedded separately. A cross-encoder reranker reads the query and a candidate together and outputs a relevance score. It is far more accurate and far too slow to run on the whole collection, so use it on the top 20 to 50 candidates and keep the best 3 to 8.

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
scores = reranker.predict([(question, chunks[i]) for i in candidate_ids])
best = [candidate_ids[i] for i in np.argsort(-scores)[:5]]

Hosted rerank APIs exist too. Reranking is often the single cheapest large improvement to a RAG system.

Grounded generation#

The prompt#

Number the retrieved chunks, tell the model to answer only from them, to cite them, and to say when they do not contain the answer.

RAG_PROMPT = """You answer questions about field instruments using only the sources below.

<sources>
{sources}
</sources>

Rules:
- Answer only from the sources. If they do not contain the answer, say so plainly and suggest
  what document might help. Do not use outside knowledge for facts.
- Cite sources inline as [1], [2] after the sentence they support.
- If sources disagree, say so and cite both.
- Be concise: a direct answer first, then any necessary detail or steps.

Question: {question}"""

def format_sources(hits: list[dict]) -> str:
    return "\n\n".join(
        f'<source id="{i}" title="{h["title"]}" section="{h["section"]}">\n{h["text"]}\n</source>'
        for i, h in enumerate(hits, start=1)
    )

The whole pipeline, no framework#

import numpy as np, anthropic
from sentence_transformers import SentenceTransformer, CrossEncoder

class MiniRAG:
    def __init__(self, embed_model="all-MiniLM-L6-v2",
                 rerank_model="cross-encoder/ms-marco-MiniLM-L-6-v2", llm_model="claude-sonnet-5-5"):
        self.embedder = SentenceTransformer(embed_model)
        self.reranker = CrossEncoder(rerank_model)
        self.client = anthropic.Anthropic()
        self.llm_model = llm_model
        self.chunks: list[dict] = []

    def index(self, documents: list[dict]):
        """documents: [{"title": ..., "text": ...}, ...]"""
        for doc in documents:
            for j, chunk in enumerate(chunk_text(doc["text"])):
                section = chunk.splitlines()[0][:80]               # crude: first line as section label
                self.chunks.append({"title": doc["title"], "section": section,
                                    "text": chunk, "id": f'{doc["title"]}#{j}'})
        texts = [f'{c["title"]}\n{c["text"]}' for c in self.chunks]   # title travels with the chunk
        self.vecs = self.embedder.encode(texts, normalize_embeddings=True)
        self.bm25 = BM25(texts)

    def retrieve(self, question: str, k_first=30, k_final=5) -> list[dict]:
        q = self.embedder.encode([question], normalize_embeddings=True)[0]
        dense = list(np.argsort(-(self.vecs @ q))[:k_first])
        sparse = list(np.argsort(-np.array(self.bm25.scores(question)))[:k_first])
        candidates = rrf([dense, sparse])[:k_first]
        scores = self.reranker.predict([(question, self.chunks[i]["text"]) for i in candidates])
        return [self.chunks[candidates[i]] for i in np.argsort(-scores)[:k_final]]

    def answer(self, question: str) -> dict:
        hits = self.retrieve(question)
        prompt = RAG_PROMPT.format(sources=format_sources(hits), question=question)
        r = self.client.messages.create(model=self.llm_model, max_tokens=700, temperature=0,
                                        messages=[{"role": "user", "content": prompt}])
        return {"answer": r.content[0].text, "sources": [h["id"] for h in hits]}

About seventy lines, and it contains every essential idea of a production RAG system. Production adds a persistent vector store, metadata filters and access control, incremental re-indexing, caching, streaming and monitoring.

Advanced retrieval techniques#

Reach for these when your evaluation (below) shows a specific weakness, not by default.

  • Query rewriting. Users write "and what about the other one?" mid-conversation. Have an LLM rewrite the latest message into a standalone search query using the chat history before retrieving.
  • Multi-query. Generate three or four rephrasings of the question, retrieve for each, fuse with RRF. Helps with vague or multi-part questions.
  • HyDE (hypothetical document embeddings). Ask the LLM to write a plausible answer, then embed that for retrieval: answers look more like documents than questions do.
  • Small-to-big (parent document) retrieval. Index small chunks for precise matching, but hand the model the larger parent section they came from.
  • Metadata filtering and routing. Extract filters from the question ("model X", "since 2025") or route to the right collection before searching.
  • Agentic RAG. Give an agent a search tool and let it search repeatedly, refine queries and decide when it has enough (lesson 14). Better for complex questions, slower and costlier.
  • GraphRAG. Extract entities and relationships into a knowledge graph to answer questions that need connecting many documents ("which sites had both firmware 2.3 and belt failures?").

Evaluate and improve#

You cannot improve what you do not measure, and RAG has two separate things to measure.

Build an evaluation set#

Collect 50 to 200 realistic questions with, for each, the chunk or document that contains the answer and a reference answer. Sources: real user questions, questions written by domain experts, and LLM-generated questions from your documents (review them; generated questions tend to be too easy because they reuse the document's wording). Include questions the documents cannot answer, to test abstention.

Retrieval metrics#

  • Recall@k: fraction of questions whose relevant chunk appears in the top kkk. If the right chunk is not retrieved, the model cannot answer correctly; this is the first thing to measure.
  • MRR (mean reciprocal rank): rewards getting the relevant chunk near the top.
def retrieval_eval(rag, eval_set, k=5):
    hits, rr = 0, 0.0
    for item in eval_set:                                   # {"question": ..., "gold_id": "manual-x#12"}
        ids = [c["id"] for c in rag.retrieve(item["question"], k_final=k)]
        if item["gold_id"] in ids:
            hits += 1
            rr += 1 / (ids.index(item["gold_id"]) + 1)
    return {"recall@k": hits / len(eval_set), "mrr": rr / len(eval_set)}

Generation metrics#

  • Faithfulness (groundedness): is every claim supported by the retrieved sources?
  • Answer correctness: does it match the reference answer?
  • Citation accuracy: do the cited sources actually support the sentences they are attached to?
  • Abstention: on unanswerable questions, does it say so?

These are judged by people on a sample, and at scale by an LLM-as-judge with a careful rubric (lesson 15). Libraries such as RAGAS package common versions of these metrics.

Diagnose, then fix#

Symptom Where it broke Typical fixes
Right chunk not in top 30 Parsing, chunking or first-stage retrieval Fix parsing; add titles and context to chunks; hybrid search; better embedding model; query rewriting
Right chunk in top 30 but not top 5 Ranking Add or improve the reranker; increase k_final
Right chunk given, wrong answer Generation Clearer prompt; extract-quotes-then-answer chaining; stronger model
Answer includes facts not in sources Grounding Stricter instructions; faithfulness check step; lower temperature
Confident answer to unanswerable question Abstention Explicit permission and instruction to say "not in the documents"; test cases for it

RAG or long context?#

Context windows of hundreds of thousands of tokens raise the question: why not paste everything? For a small, stable collection (a few long documents) that fits comfortably, long context with prompt caching is simpler and can be more accurate, since nothing is lost to retrieval. RAG wins when the collection is large or changing, when cost and latency per question matter, when you need access control per document, or when you need citations to precise passages. Many systems combine them: retrieve generously, then give the model larger sections than a classic RAG system would.

Hands-on: build, measure and improve a RAG system

  1. Pick a document collection you care about: product manuals, a set of papers, a project's documentation, or the Markdown sources of your learning log. Aim for at least 50 pages.
  2. Index it with MiniRAG. Write 25 evaluation questions with the chunk id that answers each, plus 5 questions the documents cannot answer.
  3. Measure recall@5 and MRR for: dense only, BM25 only, hybrid, and hybrid plus reranker. Record a table.
  4. Answer all 30 questions and grade faithfulness and abstention by hand. Find your three worst failures and classify each with the diagnosis table.
  5. Fix one failure class and re-measure.
Show what a typical first run looks like

Results vary with your documents, but a common pattern is:

Configuration Recall@5 MRR
Dense only 0.68 0.52
BM25 only 0.60 0.47
Hybrid (RRF) 0.80 0.61
Hybrid + reranker 0.88 0.76

To compare configurations, add a mode argument to retrieve that skips the sparse list, the dense list, or the reranker. Typical failure classes on a first run: tables that parsed into nonsense (fix parsing), chunks with no indication of which product they describe (prepend titles and sections), and the model answering an unanswerable question from general knowledge (strengthen the abstention instruction and add a check). The habit to keep: every change gets measured on the same evaluation set. Gut feeling about a few hand-picked questions is how RAG systems quietly get worse.

Check yourself#

1. Why is RAG usually preferred over fine-tuning for giving a model knowledge of company documents?

Knowledge changes; indexes are easy to update. Fine-tuning shapes how a model behaves rather than reliably storing facts.

2. What is the risk of very large chunks?

Chunk size trades precision against context. Start around 200 to 800 tokens and measure.

3. Why combine dense and BM25 results with reciprocal rank fusion rather than adding their scores?

RRF uses only positions in each ranking, so no score normalisation is needed.

4. Your evaluation shows the correct chunk is usually in the top 30 but rarely in the top 5. What should you try first?

The first stage finds it; the ordering is the problem. Rerankers fix ordering.

5. What should a RAG system do when the retrieved sources do not contain the answer?

Abstention is a feature. Test for it explicitly with unanswerable questions.

Key takeaways

  • RAG retrieves relevant passages at question time and asks the model to answer from them with citations. It grounds answers, stays current and respects access control.
  • Quality is won or lost in parsing and chunking: keep structure and metadata, chunk at natural boundaries, and give each chunk its context.
  • Hybrid retrieval (dense plus BM25 fused with RRF) followed by a cross-encoder reranker is a strong default.
  • Prompt for answers only from sources, inline citations and explicit abstention.
  • Measure retrieval (recall@k, MRR) and generation (faithfulness, correctness, abstention) separately, diagnose which stage failed, and re-measure after every change.
