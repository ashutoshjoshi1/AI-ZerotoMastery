17 Deployment, serving and LLMOps

Take an AI system from notebook to production by building a streaming API service, serving open models efficiently with quantisation and the right memory budget, controlling latency and cost, and making everything observable.

Study plan: 4 sessions of about an hour

The anatomy of an LLM application#

A production AI feature is mostly ordinary software around a few model calls:

Keep model-specific code behind a thin internal interface (generate(messages, **options)), keep prompts versioned outside business logic, and make the model name configuration. You will swap models more often than you expect.

A streaming API with FastAPI#

FastAPI is the common choice for Python AI services: typed request validation with Pydantic, async support for many concurrent slow model calls, and automatic API docs.

uv add fastapi "uvicorn[standard]" anthropic pydantic
app.py
import json, logging, time, uuid
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

MODEL = "claude-sonnet-5-5"
log = logging.getLogger("app")
logging.basicConfig(level=logging.INFO, format="%(message)s")

app = FastAPI(title="Instrument assistant")
client = anthropic.AsyncAnthropic(max_retries=3, timeout=60)

class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=4000)

@app.get("/health")
async def health():
    return {"status": "ok"}

@app.post("/ask")
async def ask(req: AskRequest):
    t0 = time.perf_counter()
    r = await client.messages.create(model=MODEL, max_tokens=800,
                                     messages=[{"role": "user", "content": req.question}])
    log.info(json.dumps({"event": "ask", "latency_s": round(time.perf_counter() - t0, 3),
                         "in": r.usage.input_tokens, "out": r.usage.output_tokens}))
    return {"answer": r.content[0].text}

@app.post("/ask/stream")
async def ask_stream(req: AskRequest, request: Request):
    request_id = str(uuid.uuid4())

    async def events():
        t0, first = time.perf_counter(), None
        try:
            async with client.messages.stream(model=MODEL, max_tokens=800,
                                              messages=[{"role": "user", "content": req.question}]) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():          # user left: stop generating and paying
                        return
                    first = first or time.perf_counter()
                    yield f"data: {json.dumps({'text': text})}\n\n"   # server-sent events format
                final = await stream.get_final_message()
            yield f"data: {json.dumps({'done': True})}\n\n"
            log.info(json.dumps({"event": "ask_stream", "id": request_id,
                                 "ttft_s": round((first or time.perf_counter()) - t0, 3),
                                 "total_s": round(time.perf_counter() - t0, 3),
                                 "in": final.usage.input_tokens, "out": final.usage.output_tokens}))
        except anthropic.APIError as e:
            log.error(json.dumps({"event": "upstream_error", "id": request_id, "error": repr(e)}))
            yield f"data: {json.dumps({'error': 'The model service is busy. Please try again.'})}\n\n"

    return StreamingResponse(events(), media_type="text/event-stream")

uv run uvicorn app:app --reload
curl -N -X POST localhost:8000/ask/stream -H "Content-Type: application/json" \
     -d '{"question": "Explain the KV cache in three sentences."}'

Visit localhost:8000/docs for the interactive documentation FastAPI generates. Production additions: authentication, per-user rate limits and quotas, request size limits, timeouts, and the guardrails from lesson 18.

Serving open models#

When you need data to stay on your hardware, very high volume at low cost, offline operation, or a fine-tuned open model (lesson 16), you serve models yourself.

The serving landscape#

Tool Best for Notes
Ollama Local development, desktops, small deployments One command to pull and run models; OpenAI-compatible API
llama.cpp CPUs, Apple silicon, edge devices Runs quantised GGUF models with very little memory; llama-server gives an HTTP API
vLLM High-throughput GPU serving PagedAttention, continuous batching, multiple LoRA adapters, OpenAI-compatible server
SGLang, TensorRT-LLM, TGI High-performance GPU serving Alternatives with different strengths; benchmark on your workload 
# vLLM: an OpenAI-compatible server on port 8000
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 16384 --gpu-memory-utilization 0.9

# serve a base model plus your LoRA adapter from lesson 16
vllm serve Qwen/Qwen2.5-0.5B-Instruct --enable-lora --lora-modules notes=./notes-to-json-lora

Your lesson 10 code then works by pointing the OpenAI client at http://localhost:8000/v1, using model="notes" to select the adapter.

Why serving is hard: memory and batching#

Generation is mostly limited by memory bandwidth: every new token requires reading all the model weights from GPU memory. Serving one user at a time leaves the GPU's compute mostly idle. Serving systems therefore batch many users' requests together so each weight read does work for many sequences. Two innovations made this efficient:

  • Continuous batching: new requests join the running batch as soon as others finish, instead of waiting for a whole batch to complete.
  • PagedAttention (vLLM): the KV cache (lesson 08) is stored in fixed-size pages, like virtual memory, eliminating fragmentation so far more sequences fit in memory at once.

Quantisation#

Store weights in fewer bits to cut memory and speed up the memory-bound decoding:

Precision Bytes per parameter 8B model weights Quality
FP32 4 32 GB Reference (rarely used for inference)
BF16 / FP16 2 16 GB Standard
INT8 / FP8 1 8 GB Usually near-lossless
4-bit (GPTQ, AWQ, GGUF Q4) about 0.5 about 4 to 5 GB Small loss, larger on hard reasoning; measure it

GGUF is the file format used by llama.cpp and Ollama, with variants such as Q4_K_M (a good default) and Q8_0. AWQ and GPTQ are 4-bit formats popular on GPUs. Always re-run your eval set after quantising: the average benchmark loss may be small while your task suffers.

The GPU memory budget#

def serving_memory_gb(params_billion, weight_bytes, layers, kv_heads, head_dim,
                      context_tokens, concurrent_seqs, kv_bytes=2):
    weights = params_billion * 1e9 * weight_bytes
    kv_per_token = 2 * layers * kv_heads * head_dim * kv_bytes      # keys and values, every layer
    kv_total = kv_per_token * context_tokens * concurrent_seqs
    return round(weights / 1e9, 1), round(kv_total / 1e9, 1)

# an 8B model with 32 layers, 8 KV heads of dimension 128:
print(serving_memory_gb(8, 2, 32, 8, 128, 8192, 16))     # (16.0, 17.2): BF16 weights + 16 users at 8k context
print(serving_memory_gb(8, 0.5, 32, 8, 128, 8192, 16))   # (4.0, 17.2): 4-bit weights; KV cache now dominates

Add 10 to 20% for activations and overheads. The lesson of the arithmetic: for many users and long contexts, KV cache memory, not weights, limits capacity. Shorter maximum context, KV-cache quantisation and grouped-query-attention models all raise the number of concurrent users per GPU.

Latency, throughput and cost#

Measure the right things#

  • Time to first token (TTFT): dominated by prompt length (the "prefill"). What makes an app feel responsive.
  • Time per output token (TPOT) or tokens per second: the streaming speed.
  • Total latency ≈ TTFT + output tokens × TPOT. Output length is the biggest lever: ask for concise answers.
  • Throughput: requests or tokens per second the system sustains.
  • Report p50 and p95 (or p99), not averages. Users remember the slow requests.

Levers, roughly in order of payoff#

  1. Shorter outputs: specify length and format. Output tokens are slow and expensive.
  2. Smaller models where they pass the eval, with routing: a cheap model for easy requests, escalate the rest.
  3. Prompt caching for long shared prefixes (lesson 10).
  4. Response caching: identical requests get the stored answer. A semantic cache also matches near-identical questions by embedding similarity; set the similarity threshold conservatively and exclude anything user-specific or time-sensitive.
  5. Trim context: retrieve fewer, better chunks (reranking); summarise long histories.
  6. Parallelise independent calls (lesson 14) and batch offline work (batch APIs, lesson 10).
  7. Streaming does not reduce total time but transforms perceived speed.
import numpy as np

class SemanticCache:
    def __init__(self, embed, threshold=0.95):
        self.embed, self.threshold = embed, threshold
        self.vecs, self.answers = [], []

    def get(self, question: str):
        if not self.vecs:
            return None
        q = self.embed(question)
        sims = np.array(self.vecs) @ q
        i = int(sims.argmax())
        return self.answers[i] if sims[i] >= self.threshold else None

    def put(self, question: str, answer: str):
        self.vecs.append(self.embed(question)); self.answers.append(answer)

Cost control in practice#

  • Track cost per request, per feature and per user, from logged token counts.
  • Set budgets and alerts, plus per-user quotas to stop abuse and runaway agents.
  • Re-run the cost estimate from lesson 10 whenever prompts grow: added context is the usual culprit.

Observability#

LLM systems fail quietly: no exception, just a worse answer. You need to see inside every request.

Tracing#

A trace records one request end to end as nested spans: the API call, query rewriting, retrieval (with the ids and scores of chunks returned), reranking, each model call (prompt version, model, parameters, full input and output, token counts, latency, cost), each tool call, and the final response. When a user reports a bad answer, the trace tells you which stage failed (lesson 13's diagnosis table, applied in production).

Tools: OpenTelemetry with its generative-AI conventions for vendor-neutral tracing; LLM-specific platforms such as Langfuse (open source), Arize Phoenix, LangSmith, Helicone or Weights & Biases Weave, which add prompt management, cost tracking, datasets and evals on top of traces.

# a minimal hand-rolled span recorder; production code would use OpenTelemetry or a tracing SDK
import contextlib, json, time, uuid

@contextlib.contextmanager
def span(name, trace_id, **attrs):
    t0 = time.perf_counter()
    record = {"trace": trace_id, "span": name, **attrs}
    try:
        yield record                      # callers add outputs, token counts, etc.
    except Exception as e:
        record["error"] = repr(e); raise
    finally:
        record["ms"] = round(1000 * (time.perf_counter() - t0), 1)
        print(json.dumps(record))         # ship to your log pipeline

trace_id = str(uuid.uuid4())
with span("retrieve", trace_id, query="belt slipping") as s:
    s["chunk_ids"] = ["manual-x#12", "manual-x#13"]

Traces contain user data

Prompts and outputs often include personal or confidential information. Decide what to store, redact where needed, restrict access, and set retention periods. Privacy obligations apply to logs too.

Monitoring#

Dashboards and alerts on: error rate and upstream provider errors; latency percentiles; tokens and cost per request; cache hit rate; refusal and "I don't know" rates; user feedback; and a regular sample of traces scored by your LLM judges (lesson 15). Sudden shifts in any of these, such as a spike in refusals after a provider's model update, are often the first sign something changed.

CI/CD for AI systems#

  • Version everything: code, prompts, model identifiers, retrieval index builds, eval datasets.
  • Gate deploys on evals: the smoke eval set runs on every change; the full set before releasing prompt or model changes.
  • Roll out gradually: canary or percentage rollouts, with automatic rollback on error or quality alarms.
  • Shadow testing: run a candidate model on live traffic in parallel without showing its answers, and compare offline.

Hands-on: production-ise your RAG system

  1. Wrap your lesson 13 MiniRAG in a FastAPI service with /ask and /ask/stream, validating input with Pydantic.
  2. Log one JSON line per request with: request id, retrieved chunk ids, model, input and output tokens, TTFT, total latency and estimated cost.
  3. Add an exact-match response cache, then a semantic cache, and measure hit rates on a replay of 100 questions (include paraphrases).
  4. Write a load test (for example with asyncio firing 50 concurrent requests, or the Locust tool) and report p50 and p95 latency.
  5. Containerise it and run it with docker run.
Show what to measure and typical findings 

import asyncio, time, httpx, numpy as np

async def one(client, q):
    t0 = time.perf_counter()
    r = await client.post("http://localhost:8000/ask", json={"question": q}, timeout=120)
    return time.perf_counter() - t0, r.status_code

async def load_test(questions, concurrency=50):
    async with httpx.AsyncClient() as client:
        res = await asyncio.gather(*(one(client, q) for q in questions[:concurrency]))
    lat = np.array([t for t, code in res if code == 200])
    print(f"ok {len(lat)}/{len(res)}  p50 {np.percentile(lat, 50):.2f}s  p95 {np.percentile(lat, 95):.2f}s")

# asyncio.run(load_test(my_questions))
Typical findings: p95 is often two to three times p50, driven by long answers and provider-side queueing; a few requests may hit rate limits under burst load, which your retries should absorb (check the logs). The semantic cache catches paraphrases that the exact cache misses, but with a loose threshold it also returns answers to subtly different questions; reading those false hits is the best way to choose the threshold. The JSON logs make all of this answerable in a few lines of pandas (lesson 01 skills, paying off).

Check yourself#

1. What mainly determines time to first token?

Prefill processes the whole prompt first. Long contexts mean slower first tokens.

2. You serve an 8B model in 4-bit for many users with long contexts and run out of GPU memory. What is the likely culprit?

At 4-bit, weights take about 4 GB; the KV cache for many long sequences can be several times that.

3. Why do serving engines batch requests from many users?

Continuous batching and PagedAttention raise throughput dramatically.

4. What is the main risk of a semantic cache?

Use a conservative threshold, exclude personal and time-sensitive queries, and review false hits.

5. A user reports a wrong answer from your RAG service. What lets you find which stage failed?

Traces turn "the answer was bad" into "retrieval missed the right chunk" or "the model ignored it".

Key takeaways

  • Production AI is ordinary software around model calls: validate, authenticate, rate-limit, stream, time out, and keep the model behind a thin interface.
  • Self-hosting uses servers such as vLLM, Ollama and llama.cpp. Continuous batching and PagedAttention make GPUs efficient; quantisation shrinks weights, but measure quality afterwards.
  • Budget GPU memory as weights plus KV cache; with many users and long contexts, the cache dominates.
  • Cut latency and cost with shorter outputs, smaller routed models, prompt and response caching, trimmed context and parallelism. Track p95, not averages.
  • Trace every request end to end, monitor quality as well as uptime, version everything, and gate releases on evals.
