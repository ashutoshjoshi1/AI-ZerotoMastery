Session 1 of 4The anatomy of an LLM application, a streaming API with FastAPI, and shipping it in a container

The anatomy of an LLM application#

A production AI feature is mostly ordinary software around a few model calls:

Keep model-specific code behind a thin internal interface (generate(messages, **options)), keep prompts versioned outside business logic, and make the model name configuration. You will swap models more often than you expect.

A streaming API with FastAPI#

FastAPI is the common choice for Python AI services: typed request validation with Pydantic, async support for many concurrent slow model calls, and automatic API docs.

Terminal
uv add fastapi "uvicorn[standard]" anthropic pydantic
app.py
import json, logging, time, uuid
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

MODEL = "claude-sonnet-5-5"
log = logging.getLogger("app")
logging.basicConfig(level=logging.INFO, format="%(message)s")

app = FastAPI(title="Instrument assistant")
client = anthropic.AsyncAnthropic(max_retries=3, timeout=60)

class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=4000)

def answer_text(message) -> str:
    """The reply may start with a thinking block, so pick the text block rather than content[0]."""
    return "".join(b.text for b in message.content if b.type == "text")

@app.get("/health")
async def health():
    return {"status": "ok"}

@app.post("/ask")
async def ask(req: AskRequest):
    t0 = time.perf_counter()
    r = await client.messages.create(model=MODEL, max_tokens=800,
                                     messages=[{"role": "user", "content": req.question}])
    log.info(json.dumps({"event": "ask", "latency_s": round(time.perf_counter() - t0, 3),
                         "in": r.usage.input_tokens, "out": r.usage.output_tokens}))
    return {"answer": answer_text(r)}

@app.post("/ask/stream")
async def ask_stream(req: AskRequest, request: Request):
    request_id = str(uuid.uuid4())

    async def events():
        t0, first = time.perf_counter(), None
        try:
            async with client.messages.stream(model=MODEL, max_tokens=800,
                                              messages=[{"role": "user", "content": req.question}]) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():          # user left: stop generating and paying
                        return
                    first = first or time.perf_counter()
                    yield f"data: {json.dumps({'text': text})}\n\n"   # server-sent events format
                final = await stream.get_final_message()
            yield f"data: {json.dumps({'done': True})}\n\n"
            log.info(json.dumps({"event": "ask_stream", "id": request_id,
                                 "ttft_s": round((first or time.perf_counter()) - t0, 3),
                                 "total_s": round(time.perf_counter() - t0, 3),
                                 "in": final.usage.input_tokens, "out": final.usage.output_tokens}))
        except anthropic.APIError as e:
            log.error(json.dumps({"event": "upstream_error", "id": request_id, "error": repr(e)}))
            yield f"data: {json.dumps({'error': 'The model service is busy. Please try again.'})}\n\n"

    return StreamingResponse(events(), media_type="text/event-stream")

Two details are easy to miss. The SDK's text_stream yields only text, but a full reply is a list of content blocks that may begin with a thinking block, so never read content[0].text; answer_text picks the text blocks. And the stream loop checks whether the client has gone away, because tokens you generate for a closed connection still cost money.

Session 2 of 4Serving open models: the serving landscape, quantisation choices and the GPU memory budget

Serving open models#

When you need data to stay on your hardware, very high volume at low cost, offline operation, or a fine-tuned open model (lesson 18), you serve models yourself. This session covers the operator's decisions: which server, which precision, how much memory. Lesson 20 explains the mechanics underneath them: prefill and decode, continuous batching, PagedAttention, prefix caching, speculative decoding and the quantisation formats.

Why serving is hard, in one paragraph#

Generating a token means reading every weight of the model from GPU memory, so decoding one user at a time leaves the GPU's arithmetic units mostly idle: the bottleneck is memory bandwidth, not compute. Serving systems therefore batch many users' requests so that each read of the weights does work for many sequences, admit new requests into the running batch as others finish (continuous batching), and manage the KV cache (lesson 08) in pages so that far more sequences fit in memory. The operator's consequence: throughput per GPU depends on how many sequences fit at once, which the memory budget below decides.

Quantisation: the operator's choice#

Store weights in fewer bits to cut memory and speed up memory-bound decoding:

Precision Bytes per parameter 8B model weights Quality
FP32 4 32 GB Reference (rarely used for inference)
BF16 / FP16 2 16 GB Standard
INT8 / FP8 1 8 GB Usually near-lossless
4-bit (GPTQ, AWQ, GGUF Q4) about 0.5 about 4 to 5 GB Small loss, larger on hard reasoning; measure it

GGUF is the file format used by llama.cpp and Ollama, with variants such as Q4_K_M (a good default) and Q8_0. AWQ and GPTQ are 4-bit formats popular on GPUs. Always re-run your eval set after quantising: the average benchmark loss may be small while your task suffers. How these formats work, and why 4-bit costs more on reasoning than on chat, is in lesson 20.

The GPU memory budget#

Python
def serving_memory_gb(params_billion, weight_bytes, layers, kv_heads, head_dim,
                      context_tokens, concurrent_seqs, kv_bytes=2):
    weights = params_billion * 1e9 * weight_bytes
    kv_per_token = 2 * layers * kv_heads * head_dim * kv_bytes      # keys and values, every layer
    kv_total = kv_per_token * context_tokens * concurrent_seqs
    return round(weights / 1e9, 1), round(kv_total / 1e9, 1)

# an 8B model with 32 layers, 8 KV heads of dimension 128:
print(serving_memory_gb(8, 2, 32, 8, 128, 8192, 16))     # (16.0, 17.2): BF16 weights + 16 users at 8k context
print(serving_memory_gb(8, 0.5, 32, 8, 128, 8192, 16))   # (4.0, 17.2): 4-bit weights; KV cache now dominates

Add 10 to 20% for activations and overheads. The lesson of the arithmetic: for many users and long contexts, KV cache memory, not weights, limits capacity. Shorter maximum context, KV-cache quantisation and grouped-query-attention models all raise the number of concurrent users per GPU. The numbers you need (layers, KV heads, head dimension) are in every model's configuration file.

Python
def max_concurrent(gpu_gb, weight_bytes, context_tokens, kv_bytes=2,
                   params_billion=8, layers=32, kv_heads=8, head_dim=128, headroom=0.15):
    weights_gb = params_billion * weight_bytes
    kv_per_seq_gb = 2 * layers * kv_heads * head_dim * kv_bytes * context_tokens / 1e9
    free = gpu_gb * (1 - headroom) - weights_gb
    return max(0, int(free // kv_per_seq_gb))

print(f"{'GPU':>6} {'weights':>8} {'context':>8} {'kv':>3}  users")
for gpu in [24, 48, 80]:
    for name, wb in [("bf16", 2), ("int8", 1), ("4-bit", 0.5)]:
        print(f"{gpu:>4}GB {name:>8} {8192:>8} {2:>3}  {max_concurrent(gpu, wb, 8192)}")
print(f"{80:>4}GB {'4-bit':>8} {8192:>8} {1:>3}  {max_concurrent(80, 0.5, 8192, kv_bytes=1)}")
print(f"{80:>4}GB {'4-bit':>8} {4096:>8} {2:>3}  {max_concurrent(80, 0.5, 4096)}")

Each 8k-token sequence costs about 1.07 GB of KV cache. A 24 GB card with 4-bit weights has about 16 GB left, so 15 users, however small the weights get: the cache, not the weights, is the wall. An 80 GB card at BF16 holds about 48 users, and at 4-bit about 60. Quantising the KV cache to 8-bit doubles that to about 120, and so, on its own, does halving the context limit: both halve the bytes each sequence needs. The cheapest route to 32 users at 8k is a single 48 GB card with 4-bit weights (about 34 users). INT8 weights fall just short at about 30, which is where KV-cache quantisation becomes the next lever. Real servers reserve memory differently, so treat the numbers as a planning estimate and confirm with a load test.

Session 3 of 4Latency, throughput and cost: metrics, caching, routing, budgets and cost dashboards

Latency, throughput and cost#

Measure the right things#

  • Time to first token (TTFT): dominated by prompt length (the "prefill"). What makes an app feel responsive.
  • Time per output token (TPOT), also called inter-token latency, or its inverse, tokens per second: the streaming speed.
  • Total latency ≈ TTFT + output tokens × TPOT. Output length is the biggest lever: ask for concise answers.
  • Throughput: requests or tokens per second the system sustains.
  • Report p50 and p95 (or p99), not averages. Users remember the slow requests.

Lesson 20 works through where each of these numbers comes from inside a serving engine. Here they are the things you log and alert on.

Levers, roughly in order of payoff#

  1. Shorter outputs: specify length and format. Output tokens are slow and expensive.
  2. Smaller models where they pass the eval, with routing: a cheap model for easy requests, escalate the rest.
  3. Prompt caching for long shared prefixes (lesson 10).
  4. Response caching: identical requests get the stored answer. A semantic cache also matches near-identical questions by embedding similarity; set the similarity threshold conservatively and exclude anything user-specific or time-sensitive.
  5. Trim context: retrieve fewer, better chunks (reranking); summarise long histories (lesson 16).
  6. Parallelise independent calls (lesson 15) and batch offline work (batch APIs, lesson 10).
  7. Streaming does not reduce total time but transforms perceived speed.
Python
import numpy as np

class SemanticCache:
    def __init__(self, embed, threshold=0.95):
        self.embed, self.threshold = embed, threshold
        self.vecs, self.answers = [], []

    def get(self, question: str):
        if not self.vecs:
            return None
        q = self.embed(question)
        sims = np.array(self.vecs) @ q
        i = int(sims.argmax())
        return self.answers[i] if sims[i] >= self.threshold else None

    def put(self, question: str, answer: str):
        self.vecs.append(self.embed(question)); self.answers.append(answer)

Cost control in practice#

  • Track cost per request, per feature and per user, from logged token counts.
  • Set budgets and alerts, plus per-user quotas to stop abuse and runaway agents.
  • Re-run the cost estimate from lesson 10 whenever prompts grow: added context is the usual culprit.

A cost dashboard from your logs#

The JSON log lines the service writes are the raw material for every cost question. A cost dashboard needs only four things per request: a timestamp, a feature name, input and output token counts, and the model, from which cost follows by multiplying by the price list you keep in configuration. Aggregate by day and feature, by user for quota alerts, and by model to see what a routing change saved. Add the cache hit rate: every hit is a request that cost nothing. The point is not the chart but the habit: the person who changed the prompt sees the cost line move the next morning.

Python
import json, random
import pandas as pd

random.seed(0)
PRICES = {"big": (2.0, 10.0), "small": (0.10, 0.50)}         # dollars per million input / output tokens
rows = []
for i in range(2000):
    day = i % 7
    feature = random.choice(["ask", "ask", "summarise", "extract"])
    model = "small" if feature == "ask" and random.random() < 0.3 else "big"
    inp = {"ask": 900, "summarise": 3000, "extract": 1500}[feature] * (2 if feature == "summarise" and day == 4 else 1)
    inp = int(random.gauss(inp, inp * 0.2)); out = int(random.gauss(250, 80))
    hit = feature == "ask" and random.random() < 0.25
    rows.append({"ts": f"2026-10-{12 + day:02d}", "feature": feature, "model": model,
                 "in": 0 if hit else inp, "out": 0 if hit else out, "cache_hit": hit,
                 "latency_s": 0.05 if hit else round(0.4 + out * (0.03 if model == "big" else 0.015) + random.random(), 2)})
with open("requests.jsonl", "w") as f:
    for r in rows:
        f.write(json.dumps(r) + "\n")

df = pd.read_json("requests.jsonl", lines=True)
df["cost"] = [(PRICES[m][0] * i + PRICES[m][1] * o) / 1e6 for m, i, o in zip(df.model, df["in"], df["out"])]
print(df.pivot_table(index="ts", columns="feature", values="cost", aggfunc="sum").round(2))
print("cache hit rate:", round(df.cache_hit.mean(), 3))
print(df.groupby("feature").latency_s.quantile([0.5, 0.95]).unstack().round(2))
ask = df[(df.feature == "ask") & ~df.cache_hit]
would_cost = (PRICES["big"][0] * ask["in"] + PRICES["big"][1] * ask["out"]).sum() / 1e6
print(f"ask: actual ${ask.cost.sum():.2f} versus ${would_cost:.2f} with no routing")

The summarise column jumps on the fifth day (16 October), which is exactly the kind of silent prompt growth that a dashboard catches and a unit test never will. Routing 30% of the easy questions to the small model cuts the ask bill by roughly a quarter; whether that is worth it depends on the eval, not the dashboard. In production the same three queries run against a log store or a metrics system instead of a file, and the price table lives in configuration next to the model name.

Session 4 of 4Observability: tracing, monitoring and drift, A/B and shadow deployments, and CI/CD

Observability#

LLM systems fail quietly: no exception, just a worse answer. You need to see inside every request.

Tracing#

A trace records one request end to end as nested spans: the API call, query rewriting, retrieval (with the ids and scores of chunks returned), reranking, each model call (prompt version, model, parameters, full input and output, token counts, latency, cost), each tool call, and the final response. When a user reports a bad answer, the trace tells you which stage failed (lesson 14's diagnosis table, applied in production).

Tools: OpenTelemetry with its generative-AI conventions for vendor-neutral tracing; LLM-specific platforms such as Langfuse (open source), Arize Phoenix, LangSmith, Helicone or Weights & Biases Weave, which add prompt management, cost tracking, datasets and evals on top of traces.

Python
# a minimal hand-rolled span recorder; production code would use OpenTelemetry or a tracing SDK
import contextlib, json, time, uuid

@contextlib.contextmanager
def span(name, trace_id, **attrs):
    t0 = time.perf_counter()
    record = {"trace": trace_id, "span": name, **attrs}
    try:
        yield record                      # callers add outputs, token counts, etc.
    except Exception as e:
        record["error"] = repr(e); raise
    finally:
        record["ms"] = round(1000 * (time.perf_counter() - t0), 1)
        print(json.dumps(record))         # ship to your log pipeline

trace_id = str(uuid.uuid4())
with span("retrieve", trace_id, query="belt slipping") as s:
    s["chunk_ids"] = ["manual-x#12", "manual-x#13"]

Traces contain user data

Prompts and outputs often include personal or confidential information. Decide what to store, redact where needed, restrict access, and set retention periods. Privacy obligations apply to logs too.

Monitoring#

Dashboards and alerts on: error rate and upstream provider errors; latency percentiles; tokens and cost per request; cache hit rate; refusal and "I don't know" rates; user feedback; and a regular sample of traces scored by your LLM judges (lesson 17). Sudden shifts in any of these, such as a spike in refusals after a provider's model update, are often the first sign something changed.

Monitoring for drift#

Drift is change without error. Three kinds matter for LLM systems:

  • Input drift: users ask about new products, in new languages, with longer messages, or a new client starts sending a different kind of traffic. Track the distribution of input length, language, detected topic and the share of each request type.
  • Output drift: answer length, refusal rate, tool-use rate and judge scores shift. The usual cause is a provider model update, a prompt change that nobody evaluated, or a retrieval index rebuild.
  • Quality drift: the offline eval set still passes but online feedback worsens, which means the eval set no longer represents the traffic. Feed the new cases back into it.

A practical detector compares this week's distribution of a metric with a reference week. For categorical metrics (topic, request type, language) a chi-square test or the population stability index works; for numeric ones, compare percentiles. Alert on the comparison, not on the raw number, so that normal daily variation does not page anyone.

Python
import numpy as np
rng = np.random.default_rng(0)
CATS = ["hardware", "software", "data", "other"]

def week(mix, n=1400):
    counts = rng.multinomial(n, mix)
    return counts / counts.sum()

def psi(p, q, eps=1e-6):
    p, q = np.asarray(p) + eps, np.asarray(q) + eps
    return float(np.sum((p - q) * np.log(p / q)))

ref = week([0.5, 0.2, 0.2, 0.1])
for name, mix in [("week 2", [0.5, 0.2, 0.2, 0.1]), ("week 3", [0.35, 0.15, 0.4, 0.1])]:
    value = psi(week(mix), ref)
    print(f"{name}: PSI {value:.3f} {'ALERT' if value > 0.2 else 'ok'}")

ref_days = rng.normal(180, 12, 7)                       # mean input length per day, reference week
mu, sd = ref_days.mean(), ref_days.std()
for name, mean in [("week 2", 180), ("week 3", 260)]:
    days = rng.normal(mean, 12, 7)
    flags = [f"day {i + 1}" for i, d in enumerate(days) if abs(d - mu) > 3 * sd]
    print(f"{name}: mean length {days.mean():.0f}, alerts: {flags or 'none'}")

Week two lands near zero (sampling noise alone gives a PSI of a few thousandths), and week three lands at about 0.21, just over the 0.2 line, because a fifth of the traffic moved category. A shift that size sits right at the threshold, so another week's sample could fall just under it: a PSI between 0.1 and 0.2 deserves a look, not silence. The length detector is the same idea for a numeric metric. Two refinements for production: compare against a rolling reference so that slow seasonal change does not accumulate into a false alert, and when an alert fires, pull a sample of the new traffic into your eval set before anyone touches the prompt.

Rolling out changes: canaries, A/B tests and shadow deployments#

Every prompt, model or index change is a deployment, and there are three ways to expose it to traffic:

  • Canary release: send a small share of requests (1 to 5%) to the new version, watch the error, latency and quality metrics, then widen or roll back. This catches crashes and gross regressions cheaply.
  • A/B test: split users randomly between versions and compare the outcome the product exists for (task completion, escalation rate, retention) with enough traffic for the difference to be real (the statistics of lesson 17 apply). This is the only way to learn whether a quality gain users notice.
  • Shadow deployment: run the candidate on live traffic in parallel but show nobody its answers; store both outputs and compare them offline with your judges. It costs double inference for the shadowed share but carries no user risk, which makes it the right first step for a model swap.

Whichever you use, the versions must be distinguishable in traces and logs, and rollback must be a configuration change, not a code deploy.

CI/CD for AI systems#

  • Version everything: code, prompts, model identifiers, retrieval index builds, eval datasets.
  • Gate deploys on evals: the smoke eval set runs on every change; the full set before releasing prompt or model changes.
  • Roll out gradually: canary or percentage rollouts, with automatic rollback on error or quality alarms.
  • Shadow first for model swaps, then canary, then the A/B test that decides.

Training and serving a model of your own adds the infrastructure side of this, from checkpoints to multi-GPU clusters; lesson 29 covers it.

Show what to measure and typical findings
Python
import asyncio, time, httpx, numpy as np

async def one(client, q):
    t0 = time.perf_counter()
    r = await client.post("http://localhost:8000/ask", json={"question": q}, timeout=120)
    return time.perf_counter() - t0, r.status_code

async def load_test(questions, concurrency=50):
    async with httpx.AsyncClient() as client:
        res = await asyncio.gather(*(one(client, q) for q in questions[:concurrency]))
    lat = np.array([t for t, code in res if code == 200])
    print(f"ok {len(lat)}/{len(res)}  p50 {np.percentile(lat, 50):.2f}s  p95 {np.percentile(lat, 95):.2f}s")

# asyncio.run(load_test(my_questions))

Typical findings: p95 is often two to three times p50, driven by long answers and provider-side queueing; a few requests may hit rate limits under burst load, which your retries should absorb (check the logs). The semantic cache catches paraphrases that the exact cache misses, but with a loose threshold it also returns answers to subtly different questions; reading those false hits is the best way to choose the threshold. The JSON logs make all of this answerable in a few lines of pandas (lesson 01 skills, paying off).

Check yourself#

1. What mainly determines time to first token?

Prefill processes the whole prompt first. Long contexts mean slower first tokens.

2. You serve an 8B model in 4-bit for many users with long contexts and run out of GPU memory. What is the likely culprit?

At 4-bit, weights take about 4 GB; the KV cache for many long sequences can be several times that.

3. Why do serving engines batch requests from many users?

Continuous batching and paged KV caches raise throughput dramatically.

4. You want to swap to a new model version with no risk to users. What is the right first step?

Shadowing costs extra inference but exposes nobody to the candidate; canary and A/B come after.

5. A user reports a wrong answer from your RAG service. What lets you find which stage failed?

Traces turn "the answer was bad" into "retrieval missed the right chunk" or "the model ignored it".

Key takeaways

  • Production AI is ordinary software around model calls: validate, authenticate, rate-limit, stream, time out, test with a fake model, and keep the model behind a thin interface.
  • Self-hosting uses servers such as vLLM, Ollama and llama.cpp. Quantisation shrinks weights, but measure quality afterwards; the mechanics are in lesson 20.
  • Budget GPU memory as weights plus KV cache; with many users and long contexts, the cache dominates.
  • Cut latency and cost with shorter outputs, smaller routed models, prompt and response caching, trimmed context and parallelism. Track p95, not averages, and keep a cost dashboard.
  • Trace every request end to end, monitor quality and drift as well as uptime, version everything, roll out through shadow, canary and A/B stages, and gate releases on evals.
