From word vectors to text embeddings

In lesson you saw word vectors whose geometry captures meaning. Text embedding models do the same for whole sentences, paragraphs or documents: a transformer encoder reads the text and outputs one fixed-length vector (typically 384 to 3,072 numbers). They are trained, usually with contrastive learning, so that texts with similar meaning land close together and unrelated texts land far apart. Training data is millions of pairs that should match: a question and its answer, a title and its article, two paraphrases.

That gives you a superpower: search by meaning, not by keywords. "Instrument stopped recording overnight" matches "data logging halted after midnight" despite sharing almost no words. Embeddings power semantic search, RAG (next lesson), recommendation, de-duplication, clustering and classification with few labels.

Getting embeddings

# uv add sentence-transformers
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")   # small, fast, 384 dims; downloads once (~90 MB)
texts = [
    "The instrument stopped recording overnight.",
    "Data logging halted shortly after midnight.",
    "Calibrate the spectrometer before each campaign.",
    "What is the capital of France?",
]
E = model.encode(texts, normalize_embeddings=True)  # (4, 384), unit length
print(E.shape)
print((E @ E.T).round(2))                           # cosine similarity matrix
from openai import OpenAI
import numpy as np

client = OpenAI()
r = client.embeddings.create(model="text-embedding-3-small", input=texts)
E = np.array([d.embedding for d in r.data])          # (4, 1536)
E /= np.linalg.norm(E, axis=1, keepdims=True)

In the similarity matrix the first two sentences score far higher with each other than with the others, even though they share almost no words. That is the whole point.

Choosing an embedding model

  • Quality on your data matters more than leaderboard rank. The public MTEB leaderboard is a useful starting shortlist; your own retrieval test (below) decides.
  • Dimensions cost memory and search time. 384 dimensions is often plenty; some models support truncating to fewer dimensions with small quality loss.
  • Maximum input length: many small models only read 256 to 512 tokens. Longer text is silently truncated, which is one reason RAG splits documents into chunks.
  • Language and domain: multilingual models for mixed-language data; domain-tuned models (code, biomedical, legal) can help a lot.
  • Query versus document prefixes: some models expect instructions such as "query:" and "passage:" prepended. Read the model card; skipping this quietly lowers quality.
  • Never mix models: embeddings from different models (or versions) live in different spaces. Change the model, re-embed everything.

Semantic search from scratch

With normalised vectors, search is a matrix multiplication and a sort. Do it yourself once before reaching for tools.

import numpy as np

docs = [
    "Replace the desiccant cartridge every six months in humid climates.",
    "If the tracker loses the sun, check the GPS time and the level of the head.",
    "Dark current increases with detector temperature; keep the cooler running.",
    "The filter wheel position error usually means a slipping belt.",
    "Upload data nightly over the cellular modem; retry on failure.",
    # ... in practice, thousands of chunks from manuals, logs and tickets
]
doc_vecs = model.encode(docs, normalize_embeddings=True)          # (N, 384)

def search(query: str, k: int = 3):
    q = model.encode([query], normalize_embeddings=True)[0]       # (384,)
    scores = doc_vecs @ q                                         # (N,) cosine similarities
    top = np.argsort(-scores)[:k]
    return [(round(float(scores[i]), 3), docs[i]) for i in top]

for hit in search("why is the noise in my spectra higher when it's hot?"):
    print(hit)
# the dark-current/temperature document ranks first, despite little word overlap

Exact search over a few hundred thousand vectors this way takes milliseconds on a laptop. You may never need anything fancier for a prototype.

Semantic versus keyword search

Embeddings are not strictly better than keyword search. They are worse at exact identifiers: part numbers, error codes, function names, rare acronyms. A query for "error E-4071" wants documents containing exactly that string; an embedding may happily return other error codes that "feel" similar. Keyword methods such as BM25 excel at this. Strong systems combine both (hybrid search), which you will build in lesson .

FAISS and vector databases

FAISS: a fast in-process index

FAISS (from Meta) is a library of highly optimised vector indexes. IndexFlatIP is exact inner-product search, the same maths as above, done fast.

# uv add faiss-cpu
import faiss

d = doc_vecs.shape[1]
index = faiss.IndexFlatIP(d)                 # exact search by inner product (= cosine for unit vectors)
index.add(doc_vecs.astype("float32"))
q = model.encode(["sun tracking problems"], normalize_embeddings=True).astype("float32")
scores, ids = index.search(q, 3)             # both (1, 3)
print([docs[i] for i in ids[0]])
faiss.write_index(index, "manuals.faiss")    # save; faiss.read_index to load

FAISS stores only vectors and integer ids. You keep the texts and metadata elsewhere and look them up by id.

Vector databases

A vector database adds what an application needs around the index: storing text and metadata with each vector, filtering ("only documents for instrument model X, newer than 2024"), updates and deletes, persistence, access control and scaling. Options range from embedded libraries to managed services:

Option Shape Good for
NumPy / FAISS In-process library Prototypes, offline jobs, up to millions of vectors on one machine
Chroma, LanceDB Embedded database Local apps and small services with metadata filtering
pgvector Extension to PostgreSQL Teams already on Postgres; vectors next to relational data and SQL filters
Qdrant, Weaviate, Milvus Dedicated vector database servers Large collections, heavy filtering, high query load
Managed services (e.g. Pinecone, cloud search products) Hosted Teams that do not want to operate infrastructure 
# uv add chromadb
import chromadb

db = chromadb.PersistentClient(path="vector_db")
col = db.get_or_create_collection("manuals", metadata={"hnsw:space": "cosine"})
col.add(
    ids=[f"doc-{i}" for i in range(len(docs))],
    documents=docs,
    embeddings=doc_vecs.tolist(),
    metadatas=[{"source": "field-manual", "section": i} for i in range(len(docs))],
)
res = col.query(
    query_embeddings=model.encode(["belt slipping"], normalize_embeddings=True).tolist(),
    n_results=2,
    where={"source": "field-manual"},          # metadata filter
)
print(res["documents"])
-- the same idea in PostgreSQL with pgvector
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, source text, body text, embedding vector(384));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT body FROM chunks
WHERE source = 'field-manual'
ORDER BY embedding <=> $1      -- <=> is cosine distance; $1 is the query vector
LIMIT 5;

Start boring

If you already run PostgreSQL, pgvector is usually the right first choice: one database, transactions, SQL filters and backups you already understand. Move to a dedicated vector database when you have measured a need.

How approximate nearest-neighbour search works

Exact search compares the query with every vector: fine at a million, slow at a billion. Approximate nearest neighbour (ANN) indexes trade a little accuracy (recall: the fraction of true top-k results found) for enormous speed-ups.

  • HNSW (hierarchical navigable small world graphs): every vector is a node linked to its near neighbours, in layers from sparse to dense. A search starts at the sparse top layer, greedily hops towards the query, and descends. The default in most vector databases. Key knobs: M (links per node: memory versus recall) and ef_search (how many candidates to explore per query: speed versus recall).
  • IVF (inverted file): cluster the vectors with k-means; at query time search only the few clusters nearest the query (nprobe controls how many).
  • Product quantisation (PQ): compress each vector into a few bytes by quantising sub-vectors. Cuts memory by 10 to 50 times at some cost in accuracy; often combined with IVF for billion-scale collections.

Measure it yourself

import numpy as np, time, faiss

rng = np.random.default_rng(0)
n, d = 50_000, 384
# real embeddings have structure: simulate 200 "topics" in a lower-dimensional subspace
centers = rng.normal(size=(200, 48))
Z = centers[rng.integers(0, 200, n)] + 0.6 * rng.normal(size=(n, 48))
X = (Z @ rng.normal(size=(48, d))).astype("float32")
X /= np.linalg.norm(X, axis=1, keepdims=True)
Q = X[rng.choice(n, 200, replace=False)] + 0.05 * rng.normal(size=(200, d)).astype("float32")
Q /= np.linalg.norm(Q, axis=1, keepdims=True)

exact = np.argsort(-(Q @ X.T), axis=1)[:, :10]                 # ground truth top-10

hnsw = faiss.IndexHNSWFlat(d, 16, faiss.METRIC_INNER_PRODUCT)
hnsw.add(X)
for ef in [16, 64, 256]:
    hnsw.hnsw.efSearch = ef
    t = time.perf_counter(); _, I = hnsw.search(Q, 10); dt = time.perf_counter() - t
    recall = np.mean([len(set(I[i]) & set(exact[i])) / 10 for i in range(len(Q))])
    print(f"ef_search={ef:<4} recall@10={recall:.3f}  {dt * 1000 / len(Q):.3f} ms/query")
ef_search=16   recall@10=0.936  0.032 ms/query
ef_search=64   recall@10=0.994  0.062 ms/query
ef_search=256  recall@10=0.999  0.151 ms/query

Exact search on the same machine took about 1.3 ms per query, so HNSW is 20 to 40 times faster while finding over 99% of the true neighbours. The gap widens as collections grow. (Try the same test on unstructured random vectors and recall collapses: ANN works because real data has structure.)

Clustering and visualising embeddings

Embeddings also let you explore collections you have never read. Embed a few thousand support tickets, cluster them with k-means (lesson ), and ask an LLM to name each cluster from a sample of its members. You get an instant map of what users complain about.

from sklearn.cluster import KMeans

ticket_vecs = model.encode(tickets, normalize_embeddings=True)
km = KMeans(n_clusters=12, n_init=10, random_state=0).fit(ticket_vecs)
for c in range(12):
    members = [t for t, lab in zip(tickets, km.labels_) if lab == c][:8]
    # name = llm("Give a 3-5 word label for these support tickets:\n" + "\n".join(members))
    print(c, len([1 for lab in km.labels_ if lab == c]), members[0][:80])

To see the structure, project to 2-D with PCA, or with UMAP (uv add umap-learn), which preserves local neighbourhoods better, and scatter-plot coloured by cluster. Clusters of near-duplicates, mislabelled examples and unexpected topics jump out.

Hands-on: a search engine for your own notes

  1. Collect at least 200 paragraphs of text you know well: your learning log, documentation you use, or public-domain articles. Split into paragraphs.
  2. Embed them with all-MiniLM-L6-v2 and build a FAISS index.
  3. Write 15 test queries, and for each note which paragraph should be found. Measure recall@5 (the fraction of queries whose correct paragraph is in the top 5).
  4. Compare with a second embedding model (for example BAAI/bge-small-en-v1.5, which expects the query prefix "Represent this sentence for searching relevant passages: "). Which wins on your data?
  5. Find a query where keyword search would beat embeddings, and one where embeddings clearly win.
Show a solution sketch 

import faiss, numpy as np
from sentence_transformers import SentenceTransformer

paras = [p.strip() for p in open("notes.txt").read().split("\n\n") if len(p.strip()) > 40]
tests = [("how do I stop overfitting", 17), ("what does the KV cache store", 88)]   # (query, correct index)

def evaluate(model_name, query_prefix=""):
    m = SentenceTransformer(model_name)
    D = m.encode(paras, normalize_embeddings=True).astype("float32")
    index = faiss.IndexFlatIP(D.shape[1]); index.add(D)
    hits = 0
    for q, gold in tests:
        qv = m.encode([query_prefix + q], normalize_embeddings=True).astype("float32")
        _, ids = index.search(qv, 5)
        hits += gold in ids[0]
    return hits / len(tests)

print(evaluate("all-MiniLM-L6-v2"))
print(evaluate("BAAI/bge-small-en-v1.5",
               query_prefix="Represent this sentence for searching relevant passages: "))
Typical findings: both models do well on paraphrased questions; the better one depends on your text, which is the point of measuring. Keyword search wins on exact strings such as error codes, version numbers and names; embeddings win on questions phrased differently from the text ("why is my model memorising the training data" finding a paragraph about overfitting). This small labelled query set is your first retrieval evaluation; you will grow it in lessons and .

Check yourself

How are text embedding models typically trained?

  • To predict the next token
  • Contrastively, so matching pairs (question and answer, paraphrases) end up close and unrelated texts far apart
  • With k-means clustering
  • By hand-labelling each dimension

Contrastive training shapes the space so that distance reflects meaning.

Why normalise embeddings to unit length before indexing?

  • To save memory
  • So cosine similarity becomes a plain dot product, making search a fast matrix multiplication
  • Because FAISS rejects non-normalised vectors
  • To improve the embedding model's accuracy

For unit vectors, cosine similarity and inner product are identical.

A user searches for "error E-4071" and gets documents about other error codes. What is the best fix?

  • Use a bigger embedding model
  • Add keyword search (such as BM25) and combine it with embeddings in a hybrid search
  • Increase the number of dimensions
  • Lower the temperature

Embeddings blur exact identifiers. Keyword search handles them precisely.

You switch to a new embedding model. What must you do with your existing vectors?

  • Nothing
  • Normalise them again
  • Re-embed every document, because different models produce incompatible vector spaces
  • Average old and new vectors

Vectors from different models are not comparable.

In HNSW, what does increasing ef_search do?

  • Explores more candidates per query, raising recall at the cost of speed
  • Builds the index faster
  • Reduces memory use
  • Changes the similarity metric

It is the main query-time knob for trading speed against recall.

Key takeaways

  • Text embeddings map meaning to geometry; similar texts have high cosine similarity. They enable search by meaning.
  • Choose embedding models by testing on your own data; mind input length, query prefixes and never mix models.
  • Semantic search is a normalised dot product plus a sort. FAISS makes it fast; vector databases add metadata, filtering and persistence (pgvector is a fine default).
  • ANN indexes such as HNSW trade a little recall for large speed-ups; measure recall against exact search.
  • Embeddings are weak on exact identifiers, which is why production search is usually hybrid.
