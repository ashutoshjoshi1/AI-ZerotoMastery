What an AI engineer does

An AI engineer builds products and systems whose behaviour depends on a learned model. Most of the time today that model is a large language model (LLM) reached through an API or served from your own hardware, but the job also covers classical machine learning, embeddings, retrieval systems, evaluation pipelines and the plumbing that keeps all of it fast, cheap and safe.

It helps to see how the role differs from its neighbours:

Role Main question Typical output
Research scientist Can we make a better model? Papers, new architectures, training recipes
ML engineer Can we train and serve this model reliably? Training pipelines, feature stores, model servers
Data scientist What does the data say, and what should we do? Analyses, experiments, forecasts, dashboards
AI engineer Can we build a useful, dependable product on top of models? Applications, RAG systems, agents, eval suites, fine-tuned models

The boundaries are blurry and the best AI engineers borrow from all three neighbours. You need enough maths and deep learning to understand why a model behaves the way it does, enough software engineering to ship it, and enough scientific discipline to measure whether it actually works. This course is built around that combination.

The work, concretely

A week in the life of an AI engineer might include:

  • Designing a prompt and a retrieval pipeline so a support assistant answers from the company's own manuals, with citations.
  • Writing an evaluation set of 200 real questions, then measuring how a model change moves accuracy, latency and cost.
  • Giving an agent tools (a database query, a ticketing API) and making sure it cannot do anything destructive.
  • Fine-tuning a small open model so it can run on cheap hardware for a narrow task.
  • Debugging why answers got worse after a "harmless" change to the chunking code.

Notice how much of this is engineering and measurement rather than model invention. That is the job.

How the field fits together

The vocabulary is nested, and people use the words loosely, so it is worth pinning them down once.

Artificial intelligence is the broadest term. A chess engine that searches moves with hand-written rules is AI, but it does not learn.

Machine learning (ML) means the behaviour comes from data. You show a spam filter thousands of labelled emails and it works out the rules itself. Classical ML (linear models, decision trees, gradient boosting) still powers a huge share of real systems, especially on tabular data.

Deep learning is ML with neural networks that have many layers. It took over around 2012 because, given enough data and GPU compute, deep networks learn their own features from raw pixels, audio or text.

Large language models are deep networks, almost always transformers, trained on trillions of tokens of text to predict the next token. That simple objective, at enormous scale, produces models that can write, summarise, translate, reason through problems and use tools.

A short history, so the names make sense

Year Milestone Why it matters
1950 Turing's "Computing Machinery and Intelligence" Frames the question "can machines think?"
1958 Rosenblatt's perceptron The first trainable artificial neuron
1986 Backpropagation popularised (Rumelhart, Hinton, Williams) A practical way to train multi-layer networks
1997 LSTM (Hochreiter and Schmidhuber) Neural networks that can remember across long sequences
2012 AlexNet wins ImageNet GPUs plus deep networks beat hand-engineered vision features
2013 word2vec Words as vectors whose geometry captures meaning
2017 "Attention Is All You Need" The transformer: the architecture behind every modern LLM
2018 BERT and GPT Pretrain once on lots of text, then adapt to many tasks
2020 GPT-3 and scaling laws Bigger models plus more data give predictable gains; prompting replaces task-specific training
2022 Instruction-tuned chat models reach the public RLHF turns raw predictors into helpful assistants
2023 onward Open-weight models, tool use, agents, multimodality Models you can run yourself; models that act, see and hear
2024 onward Reasoning models Spending more compute at inference time to think before answering

You will meet most of these ideas again, in order, as you go through the course.

How to study this, an hour at a time

Learning a field this wide is a long game. Three habits matter more than any particular resource.

Retrieval beats rereading. At the end of each session, close the page and write a short summary from memory in a learning log. The effort of recall is what makes it stick. The quizzes at the end of each lesson exist for the same reason.

Build, then read. When an idea feels abstract, run the code, change a number, and watch what happens. Every lesson has at least one hands-on exercise with a hidden solution. Try the exercise for real before you open the solution, even if you only get halfway.

Spaced review. Once a week, skim the key takeaways of the last two or three lessons. Five minutes of review saves hours of relearning later.

Your learning log

Create a repository called ai-engineering-log with one Markdown file per lesson. Each entry gets three things: what you learned in your own words, the code you wrote, and one question you still have. By the end of the course this repository is a portfolio, a reference manual and proof of work, all in one.

Set up your workbench

You need Python, an isolated environment per project, a notebook for exploration, an editor for real code, Git, and a safe way to store API keys.

Python and environments

Use Python 3.11 or newer. The easiest modern way to manage Python versions and packages is uv, a fast replacement for pip and venv. The classic venv plus pip route works just as well; both are shown.

# install uv (macOS / Linux); see the uv docs for Windows
curl -LsSf https://astral.sh/uv/install.sh | sh

mkdir ai-engineering-log && cd ai-engineering-log
uv init --python 3.12          # creates pyproject.toml and a .venv on first sync
uv add numpy pandas matplotlib scikit-learn jupyterlab python-dotenv
uv run jupyter lab             # runs inside the project's environment
mkdir ai-engineering-log && cd ai-engineering-log
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install --upgrade pip
pip install numpy pandas matplotlib scikit-learn jupyterlab python-dotenv
jupyter lab

Why bother with environments? Every project pins its own library versions. Without isolation, upgrading a package for one project silently breaks another. AI libraries move fast and break compatibility often, so this matters more here than almost anywhere else.

Notebooks versus scripts

Jupyter notebooks are excellent for exploring data and trying ideas cell by cell. They are poor for anything you want to rerun, test or deploy, because hidden state builds up as you run cells out of order. A good rule: explore in a notebook, then move anything you want to keep into a .py file with functions you can import and test.

For an editor, VS Code with the Python and Jupyter extensions is the common choice. It opens notebooks too, so you can stay in one tool.

GPUs without buying one

You will not need a GPU until part IV. When you do, Google Colab gives you a free NVIDIA GPU in the browser (Runtime, then Change runtime type). Kaggle notebooks offer similar free quotas. For heavier work later, cloud GPU providers rent by the hour.

Git

Initialise Git now and commit after every session. Small, frequent commits make your log readable and give you an undo button.

git init
printf ".venv/\n.env\n__pycache__/\n.ipynb_checkpoints/\n*.pt\ndata/raw/\n" > .gitignore
git add . && git commit -m "Lesson 00: workbench set up"

API keys, safely

In part VI you will call hosted models. Their API keys are secrets that cost you money if leaked. Never paste a key into code or a notebook. Put it in a .env file that Git ignores, and load it at runtime.

ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-...
from dotenv import load_dotenv
import os

load_dotenv()                      # reads .env into environment variables
key = os.environ.get("ANTHROPIC_API_KEY")
print("key loaded" if key else "no key found")   # never print the key itself

If a key leaks

Revoke it in the provider's console immediately, then create a new one. Bots scan public GitHub repositories for keys within minutes of a push. Rewriting Git history afterwards is not enough, because the key has already been copied.

A project layout that scales

ai-engineering-log/
├── pyproject.toml        # dependencies (uv) or requirements.txt (pip)
├── .env                  # secrets, git-ignored
├── notes/                # one markdown file per lesson
├── notebooks/            # exploration
├── src/                  # reusable code you import from notebooks and scripts
├── data/                 # small datasets; large ones stay out of git
└── tests/                # yes, even for AI projects

Hands-on: prove your workbench works

Create src/check_env.py that prints your Python version and the versions of NumPy, pandas, scikit-learn and Matplotlib, then reports whether an API key is present (without printing it). Run it with uv run python src/check_env.py or python src/check_env.py. Commit the file and write your first log entry.

Show a solution 
import os
import sys
from importlib.metadata import version, PackageNotFoundError

from dotenv import load_dotenv

load_dotenv()
print(f"Python {sys.version.split()[0]}")
for pkg in ["numpy", "pandas", "scikit-learn", "matplotlib", "jupyterlab"]:
    try:
        print(f"{pkg:<14}{version(pkg)}")
    except PackageNotFoundError:
        print(f"{pkg:<14}MISSING: install it with uv add {pkg}")

for var in ["ANTHROPIC_API_KEY", "OPENAI_API_KEY"]:
    status = "present" if os.environ.get(var) else "not set (fine until part VI)"
    print(f"{var:<20}{status}")

importlib.metadata.version reads installed package metadata, which works even for packages whose import name differs from their install name (scikit-learn installs as sklearn).

Key takeaways

  • An AI engineer builds dependable products on top of learned models. Most of the work is engineering and measurement, not inventing models.
  • AI contains machine learning, which contains deep learning, which contains LLMs.
  • Use one isolated environment per project, keep secrets in a git-ignored .env, and commit after every session.
  • Retrieval practice and building things beat rereading. Keep a learning log from day one.
