What makes something an agent

A chatbot produces text. An agent uses a model to decide on actions, takes them through tools, observes the results, and keeps going until the task is done. The model is no longer just answering; it is controlling a loop.

A useful working definition: an agent is a model using tools in a loop, deciding for itself what to do next. A useful working caution: autonomy costs latency, money and predictability, so use the least autonomy that solves the problem.

Tool use: the mechanism

You describe tools to the model with a name, a description and a JSON schema for the inputs. The model cannot run anything itself. When it wants a tool, it replies with a structured tool call (name plus arguments) and stops. Your code runs the tool and sends back the result, and the model continues, possibly calling more tools, until it gives a final answer.

Define tools

import json, math, ast, operator as op
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"

# --- the actual tool implementations -------------------------------------------
FLEET = {   # stand-in for a real database or API
    "P-117": {"site": "coastal", "status": "offline", "last_data": "2026-10-18T02:00Z", "firmware": "2.3"},
    "P-204": {"site": "urban", "status": "ok", "last_data": "2026-10-19T09:55Z", "firmware": "2.4"},
}

def get_instrument_status(instrument_id: str) -> dict:
    if instrument_id not in FLEET:
        return {"error": f"unknown instrument '{instrument_id}'. Known ids: {sorted(FLEET)}"}
    return FLEET[instrument_id]

OPS = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv,
       ast.Pow: op.pow, ast.Mod: op.mod, ast.USub: op.neg, ast.UAdd: op.pos}
FUNCS = {"sqrt": math.sqrt, "log": math.log, "exp": math.exp, "abs": abs, "round": round}

def calculate(expression: str) -> float:
    """Evaluate arithmetic safely: never call eval() on model output."""
    def ev(node):
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            left, right = ev(node.left), ev(node.right)
            if isinstance(node.op, ast.Pow) and abs(right) > 100:
                raise ValueError("exponent too large")
            return OPS[type(node.op)](left, right)
        if isinstance(node, ast.UnaryOp) and type(node.op) in OPS:
            return OPS[type(node.op)](ev(node.operand))
        if isinstance(node, ast.Call) and isinstance(node.func, ast.Name) and node.func.id in FUNCS:
            return FUNCS[node.func.id](*[ev(a) for a in node.args])
        if isinstance(node, ast.Name) and node.id in ("pi", "e"):
            return getattr(math, node.id)
        raise ValueError("unsupported expression")
    return ev(ast.parse(expression, mode="eval").body)

# --- what the model sees ---------------------------------------------------------
TOOLS = [
    {
        "name": "get_instrument_status",
        "description": ("Look up the current status of one field instrument by its id (format 'P-123'). "
                        "Returns site, status (ok/degraded/offline), time of last data (UTC) and firmware version."),
        "input_schema": {
            "type": "object",
            "properties": {"instrument_id": {"type": "string", "description": "Instrument id, e.g. 'P-117'"}},
            "required": ["instrument_id"],
        },
    },
    {
        "name": "calculate",
        "description": "Evaluate an arithmetic expression exactly. Use for any calculation instead of mental arithmetic.",
        "input_schema": {
            "type": "object",
            "properties": {"expression": {"type": "string", "description": "e.g. '(17 - 2.5) * 3600'"}},
            "required": ["expression"],
        },
    },
]
TOOL_FUNCS = {"get_instrument_status": get_instrument_status, "calculate": calculate}

The loop

def run_agent(task: str, max_steps: int = 10, verbose: bool = True) -> str:
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        resp = client.messages.create(
            model=MODEL, max_tokens=1500, tools=TOOLS, messages=messages,
            system="You are an operations assistant for a fleet of field instruments. "
                   "Use tools to check facts rather than guessing. Be concise.",
        )
        messages.append({"role": "assistant", "content": resp.content})   # keep the tool calls in history

        if resp.stop_reason != "tool_use":                                 # the model has finished
            return "".join(b.text for b in resp.content if b.type == "text")

        results = []
        for block in resp.content:                                         # may contain several calls
            if block.type != "tool_use":
                continue
            if verbose:
                print(f"  -> {block.name}({block.input})")
            try:
                output = TOOL_FUNCS[block.name](**block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": json.dumps(output)})
            except Exception as e:                                         # report errors to the model
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"Error: {e}", "is_error": True})
        messages.append({"role": "user", "content": results})              # results go back as a user turn
    return "Stopped: step limit reached before the task was finished."

print(run_agent("Is P-117 healthy? If not, how many hours has it been without data as of 2026-10-19T10:00Z?"))
#   -> get_instrument_status({'instrument_id': 'P-117'})
#   -> calculate({'expression': '24 + 8'})
# P-117 is offline. Its last data arrived at 02:00 UTC on 18 October, so it has been
# without data for 32 hours as of 10:00 UTC today.

That is a complete agent. Every agent framework is this loop plus conveniences. Note three details that trip people up: the assistant's tool-call blocks must be kept in the history, each result must reference its tool_use_id, and results are sent in a user turn.

Designing tools models use well

Tools are a user interface whose user is a model. Most agent failures are tool design failures.

  • Write descriptions like documentation for a new colleague: what it does, when to use it, what it returns, the format of each argument, with an example. The description is the only thing the model knows about your tool.
  • Few, well-scoped tools beat many overlapping ones. If two tools could plausibly answer the same request, the model will sometimes pick the wrong one.
  • Return what the model needs, compactly. Not 5,000 rows of raw JSON; filter, paginate and summarise. Every returned token costs context.
  • Make errors instructive. "unknown instrument 'P117'. Known ids look like 'P-117'" lets the model fix its own mistake; a stack trace does not.
  • Make tools safe by construction. Validate inputs, use read-only credentials where possible, and never pass model output to eval, a shell or raw SQL. The calculator above parses an expression tree instead of calling eval.
  • Separate reading from acting. Tools that change the world (send email, restart an instrument, delete data) deserve confirmation steps, narrow permissions and logs.

Models can request several tool calls in one turn (for example, checking five instruments at once). The loop above handles this; run independent calls concurrently when they are slow.

Workflows, agents and when to use which

Many "agent" problems are better solved with workflows: predefined code paths that call models at fixed points. They are cheaper, faster and easier to test. Anthropic's guide "Building effective agents" names a useful set of patterns:

Pattern How it works Example
Prompt chaining Fixed sequence of calls, each using the previous output Extract facts, then draft, then check
Routing A classifier sends input to a specialised prompt or model Hardware questions to one flow, billing to another
Parallelisation Run independent calls at once, then combine (or vote) Review a document for five risks in parallel
Orchestrator-workers A model breaks a task into subtasks and delegates them Research a topic across many sources
Evaluator-optimiser One call drafts, another critiques, loop until good enough Translate, critique, revise
Autonomous agent Model chooses tools and steps freely in a loop Open-ended debugging or research

Rule of thumb: if you can draw the flowchart in advance, write a workflow. Use an autonomous agent when the number and order of steps genuinely cannot be known beforehand, and when the value of the task justifies the cost and unpredictability.

Planning and ReAct

The ReAct pattern (reason, act, observe) interleaves short reasoning with tool calls: think about what to do, call a tool, read the result, think again. Modern models do this naturally inside the tool loop, especially with reasoning enabled. For long tasks, asking the agent to write an explicit plan first, then revise it as results come in, helps it stay on track.

Memory

  • Short-term memory is the conversation and tool history in the context window. It fills up: summarise or drop old tool results in long runs.
  • Long-term memory is anything stored outside the context and retrieved when relevant: a database of facts about the user, notes files the agent writes and later reads, a vector store of past interactions. It is RAG (lesson ) applied to the agent's own history.
  • Scratchpads: letting an agent write intermediate results to files keeps its context small and makes its work inspectable.

Multi-agent systems

Splitting work across several agents (an orchestrator plus specialised sub-agents with their own context windows) can help on broad tasks such as deep research, because each sub-agent explores in parallel with a clean context. It also multiplies token use and adds coordination failure modes. Start with one agent and add more only when a single context demonstrably becomes the bottleneck.

The Model Context Protocol

Every application used to wire up its own tools. The Model Context Protocol (MCP) is an open standard, introduced by Anthropic in 2024 and since adopted widely, for connecting AI applications to tools and data. Write an MCP server once, and any MCP-capable client (Claude's apps, IDEs, agent frameworks, your own code) can use it. Think of it as USB for AI tools.

An MCP server can expose:

  • Tools: functions the model can call (like the ones above).
  • Resources: data the application can read into context (files, records).
  • Prompts: reusable prompt templates.

Build a server

uv add "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("instrument-fleet")

FLEET = {
    "P-117": {"site": "coastal", "status": "offline", "last_data": "2026-10-18T02:00Z", "firmware": "2.3"},
    "P-204": {"site": "urban", "status": "ok", "last_data": "2026-10-19T09:55Z", "firmware": "2.4"},
}

@mcp.tool()
def get_instrument_status(instrument_id: str) -> dict:
    """Current status of one instrument by id (format 'P-123'): site, status, last data time (UTC), firmware."""
    return FLEET.get(instrument_id, {"error": f"unknown id; known ids: {sorted(FLEET)}"})

@mcp.tool()
def list_instruments(status: str | None = None) -> list[str]:
    """List instrument ids, optionally only those with a given status ('ok', 'degraded', 'offline')."""
    return [i for i, v in FLEET.items() if status is None or v["status"] == status]

@mcp.resource("fleet://firmware-notes")
def firmware_notes() -> str:
    """Release notes for instrument firmware versions."""
    return "2.4: fixes overnight logging stall on cellular modems. 2.3: adds GPS time sync."

if __name__ == "__main__":
    mcp.run()          # speaks MCP over stdin/stdout by default

The decorators turn type hints and docstrings into the tool schemas and descriptions, so write them carefully: they are what the model reads. Test the server interactively with the MCP Inspector (uv run mcp dev fleet_server.py), then register it with a client. For Claude Desktop, add it to the configuration file:

{
  "mcpServers": {
    "fleet": {
      "command": "uv",
      "args": ["run", "--directory", "/path/to/project", "fleet_server.py"]
    }
  }
}

After a restart, you can ask in plain language which instruments are offline and whether a firmware update might help, and the client will call your tools and read your resource. Servers can also run remotely over HTTP for shared use, which brings authentication and permissions into play.

MCP servers are code you run with your permissions

Only install servers you trust, give them the narrowest credentials that work, and remember that tool results are untrusted input to the model: a document or web page fetched by one tool can contain instructions trying to hijack the agent (prompt injection, lesson ).

Guardrails, budgets and evaluation

An agent that loops forever, burns your budget or deletes the wrong thing is worse than no agent. Build in:

  • Hard limits: maximum steps, maximum tokens or cost per task, wall-clock timeouts.
  • Least privilege: read-only by default; separate credentials per tool; scope to the user's own data.
  • Human approval for consequential or irreversible actions: show the exact action and wait for a yes.
  • Validation of tool arguments before execution, and of outputs before they reach users.
  • Idempotency and dry-runs for actions that might be retried.
  • Full tracing: log every model call, tool call, argument, result, token count and latency. You cannot debug an agent from its final answer alone (lesson covers tracing tools).

Evaluating agents means more than checking the final answer:

  • Task success rate on a set of realistic tasks with checkable outcomes (the database ended up in the right state; the report contains the right numbers).
  • Trajectory quality: did it use sensible tools, avoid redundant calls, ask for confirmation where needed?
  • Cost and latency per task, and their spread: agents have long tails.
  • Safety cases: tasks that should be refused or escalated, and injected instructions that should be ignored.

Hands-on: a research agent over your documents

  2. Add a tool read_chunk(chunk_id: str) that returns a chunk with its neighbours for more context, and the calculate tool.
  3. Give the agent a system prompt that requires citations by chunk id and allows "not found".
  4. Add limits: 12 steps, and a running token count that stops the agent above 60,000 input tokens.
  5. Write 8 questions that need several searches (comparisons, multi-step lookups) and compare the agent's answers, cost and latency with plain MiniRAG.answer.
Show a solution sketch and typical findings 

rag = MiniRAG(); rag.index(documents)
by_id = {c["id"]: i for i, c in enumerate(rag.chunks)}

def search_docs(query: str, k: int = 5) -> list[dict]:
    return [{"id": c["id"], "title": c["title"], "text": c["text"][:1200]}
            for c in rag.retrieve(query, k_final=min(k, 8))]

def read_chunk(chunk_id: str) -> dict:
    i = by_id.get(chunk_id)
    if i is None:
        return {"error": "unknown chunk id; use ids returned by search_docs"}
    window = rag.chunks[max(0, i - 1): i + 2]
    return {"id": chunk_id, "text": "\n\n".join(c["text"] for c in window)}

TOOL_FUNCS.update(search_docs=search_docs, read_chunk=read_chunk)
TOOLS += [
    {"name": "search_docs",
     "description": "Search the document collection. Returns the most relevant chunks with ids. "
                    "Search several times with different wording for multi-part questions.",
     "input_schema": {"type": "object",
                      "properties": {"query": {"type": "string"}, "k": {"type": "integer", "default": 5}},
                      "required": ["query"]}},
    {"name": "read_chunk",
     "description": "Read a chunk together with its neighbouring chunks, for more context.",
     "input_schema": {"type": "object", "properties": {"chunk_id": {"type": "string"}},
                      "required": ["chunk_id"]}},
]
# In run_agent: accumulate resp.usage.input_tokens and stop when the total exceeds 60_000.
Typical findings: on simple lookups the agent matches plain RAG but costs several times more and takes longer. On comparison and multi-hop questions it often wins clearly, because it searches for each part separately and follows up on what it finds. Failures to look for: repeating near-identical searches, citing chunks it never read, and stopping too early. Each suggests a fix to the tool descriptions or system prompt. The cost and latency gap is why production systems often route: plain RAG first, the agent only for questions that need it.

Check yourself

Who actually executes a tool when a model "calls" it?

  • The model, inside the provider's servers
  • Your application code, which then sends the result back to the model
  • The user
  • The tool description

The model only proposes a structured call. Your code decides whether and how to run it.

In the Anthropic Messages API, how are tool results returned to the model?

  • As a new system prompt
  • As tool_result blocks in a user message, each referencing its tool_use_id
  • As an assistant message
  • By calling the tool endpoint

The assistant's tool_use blocks stay in history, followed by a user turn containing the matching results.

You can draw the full flowchart of a task in advance. What should you build?

  • A workflow with fixed steps that call the model where needed
  • A multi-agent system
  • An autonomous agent with all tools available
  • Nothing; models cannot handle fixed steps

Workflows are cheaper, faster and easier to test. Save autonomy for genuinely open-ended tasks.

What is the main benefit of the Model Context Protocol?

  • It makes models smarter
  • Tools and data exposed once as an MCP server can be used by any MCP-capable client
  • It encrypts all model traffic
  • It replaces the need for tool descriptions

It standardises the connection between AI applications and tools, like a common port.

Which is the strongest safeguard for an agent tool that can delete data?

  • A longer system prompt asking the model to be careful
  • A higher temperature
  • Least-privilege credentials plus explicit human approval of the exact action, with logging
  • Running more agents to double-check

Do not rely on the model's judgement alone for irreversible actions.

Key takeaways

  • An agent is a model using tools in a loop. The model proposes calls; your code executes them and returns results.
  • Tool design decides agent quality: clear descriptions, few well-scoped tools, compact results, instructive errors, safe implementations.
  • Prefer workflows (chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser) when steps are predictable; use autonomous agents when they are not.
  • MCP standardises tools and data access across applications; treat servers and their outputs as untrusted.
  • Guard agents with step and cost limits, least privilege, human approval for consequential actions and full tracing. Evaluate success, trajectory, cost and safety.
