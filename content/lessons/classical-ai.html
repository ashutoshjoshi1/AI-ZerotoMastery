The other half of AI

Everything in this course so far has been learned from data: a model sees examples, a loss measures its mistakes, and gradient descent nudges millions of numbers. The field did not start there. For its first thirty years, AI mostly meant programs that search through possibilities and reason with knowledge written down by people, with no training data at all.

That half never went away. The route planner on your phone, the engine that beats every human at chess, the solver that builds an airline's crew rosters and the resolver that picks compatible versions of your Python packages are all classical AI. It also sits at the heart of the most impressive learned systems: AlphaZero is a neural network wrapped in a tree search, and a reliable LLM agent is a learned model wrapped in planning, search and verification. This lesson builds the core algorithms, each in a few dozen lines of Python, and shows where they still earn their keep.

A short history of AI

Each era of AI was driven by one big idea, promised too much, and left behind something that still works. Knowing the pattern helps you judge today's claims.

You have spent nineteen lessons on learning. This one is about search, and about how the two combine.

Problems as search

Mazes, delivery routes, puzzles and plans can all be written in the same five parts. Writing them down is the most important step, because once a problem has this shape any search algorithm can solve it.

  • A state: a snapshot of everything that matters, such as a cell in a maze, a town on a map or a board position.
  • The initial state you start from.
  • The actions available in each state, and the state each one leads to (the transition model).
  • A goal test that says whether a state is a solution.
  • A path cost: the sum of the step costs, such as kilometres driven or moves made.

In code, actions and transitions become one successor function that lists the next states and the cost of reaching each. Here is a maze in that form:

MAZE = """\
S.......#.
.######.#.
......#...
.####.#.#.
.#G...#.#.
.######.#.
..........
"""

def find(grid, ch):
    return next((r, c) for r, row in enumerate(grid) for c, x in enumerate(row) if x == ch)

def neighbours(state, grid):
    """Successor function: yield (next_state, step_cost) for every legal move."""
    r, c = state
    for dr, dc in [(-1, 0), (1, 0), (0, -1), (0, 1)]:      # up, down, left, right
        nr, nc = r + dr, c + dc
        if 0 <= nr < len(grid) and 0 <= nc < len(grid[0]) and grid[nr][nc] != "#":
            yield (nr, nc), 1

def show(grid, path):
    rows = [list(row) for row in grid]
    for r, c in path[1:-1]:
        rows[r][c] = "*"
    print("\n".join("".join(row) for row in rows))

grid = MAZE.splitlines()
start, goal = find(grid, "S"), find(grid, "G")
print("start", start, "goal", goal)
print("moves from start:", list(neighbours(start, grid)))

moves from start: [((1, 0), 1), ((0, 1), 1)]

A search algorithm grows a tree of paths from the start. The frontier holds states that have been generated but not yet expanded, where expanding a state means generating its successors. Every algorithm in this lesson runs that same loop. They differ in one thing only: which frontier state to expand next.

Breadth-first and depth-first search

Breadth-first search (BFS) keeps the frontier in a first-in, first-out queue. It expands every state one step from the start, then every state two steps away, and so on, so the first path it finds to the goal has the fewest steps. Depth-first search (DFS) uses a last-in, first-out stack: it dives down one path as far as it can and backs up only at a dead end. In code the difference is a single line.

from collections import deque

def reconstruct(parent, s):
    path = []
    while s is not None:
        path.append(s)
        s = parent[s]
    return path[::-1]

def uninformed_search(start, is_goal, successors, kind="bfs"):
    frontier = deque([start])
    parent = {start: None}                # also the set of states already reached
    expanded = 0
    while frontier:
        s = frontier.popleft() if kind == "bfs" else frontier.pop()   # FIFO or LIFO
        expanded += 1
        if is_goal(s):
            return reconstruct(parent, s), expanded
        for s2, _ in successors(s):
            if s2 not in parent:
                parent[s2] = s
                frontier.append(s2)
    return None, expanded

moves = lambda s: neighbours(s, grid)
for kind in ["bfs", "dfs"]:
    path, n = uninformed_search(start, lambda s: s == goal, moves, kind)
    print(f"{kind}: {len(path) - 1} steps, {n} states expanded")
    show(grid, path)

Both reach the goal, but the DFS route is three times longer: it charged off along the top corridor and never looked back. The parent dictionary records every state already reached, so neither version expands a state twice or walks in circles.

BFS pays for its guarantee in memory. With \(b\) choices per state and the goal \(d\) steps away, it can hold on the order of \(b^d\) states: with \(b = 10\) and \(d = 10\), ten billion. DFS without the reached set only needs the current path and its siblings, which is why iterative deepening (DFS with a depth limit of 0, then 1, then 2, and so on) is the standard way to get BFS's shortest paths with DFS's small memory.

Uniform-cost search (Dijkstra's algorithm)

BFS counts steps, but real steps have different costs: roads have lengths, actions take time. Uniform-cost search (UCS) always expands the frontier state with the lowest path cost so far, written \(g(n)\), using a priority queue. It is Dijkstra's 1959 shortest-path algorithm, stopped as soon as the goal comes off the queue. Here it is on a map of field sites that a technician drives between.

import heapq, math

# Field sites: (x, y) position in km, and the roads between them with their length in km
SITES = {"depot": (0, 0), "harbour": (12, 4), "mill": (5, 9), "ridge": (14, 14),
         "lake": (22, 8), "airfield": (8, 18), "observatory": (24, 19)}
ROADS = [("depot", "harbour", 14), ("depot", "mill", 11), ("depot", "ridge", 30),
         ("harbour", "lake", 12), ("harbour", "ridge", 11), ("mill", "ridge", 11),
         ("mill", "airfield", 10), ("ridge", "observatory", 12),
         ("lake", "observatory", 12), ("airfield", "observatory", 17)]
graph = {s: [] for s in SITES}
for a, b, km in ROADS:
    graph[a].append((b, km))
    graph[b].append((a, km))

def uniform_cost_search(start, is_goal, successors):
    frontier = [(0, start)]               # a priority queue ordered by path cost g
    parent, g = {start: None}, {start: 0}
    expanded = 0
    while frontier:
        cost, s = heapq.heappop(frontier)
        if cost > g[s]:
            continue                      # stale entry: a cheaper route was found later
        expanded += 1
        if is_goal(s):                    # test when expanded, not when generated
            return reconstruct(parent, s), cost, expanded
        for s2, step in successors(s):
            new = cost + step
            if s2 not in g or new < g[s2]:
                g[s2], parent[s2] = new, s
                heapq.heappush(frontier, (new, s2))
    return None, math.inf, expanded

roads = lambda s: graph[s]
at_obs = lambda s: s == "observatory"
path, _ = uninformed_search("depot", at_obs, roads, "bfs")
km = sum(dict(graph[a])[b] for a, b in zip(path, path[1:]))
print("BFS:", " -> ".join(path), f"({km} km)")
path, km, n = uniform_cost_search("depot", at_obs, roads)
print("UCS:", " -> ".join(path), f"({km} km, {n} expanded)")
BFS: depot -> ridge -> observatory (42 km)
UCS: depot -> mill -> ridge -> observatory (34 km, 7 expanded)

BFS finds the route with the fewest roads, but one of them is the 30 km mountain road. UCS finds the shortest drive. Python's heapq cannot lower the priority of an item already in the queue, so the code pushes a fresh entry whenever it finds a cheaper route and skips stale entries as they come out.

Test for the goal when you expand, not when you generate

The first time UCS sees the goal, it may be at the end of an expensive route while a cheaper one is still waiting in the queue. Only when the goal is popped as the cheapest item on the frontier is its cost guaranteed to be the lowest. The same holds for A* below. Getting this wrong is the most common search bug, and it fails silently: you still get a path, just not the best one.

def depth_limited(path, is_goal, successors, limit):
    if is_goal(path[-1]):
        return path
    if limit == 0:
        return None
    for s2, _ in successors(path[-1]):
        if s2 not in path:                       # never revisit a state on this path
            found = depth_limited(path + [s2], is_goal, successors, limit - 1)
            if found:
                return found
    return None

def iterative_deepening(start, is_goal, successors, max_depth=100):
    for limit in range(max_depth + 1):
        found = depth_limited([start], is_goal, successors, limit)
        if found:
            return found

Informed search

UCS spreads out evenly in every direction, like a ripple in a pond, because it knows nothing about where the goal is. Usually you do know something: the goal is to the east, or 20 km away as the crow flies. A heuristic \(h(n)\) turns that knowledge into a number, an estimate of the cost from state \(n\) to the goal.

Admissible and consistent heuristics

A heuristic is admissible if it never overestimates: \(h(n) \le h^*(n)\), where \(h^*(n)\) is the true cheapest cost from \(n\) to the goal. It is consistent if it never drops by more than the cost of a step: \(h(n) \le c(n, n') + h(n')\) for every successor \(n'\). Every consistent heuristic is admissible, and most admissible heuristics you will design are consistent too.

The reliable way to invent one is to relax the problem: solve an easier version exactly and use its cost. Delete the maze walls and the cost of the relaxed problem is the Manhattan distance \(|r_1 - r_2| + |c_1 - c_2|\). Ignore the road network and you get the straight-line distance. Removing rules can only make a problem easier, so a relaxed cost never overestimates the real one.

A*, greedy and weighted A*

A* (Hart, Nilsson and Raphael, 1968) expands the frontier state with the lowest

\[ f(n) = g(n) + h(n), \]

the cost so far plus the estimated cost to go: its best guess at the total cost of a solution through \(n\). With an admissible heuristic, the path it returns is optimal. Two variants change the weights. Greedy best-first search uses \(f = h\) alone, rushing towards the goal and ignoring what it has spent. Weighted A* uses \(f = g + w\,h\) with \(w > 1\), trading optimality for speed, with a guarantee that the path costs at most \(w\) times the optimum. One function covers all of them, and UCS too:

def best_first(start, is_goal, successors, h=lambda s: 0, wg=1, wh=1):
    """Expand the node with the lowest f = wg*g + wh*h.
    wh=0 is uniform-cost search, wg=wh=1 is A*, wg=0 is greedy best-first."""
    frontier = [(wh * h(start), 0, start)]
    parent, g = {start: None}, {start: 0}
    expanded = 0
    while frontier:
        _, cost, s = heapq.heappop(frontier)
        if cost > g[s]:
            continue
        expanded += 1
        if is_goal(s):
            return reconstruct(parent, s), cost, expanded
        for s2, step in successors(s):
            new = cost + step
            if s2 not in g or new < g[s2]:
                g[s2], parent[s2] = new, s
                heapq.heappush(frontier, (wg * new + wh * h(s2), new, s2))
    return None, math.inf, expanded

Common heuristic mistakes

  • Using Manhattan distance when diagonal moves cost 1. A diagonal step reduces the Manhattan distance by 2, so it overestimates and A* can return a longer path. Use the larger of the two coordinate differences instead.
  • Mixing units. If costs are travel times, divide the distance by the fastest possible speed, or the estimate can overestimate.
  • A heuristic so expensive to compute that it costs more time than the expansions it saves.

Constraint satisfaction

Some problems care about the final arrangement, not the path to it. In a timetable, a rota or a Sudoku, the order in which you fill things in does not matter, as long as the result breaks no rules. These are constraint satisfaction problems (CSPs): a set of variables, a domain of possible values for each, and constraints on which combinations are allowed.

The basic algorithm is backtracking: assign one variable at a time, check the constraints straight away, and undo the most recent choice when something breaks. Two additions make it practical. Forward checking: after each assignment, delete the values that are now impossible from the domains of neighbouring variables, and back up as soon as any domain is empty, instead of finding the dead end several levels deeper. Minimum remaining values (MRV): always assign next the variable with the fewest values left, so the hardest decisions come first and failures come early.

Here is a week of maintenance visits. Each technician does one job a day; calibration must come after the new belt and the firmware update before the optics clean; one site opens only on Wednesday; and the battery swap shares a van with the inspection, so they happen on the same day.

def forward_check(var, a, assignment, domains, cons):
    """Remove values that clash with var=a from unassigned neighbours' domains."""
    pruned = dict(domains)
    for y, ok in cons[var]:
        if y not in assignment:
            pruned[y] = [b for b in domains[y] if ok(a, b)]
            if not pruned[y]:
                return None               # a neighbour has no value left: dead end
    return pruned

def backtrack(domains, cons, assignment=None, fc=True, stats=None):
    assignment = {} if assignment is None else assignment
    if len(assignment) == len(domains):
        return dict(assignment)
    # Most constrained variable first: the one with the fewest values left (MRV)
    var = min((v for v in domains if v not in assignment), key=lambda v: len(domains[v]))
    for a in domains[var]:
        if all(ok(a, assignment[y]) for y, ok in cons[var] if y in assignment):
            stats["assignments"] += 1
            assignment[var] = a
            pruned = forward_check(var, a, assignment, domains, cons) if fc else domains
            if pruned is not None:
                result = backtrack(pruned, cons, assignment, fc, stats)
                if result:
                    return result
            del assignment[var]           # undo, then try the next value
    return None

JOBS = {"belt P-117": "Ana", "calibrate P-117": "Ana", "inspect P-310": "Ana",
        "firmware P-204": "Ben", "optics P-204": "Ben", "battery P-310": "Ben"}

Six assignments for six variables: forward checking and MRV steered straight to the answer without a single backtrack. To see how much they matter, try the classic N-queens puzzle, placing \(n\) queens on an \(n \times n\) board so that no two share a row, column or diagonal:

def queens(n):
    domains = {c: list(range(n)) for c in range(n)}     # the row of the queen in column c
    cons = {c: [(c2, lambda r1, r2, d=abs(c - c2): r1 != r2 and abs(r1 - r2) != d)
                for c2 in range(n) if c2 != c] for c in range(n)}
    return domains, cons

The industrial versions

Real scheduling, routing and configuration problems are handed to mature solvers, and the engineer's job is to model the problem well. SAT solvers decide whether a formula over true/false variables can be satisfied, and handle huge industrial instances in chip and software verification. SMT solvers such as Z3 add arithmetic and other theories. Constraint programming and integer programming solvers build rosters, timetables and delivery routes; Google's open-source OR-Tools packages a strong one, CP-SAT, along with routing libraries. You declare the variables and constraints, the solver does the search, and for optimisation problems it reports how far its answer could be from the best possible. This is also a good division of labour with an LLM: the model turns a messy request into a constraint model, and the solver returns an answer that is guaranteed to satisfy it.

Adversarial search: playing games

In a game an opponent picks every other move, and they are trying to beat you. A plan that ignores them is useless, so the search has to consider their replies too. The classic setting is a two-player, zero-sum game in which both players see everything: chess, Go, tic-tac-toe.

Minimax and alpha-beta pruning

Minimax assumes the opponent always replies with the move that is worst for you, and chooses the move whose worst case is best. A finished game has a fixed value for the maximising player X (here +1 for a win, 0 for a draw, -1 for a loss), and every other position takes its value from its children:

\[ V(s) = \max_a V(\text{result}(s, a)) \ \text{if X is to move}, \qquad V(s) = \min_a V(\text{result}(s, a)) \ \text{if O is to move} \]

Alpha-beta pruning gets the same answer with far less work. It tracks \(\alpha\), the score X can already guarantee, and \(\beta\), the score O can already hold X to. As soon as \(\alpha \ge \beta\) in some position, one player has a better option elsewhere and will never let the game reach this position, so its remaining moves are skipped.

from functools import lru_cache

LINES = [(0, 1, 2), (3, 4, 5), (6, 7, 8), (0, 3, 6),
         (1, 4, 7), (2, 5, 8), (0, 4, 8), (2, 4, 6)]

def winner(b):
    for i, j, k in LINES:
        if b[i] != "." and b[i] == b[j] == b[k]:
            return b[i]
    return None

def legal(b):      return [i for i, v in enumerate(b) if v == "."]
def play(b, i, p): return b[:i] + p + b[i + 1:]
def other(p):      return "O" if p == "X" else "X"

def minimax(b, player, alpha=-2, beta=2, prune=True, stats=None):
    """Value of board b for X (+1 win, 0 draw, -1 loss) with `player` to move."""
    stats["nodes"] += 1
    w = winner(b)
    if w or "." not in b:
        return {"X": 1, "O": -1, None: 0}[w]
    values = []
    for i in legal(b):
        v = minimax(play(b, i, player), other(player), alpha, beta, prune, stats)
        values.append(v)
        if player == "X":
            alpha = max(alpha, v)         # X can already guarantee at least alpha
        else:
            beta = min(beta, v)           # O can already hold X to at most beta
        if prune and alpha >= beta:
            break                         # the other player would never allow this line
    return max(values) if player == "X" else min(values)

for prune in [False, True]:
    stats = {"nodes": 0}
    v = minimax("." * 9, "X", prune=prune, stats=stats)
    print(f"alpha-beta={prune!s:5}  value={v}  nodes searched={stats['nodes']:,}")

@lru_cache(maxsize=None)                  # a transposition table: each position solved once
def value(b, player):
    w = winner(b)
    if w or "." not in b:
        return {"X": 1, "O": -1, None: 0}[w]
    vals = [value(play(b, i, player), other(player)) for i in legal(b)]
    return max(vals) if player == "X" else min(vals)

def perfect_move(b, player):
    pick = max if player == "X" else min
    return pick(legal(b), key=lambda i: value(play(b, i, player), other(player)))

alpha-beta=True   value=0  nodes searched=18,297

Tic-tac-toe is a draw with perfect play, as every child eventually discovers. Pruning cut the search 30-fold without changing the answer; with good move ordering, alpha-beta can search about twice as deep as plain minimax in the same time. The cached value function shows another trick every game engine uses. The full game tree has 549,946 nodes but only 5,478 distinct positions, because the same position arises from different move orders, so a transposition table solves each position once.

Chess has around 35 legal moves per position and games last dozens of moves, so no engine searches to the end. It stops at a depth limit and scores the positions there with an evaluation function. Deep Blue used a hand-tuned evaluation on custom hardware. Stockfish, the strongest open-source engine, still runs alpha-beta search but scores positions with a small neural network.

Monte Carlo tree search

Go resisted this recipe for decades: there are around 250 moves per position and nobody could write a good evaluation function. Monte Carlo tree search (MCTS) needs neither a full search nor an evaluation function. It estimates how good a move is by playing many fast, random games from it, and it spends those games unevenly: more on moves that look promising, while still trying the others now and then.

Choosing which child to descend into is a multi-armed bandit problem: each move is a slot machine with an unknown payout. UCT (upper confidence bounds applied to trees, Kocsis and Szepesvári, 2006) picks the child with the highest

\[ \frac{W_i}{N_i} + c\sqrt{\frac{\ln N}{N_i}}, \]

where \(W_i / N_i\) is the child's average result so far (exploitation), \(N\) is the parent's visit count, and the second term grows for children that have rarely been tried (exploration). You will meet this trade-off again in lesson .

import random

class Node:
    def __init__(self, board, player, parent=None, move=None):
        self.board, self.player, self.parent, self.move = board, player, parent, move
        self.children = []
        self.untried = [] if winner(board) else legal(board)
        self.visits, self.score = 0, 0.0  # score for the player who moved INTO this node

def uct(child, parent_visits, c):
    return (child.score / child.visits
            + c * math.sqrt(math.log(parent_visits) / child.visits))

def mcts(board, player, iterations=500, c=1.4, rng=random):
    root = Node(board, player)
    for _ in range(iterations):
        node = root
        # 1. Selection: descend through fully expanded nodes by the UCT score
        while not node.untried and node.children:
            node = max(node.children, key=lambda ch: uct(ch, node.visits, c))
        # 2. Expansion: add one untried move as a new child
        if node.untried:
            i = node.untried.pop(rng.randrange(len(node.untried)))
            child = Node(play(node.board, i, node.player), other(node.player), node, i)
            node.children.append(child)
            node = child
        # 3. Simulation: play random moves to the end of the game
        b, p = node.board, node.player
        while not winner(b) and "." in b:
            b, p = play(b, rng.choice(legal(b)), p), other(p)
        w = winner(b)
        # 4. Backpropagation: update every node on the path back to the root
        while node:
            node.visits += 1
            mover = other(node.player)
            node.score += 1.0 if w == mover else 0.5 if w is None else 0.0
            node = node.parent
    return max(root.children, key=lambda ch: ch.visits).move   # the most visited move

def match(x_player, o_player, games, seed=0):
    rng, tally = random.Random(seed), {"X": 0, "O": 0, None: 0}
    for _ in range(games):
        b, p = "." * 9, "X"
        while not winner(b) and "." in b:
            move = (x_player if p == "X" else o_player)(b, p, rng)
            b, p = play(b, move, p), other(p)
        tally[winner(b)] += 1
    return {"X wins": tally["X"], "O wins": tally["O"], "draws": tally[None]}

randomly = lambda b, p, rng: rng.choice(legal(b))
perfectly = lambda b, p, rng: perfect_move(b, p)

    player = lambda b, p, rng, n=n: mcts(b, p, n, rng=rng)
    print(f"perfect X vs MCTS({n:4}) as O:", match(perfectly, player, 20))

With 20 simulations per move, MCTS loses almost every game against perfect play; with 1,000 it never loses. Nobody told it anything about tic-tac-toe strategy. It is also an anytime algorithm: stop it whenever you like and take the most visited move.

Whose point of view?

The classic MCTS bug is scoring results from the wrong player's perspective, so the tree carefully finds the opponent's best moves and plays them. In the code above, each node's score is from the point of view of the player who made the move into it, which is exactly what its parent needs when choosing between children.

AlphaGo and AlphaZero: search plus learned intuition

DeepMind's AlphaGo, which beat Lee Sedol in 2016, combined MCTS with two neural networks: a policy network that suggests promising moves, first trained on human expert games, and a value network that estimates who is winning a position. AlphaGo Zero and then AlphaZero (Silver et al., 2017) dropped the human games: a single network with a policy head and a value head learns entirely from games against itself, and the same algorithm mastered Go, chess and shogi.

The networks change two steps of the loop you just wrote. Selection uses the policy's prior \(P(s, a)\) to focus on plausible moves:

\[ a^* = \arg\max_a \left[ Q(s, a) + c\,P(s, a)\,\frac{\sqrt{N(s)}}{1 + N(s, a)} \right] \]

and the random playout disappears: a new leaf is scored by the value network instead. Training closes the loop. The move probabilities that come out of a search, proportional to the visit counts, are better than the network's raw policy, so the network is trained to imitate them and to predict the final result of each self-play game. Search improves the network, and the better network makes the next search stronger. MuZero (2019) went one step further and learned its own model of the game, so it could plan without being given the rules. That pairing of fast learned intuition with slow, deliberate search is one of the most important ideas in modern AI, and it comes back at the end of this lesson.

Knowledge and logic

Search needs a description of the problem; logic is a way of writing down what you know so that a program can draw conclusions from it. In propositional logic, facts are symbols that are true or false (battery_low, no_data) and rules combine them: if no_data and battery_low, then power_fault. Forward chaining starts from the known facts and fires every rule whose premises all hold, adding its conclusion, until nothing new appears. That loop was the inference engine of the expert systems of the 1980s.

RULES = [
    ({"no_data", "battery_low"}, "power_fault"),
    ({"no_data", "battery_ok"}, "comms_fault"),
    ({"comms_fault", "modem_light_off"}, "replace_modem"),
    ({"power_fault", "panel_dirty"}, "clean_panel"),
    ({"power_fault"}, "send_spare_battery"),
]

def forward_chain(facts, rules):
    facts = set(facts)
    changed = True
    while changed:                        # keep firing rules until nothing new appears
        changed = False
        for premises, conclusion in rules:
            if premises <= facts and conclusion not in facts:
                facts.add(conclusion)
                changed = True
                print("  ", " and ".join(sorted(premises)), "=>", conclusion)
    return facts

Rules remain the right tool where the logic is genuinely crisp and must be auditable: tax and benefit calculations, eligibility checks, compliance policies, and deterministic guardrails around a model (lesson ).

Reasoning under uncertainty

Probability is the fix for "usually". Bayes' rule from lesson updates a belief in the light of evidence:

\[ P(\text{cause} \mid \text{evidence}) = \frac{P(\text{evidence} \mid \text{cause})\,P(\text{cause})}{P(\text{evidence})} \]

The difficulty is scale. A full joint distribution over \(n\) true/false variables needs \(2^n - 1\) numbers, which is hopeless beyond a few dozen variables.

Bayesian networks

A Bayesian network is a directed graph in which each variable depends directly only on its parents, an idea Judea Pearl did much to develop in the 1980s. The joint distribution then splits into small local tables:

\[ P(x_1, \ldots, x_n) = \prod_{i=1}^{n} P\big(x_i \mid \text{parents}(x_i)\big) \]

Here is a station that has gone silent. A storm or a hardware fault can cause an outage, and a storm also tends to knock out the neighbouring station. Eight numbers describe the network, where the full joint would need fifteen. Inference by enumeration answers any question by adding up the joint probability of every world consistent with the evidence:

from itertools import product

# node: (parents, P(node is True | each combination of parent values))
NET = {
    "storm":     ((), {(): 0.10}),
    "fault":     ((), {(): 0.02}),
    "outage":    (("storm", "fault"), {(True, True): 0.95, (True, False): 0.30,
                                       (False, True): 0.90, (False, False): 0.01}),
    "neighbour": (("storm",), {(True,): 0.70, (False,): 0.05}),
}

def joint(world):
    """P(world) as the product of each node's probability given its parents."""
    p = 1.0
    for var, (parents, cpt) in NET.items():
        p_true = cpt[tuple(world[q] for q in parents)]
        p *= p_true if world[var] else 1 - p_true
    return p

def query(var, evidence):
    """P(var is True | evidence), by summing the joint over every possible world."""
    totals = {True: 0.0, False: 0.0}
    for values in product([True, False], repeat=len(NET)):
        world = dict(zip(NET, values))
        if all(world[k] == v for k, v in evidence.items()):
            totals[world[var]] += joint(world)
    return totals[True] / (totals[True] + totals[False])

print(f"P(fault)                             = {query('fault', {}):.3f}")
print(f"P(fault | outage)                    = {query('fault', {'outage': True}):.3f}")
print(f"P(fault | outage, neighbour offline) = "
      f"{query('fault', {'outage': True, 'neighbour': True}):.3f}")
print(f"P(fault | outage, neighbour online)  = "
      f"{query('fault', {'outage': True, 'neighbour': False}):.3f}")
P(fault)                             = 0.020
P(fault | outage)                    = 0.321
P(fault | outage, neighbour offline) = 0.092
P(fault | outage, neighbour online)  = 0.481

The outage raises the chance of a hardware fault from 2% to 32%. Then the neighbour changes the picture. If it is offline too, a storm explains the outage and the fault probability falls to 9%; if it is fine, a storm is unlikely and the fault probability rises to 48%. This is explaining away, and it is exactly the reasoning that if-then rules cannot do. Enumeration takes time exponential in the number of hidden variables, so real systems use smarter exact methods (variable elimination) or sampling, and probabilistic programming languages such as Stan and PyMC let you write such models as code and run the inference automatically.

Naive Bayes

A Naive Bayes classifier is the simplest useful Bayesian network: the class is the only parent, and every word is a child that depends only on the class. "Naive" refers to that assumption, that words are independent once you know the class. It is plainly false and works surprisingly well anyway. To classify a document, pick the class \(c\) with the highest score

\[ \log P(c) + \sum_{i} \log P(w_i \mid c), \qquad P(w \mid c) = \frac{\text{count}(w, c) + \alpha}{\sum_{w'} \text{count}(w', c) + \alpha\,|V|} \]

where \(|V|\) is the vocabulary size and \(\alpha\), usually 1, is Laplace smoothing. Here it is from scratch on 24 hand-written maintenance tickets:

import re

def tokens(text):
    return re.findall(r"\b\w\w+\b", text.lower())   # the same rule scikit-learn uses

class NaiveBayes:
    def fit(self, texts, labels, alpha=1.0):
        self.classes = sorted(set(labels))
        self.vocab = {w for t in texts for w in tokens(t)}
        self.log_prior, self.log_lik = {}, {}
        for c in self.classes:
            docs = [t for t, y in zip(texts, labels) if y == c]
            counts = Counter(w for t in docs for w in tokens(t))
            self.log_prior[c] = np.log(len(docs) / len(texts))
            # Laplace smoothing: pretend every word was seen alpha extra times
            denom = sum(counts.values()) + alpha * len(self.vocab)
            self.log_lik[c] = {w: np.log((counts[w] + alpha) / denom) for w in self.vocab}
        return self

    def scores(self, text):
        """log P(class) + sum of log P(word | class), skipping words never seen."""
        words = [w for w in tokens(text) if w in self.vocab]
        return {c: self.log_prior[c] + sum(self.log_lik[c][w] for w in words)
                for c in self.classes}

    def predict(self, text):
        s = self.scores(text)
        return max(s, key=s.get)

texts, labels = zip(*TRAIN)

Two details that break hand-written Naive Bayes

Add log probabilities instead of multiplying probabilities: the product of a few hundred small numbers underflows to zero. And smooth the counts: without \(\alpha\), a single word never seen with a class in training gives that class probability zero, whatever the rest of the document says.

Naive Bayes trains in one pass over the data and makes a good first baseline for text classification; early spam filters were built on it. Compare it with embeddings plus logistic regression (lesson ) or a zero-shot prompt (lesson ) before reaching for anything bigger.

Planning

Planning is search where each state is a description of the world. The STRIPS representation (Fikes and Nilsson, 1971, built for the Shakey robot) describes a state as the set of facts that are true, and each action by three sets: preconditions that must hold, an add list of facts it makes true and a delete list of facts it makes false. Everything else stays as it was. Here is a technician's repair visit, and the planner is the BFS from session 1, unchanged:

from typing import NamedTuple

class Action(NamedTuple):
    name: str
    pre: frozenset                        # facts that must be true beforehand
    add: frozenset                        # facts the action makes true
    delete: frozenset                     # facts the action makes false

def act(name, pre, add, delete=()):
    return Action(name, frozenset(pre), frozenset(add), frozenset(delete))

ACTIONS = [
    act("load spare part", {"at_depot"}, {"have_part"}),
    act("drive to site", {"at_depot"}, {"at_site"}, {"at_depot"}),
    act("drive to depot", {"at_site"}, {"at_depot"}, {"at_site"}),
    act("power down", {"at_site", "powered"}, {"unpowered"}, {"powered"}),
    act("power up", {"at_site", "unpowered"}, {"powered"}, {"unpowered"}),
    act("fit part", {"at_site", "have_part", "unpowered"}, {"part_fitted"}, {"have_part"}),
    act("calibrate", {"at_site", "powered", "part_fitted"}, {"calibrated"}),
]

def applicable(state):
    for a in ACTIONS:
        if a.pre <= state:
            yield (state - a.delete) | a.add, a.name

def plan(initial, goal):
    """Breadth-first search over sets of facts, with the search code from session 1."""
    succ = lambda s: [(s2, 1) for s2, _ in applicable(s)]
    path, expanded = uninformed_search(frozenset(initial), lambda s: goal <= s, succ)
    names = [next(n for s2, n in applicable(s) if s2 == t) for s, t in zip(path, path[1:])]
    return names, expanded

steps, n = plan({"at_depot", "powered"}, {"part_fitted", "calibrated", "at_depot"})
for i, step in enumerate(steps, 1):
    print(i, step)
print(n, "states expanded")

Nobody wrote that sequence down; the planner derived it, including the easily forgotten steps of powering down before fitting the part and powering up again before calibrating. With \(k\) facts there are up to \(2^k\) states, so real planners need heuristics, and the clever part is that they compute them automatically from the action descriptions. A common one solves a relaxed problem that ignores delete lists, the same relaxation idea that gave you Manhattan distance. The standard language today is PDDL, read by planners such as Fast Downward, and planning software has run logistics, factories and even a spacecraft: NASA's Remote Agent experiment flew on Deep Space 1 in 1999.

Classical AI inside LLM agents

An LLM agent (lesson ) has exactly the strengths classical AI lacked: it understands messy language, has broad common sense and needs no hand-written model of the domain. It also has the opposite weaknesses: it guesses, it is not exhaustive and it offers no guarantees. The strongest systems pair the two. Four patterns keep recurring.

  • The LLM models, a solver solves. The model turns a request into a constraint model, a PDDL problem, a SQL query or a call to a route planner, and a classical tool produces an answer that is correct by construction. The LLM+P paper (2023) did this for PDDL planning; with tool use you can do it with OR-Tools today.
  • Search over the model's outputs. Tree of Thoughts (Yao et al., 2023) runs breadth-first or depth-first search over partial solutions, with the LLM proposing next steps and rating how promising each one is. The model plays the part of the successor function and the heuristic. Best-of-\(n\) sampling with a scorer is the simplest version of the same idea.
  • Generate, then verify. A checker tests what the model proposes: unit tests for generated code, a schema for structured output, a proof checker for mathematics, a validator for plans. AlphaGeometry (2024) paired a language model that suggests geometric constructions with a symbolic engine that does the deduction; FunSearch (2023) had an LLM propose programs and an automatic evaluator score them inside an evolutionary search.
  • Plan, act, check, replan. The ReAct loop decides one step at a time. For long tasks, have the agent write a plan, check each step's preconditions before acting, and replan when an observation contradicts the plan. That is classical planning and execution monitoring with a learned model inside.

The common thread is the AlphaZero idea: a fast learned model proposes, and search plus verification make the result reliable. A verifier is only as good as what it checks, so that is where the engineering effort belongs.

Hands-on: check a plan before you run it

  1. Write validate(initial, goal, steps). It applies a list of action names from ACTIONS one at a time and returns (True, "goal reached"), or False with a message naming the first step whose preconditions fail and the missing facts, or the goal facts still false at the end.
  2. Check the planner's plan, then this one, as if an LLM had proposed it: ["load spare part", "drive to site", "fit part", "calibrate", "drive to depot"].
  3. Add an action log visit that needs at_depot and calibrated and adds logged. Add logged to the goal, replan, and validate the new plan.

You are done when the proposed plan is rejected at step 3 because unpowered is missing, and the new plan has eight steps ending with log visit.

Show a solution 
def validate(initial, goal, steps):
    """Simulate a plan one step at a time. Return (ok, message)."""
    by_name = {a.name: a for a in ACTIONS}
    state = frozenset(initial)
    for i, name in enumerate(steps, 1):
        if name not in by_name:
            return False, f"step {i}: unknown action {name!r}"
        a = by_name[name]
        missing = a.pre - state
        if missing:
            return False, f"step {i} ({name}): preconditions not met: {sorted(missing)}"
        state = (state - a.delete) | a.add
    missing = goal - state
    return not missing, "goal reached" if not missing else f"goal not met: {sorted(missing)}"

init, goal = {"at_depot", "powered"}, {"part_fitted", "calibrated", "at_depot"}
print("planner's plan:", validate(init, goal, steps))
proposed = ["load spare part", "drive to site", "fit part", "calibrate", "drive to depot"]
print("proposed plan: ", validate(init, goal, proposed))

if "log visit" not in [a.name for a in ACTIONS]:       # safe to re-run this cell
    ACTIONS.append(act("log visit", {"at_depot", "calibrated"}, {"logged"}))
new_steps, _ = plan(init, goal | {"logged"})
print("new plan:")
for i, step in enumerate(new_steps, 1):
    print(" ", i, step)
print("new plan check:", validate(init, goal | {"logged"}, new_steps))

This is the pattern agents need. The model can propose a plan in any wording, but before anything touches real equipment a dozen lines of deterministic code check it against a model of the world. The error message is also exactly what you would send back to the model so that it can repair its plan, which turns a one-shot guess into a search with a verifier.

Check yourself

You need the shortest drive across a road map whose roads have different lengths. Why is breadth-first search the wrong tool?

  • It cannot handle maps with loops in them
  • It finds the route with the fewest roads, which need not be the shortest in kilometres
  • It always runs out of memory on road maps
  • It only works on grids

BFS is optimal only when every step costs the same. Uniform-cost search and A* order the frontier by path cost instead.

What does an admissible heuristic guarantee when you use it with A*?

  • A* will expand fewer states than greedy best-first search
  • The heuristic equals the true remaining cost
  • The path A* returns is optimal, because the heuristic never overestimates the remaining cost
  • A* no longer needs a priority queue

Because \(h\) never overestimates, the \(f\) value of a state on the best path never exceeds the optimal cost, so A* cannot pop the goal by a worse route first.

Compared with plain minimax, what does alpha-beta pruning change?

  • It returns the same value while skipping branches that cannot affect the decision
  • It returns an approximate value that is usually close enough
  • It only works for games that involve dice
  • It needs an evaluation function learned from data

Pruning is exact. On tic-tac-toe it searched 18,297 nodes instead of 549,946 and still found the draw.

In AlphaZero, what takes the place of the random playouts of classic MCTS?

  • Many more random playouts
  • Alpha-beta search to the end of the game
  • A database of human expert games
  • A value network that scores the new leaf, with a policy network guiding which moves to explore

The value head evaluates leaves and the policy head supplies the priors in the selection rule. Self-play then trains both on the results of the search.

A hand-written Naive Bayes classifier gives the class "power" a probability of exactly zero for a ticket that is mostly about batteries, because it also contains one word never seen in a power ticket during training. What fixes it?

  • Removing the class prior
  • Laplace smoothing: add a small count \(\alpha\) for every word in every class
  • Multiplying probabilities instead of adding their logs
  • Training on fewer examples

Without smoothing, one unseen word has \(P(w \mid c) = 0\), which wipes out the whole product whatever the other words say.

Key takeaways

  • Many problems become routine once written as states, actions, a goal test and path costs. BFS, DFS, uniform-cost search and A* differ only in which frontier state they expand next.
  • Uniform-cost search (Dijkstra) is optimal for non-negative costs. A* adds an admissible heuristic, \(f = g + h\), to stay optimal while expanding far fewer states. Test for the goal when a state is expanded.
  • Constraint problems yield to backtracking with forward checking and MRV. In production, model the problem and hand it to a SAT, constraint or integer programming solver such as OR-Tools.
  • Alpha-beta is exact and far cheaper than plain minimax. MCTS replaces the evaluation function with simulation, and AlphaZero replaces simulation with learned policy and value networks.
  • Rules are auditable but brittle. Bayesian networks handle uncertainty and explaining away, and Naive Bayes is a fast text baseline (smooth the counts, add the logs).
  • Strong LLM systems use the AlphaZero split: a learned model proposes, while search, solvers and verifiers make the result reliable.
