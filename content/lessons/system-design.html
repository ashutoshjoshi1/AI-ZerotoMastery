A design framework

Whether in an interview or a real project kickoff, AI system design goes better with a structure. This one follows the order in which mistakes are cheapest to fix. You have met every ingredient already; this lesson is about putting them together.

1. Problem and success criteria

  • Who uses it, for what decision or task, and what happens today without it?
  • What does good look like, measurably? Accuracy on what, latency under what, cost below what?
  • What does a mistake cost? A wrong film recommendation and a wrong maintenance instruction deserve very different designs.
  • Is a language model even the right tool? If rules or a database query solve it, use them. If a classical model on tabular data solves it, use that (lesson ). If the problem is a route, a schedule, a forecast, a ranking or an image, part IX has a better tool than any prompt.

2. Data

  • What data exists, where, in what format and quality? Who owns it, and what are the privacy constraints?
  • What will the system see at inference time, and does it match what you can train or evaluate on?
  • Where will evaluation data come from? If you cannot answer this, you are not ready to build.

3. Approach: the simplest thing that could work

Climb the ladder only as far as your evaluation says you must:

Rung Use when
Rules, queries or search The logic is known and stable, or the problem is a route, a schedule or a game (lesson )
Classical ML Structured or tabular data, labelled outcomes (lesson )
Prompted LLM Language tasks, few examples, fast iteration (lesson )
Reasoning model Multi-step problems where correctness matters more than latency: maths, code, planning, hard diagnosis (lesson )
LLM + retrieval Answers depend on your documents or data (lesson )
Workflow with tools Needs live data or actions, steps are predictable (lesson )
Agent Steps genuinely cannot be known in advance; needs memory across turns (lessons , )
Fine-tuned model Behaviour, format or cost targets that prompting cannot reach (lessons , )

Each rung adds cost, latency and ways to fail. The question to ask at every step is "what did the evaluation show that the rung below could not do?" If you cannot answer, stay put.

When a language model is the wrong tool

Language models are good at language: understanding requests, synthesising text, calling tools, talking to people. A great deal of valuable AI is not language. The lessons of part IX exist so that you recognise these cases and reach for the right tool.

The task looks like Reach for Lesson
Find a route, a schedule, a valid assignment or a move Search, a constraint solver, a planner, Monte Carlo tree search
Predict an outcome from rows and columns Gradient boosting, logistic regression, a well-chosen baseline
Choose actions with delayed rewards in a simulator or a game Reinforcement learning, or a bandit for exploration
Classify, detect or segment images at volume A CNN or vision transformer trained on your images
Forecast a numeric series Seasonal baselines, exponential smoothing, boosting on lag features
Rank items for a person, or reason over a network Collaborative filtering, two-tower models, graph neural networks
Generate images, audio or designs Diffusion or flow models
Explain why a model decided what it did Attribution methods, probes, feature analysis

The language model usually still has a job in these systems: parsing the request, explaining the result, writing the report, answering follow-up questions. Case study 3 and the design drill below show the pattern.

4. Architecture

Sketch the components (lesson 's diagram is a good template): clients, API layer, orchestration, model calls, retrieval stores, tools, caches, observability. For each model call, decide the model tier, the prompt, the output format and the failure behaviour.

Then go through the levers you learned in parts VI and VII, one by one. Most designs need two or three of them, not all.

Lever Reach for it when Lesson
Model tier and routing Always. Start mid-tier; send easy cases to a small model and hard ones up, decided by a classifier or a confidence score ,
Reasoning effort A minority of requests need multi-step thinking. Give those a thinking budget; keep it off for extraction and lookup, where it adds latency and cost for nothing
Context engineering Every multi-turn or agentic system. Decide what enters the window each turn, how history is compacted, and what is stored as memory and retrieved on demand
Prompt caching A long, stable prefix (instructions, tools, reference text) is reused across many calls ,
Post-training Prompting cannot reach the behaviour, format or cost you need at volume: distil to a small model, then preference-tune on your own error analysis ,
Inference optimisation You serve a model yourself. Quantise the weights, batch continuously, cache shared prefixes, and use speculative decoding when decode speed matters
Hosted API versus self-hosting Decide on volume, privacy, latency and the operations capacity you really have. Hosted first unless one of these forces your hand

5. Evaluation

Define offline evals (golden set, graders, slices, thresholds), the human review loop, and online metrics. Decide what blocks a release (lesson ). For a non-LLM component, use its own metrics: precision and recall at the operating threshold, forecast error against a seasonal baseline, recall@k for a recommender.

6. Risks and safeguards

Prompt injection exposure, data access boundaries, consequential actions and approvals, privacy, bias, abuse (lesson ). Name the one failure that would get the system switched off, and design against it first.

7. Operations

Latency budget and where it goes, cost per request and per month, scaling, caching, monitoring, alerting, incident response, and how you will upgrade models safely (lesson ).

Do the cost arithmetic early, with illustrative numbers if you do not have real ones yet. A back-of-envelope estimator is enough to see which lever matters:

def estimate(requests_per_day, in_tokens, out_tokens, price_in, price_out,
             cached_fraction=0.0, cache_discount=0.9,
             batch_fraction=0.0, batch_discount=0.5,
             ttft_s=0.6, tokens_per_s=60):
    """Monthly cost and typical latency for one model call per request.

    Prices are per million tokens. cached_fraction is the share of input
    tokens read from the prompt cache at (1 - cache_discount) of the price.
    batch_fraction is the share of requests sent through a batch API at
    (1 - batch_discount) of the price."""
    in_price = price_in * ((1 - cached_fraction)
                           + cached_fraction * (1 - cache_discount))
    per_request = in_tokens / 1e6 * in_price + out_tokens / 1e6 * price_out
    per_request *= (1 - batch_fraction) + batch_fraction * (1 - batch_discount)
    latency = ttft_s + out_tokens / tokens_per_s
    return {"per_request": round(per_request, 4),
            "monthly": round(per_request * requests_per_day * 30),
            "latency_s": round(latency, 1)}

# Illustrative prices; plug in your provider's current ones.
base = dict(requests_per_day=2000, in_tokens=4000, out_tokens=350,
            price_in=3.0, price_out=15.0)
print("plain       ", estimate(**base))
print("cached 70%  ", estimate(**base, cached_fraction=0.7))
print("+ batch 50% ", estimate(**base, cached_fraction=0.7, batch_fraction=0.5))
plain        {'per_request': 0.0173, 'monthly': 1035, 'latency_s': 6.4}
cached 70%   {'per_request': 0.0097, 'monthly': 581, 'latency_s': 6.4}
+ batch 50%  {'per_request': 0.0073, 'monthly': 436, 'latency_s': 6.4}

Notice what the numbers say: caching nearly halves the bill because input tokens dominate, batching helps only the traffic that can wait, and neither touches latency. Latency here is almost all generation, so a shorter answer or a faster model is the lever (lesson ).

8. Iteration plan

What ships first (a narrow slice), what you will learn from it, and what comes next.

Talk in trade-offs

Every design decision trades something: quality against latency, cost against coverage, autonomy against predictability, freshness against complexity. Strong designers name the trade-off, state which way they lean for this problem, and say what evidence would change their mind.

Hands-on: choose the approach for six briefs

For each brief, write three lines: the rung or tool you would start with, why the one below it is not enough, and the first metric you would measure. Decide in under four minutes per brief; that is roughly the time you get in an interview.

  1. A warehouse wants to know how many units of each of 2,000 products it will ship next week.
  2. A laboratory wants to flag microscope images that contain a contaminated sample, 50,000 images a day.
  3. A school must build a timetable that satisfies about 300 constraints on rooms, teachers and periods.
  4. An insurer wants to decide which of 10,000 daily claims to send for manual review, and has five years of labelled history.
  5. A support team wants an assistant that answers questions about a 500-page policy manual that changes monthly, and hands over to a person when unsure.
  6. A platform team wants an assistant that fixes failing builds by reading the logs, editing the code and rerunning the tests.

You are done when every brief has a tool, a reason and a metric, and at most two of the six use a language model as the core.

Show a worked answer
  1. Forecasting (lesson ): a seasonal naive baseline per product, then gradient boosting on lag and calendar features if it beats the baseline. A language model has no advantage on 2,000 numeric series. Metric: error against the seasonal baseline, measured on the last eight weeks held out.
  2. Vision classifier (lesson ): a small CNN or a fine-tuned vision transformer on labelled images. A vision-language model could label the first few thousand examples, but at 50,000 images a day it is too slow and costly to be the classifier. Metric: recall at a threshold that keeps false alarms reviewable.
  3. Constraint solver (lesson ): the problem is exactly a constraint satisfaction problem. No learning is needed; a solver gives a valid timetable or proves there is none. Metric: constraints satisfied, and solve time.
  4. Classical ML (lesson ): gradient boosting on the claim features, with labelled history as training data. An LLM may help extract features from free-text claim notes, but the decision model is tabular. Metric: recall on fraudulent or erroneous claims at the review capacity you have.
  5. LLM with retrieval (lesson ): the knowledge changes monthly and answers must cite the manual, so retrieval beats fine-tuning and long context. Prompting alone fails because the model has not read the manual. Metric: citation accuracy and abstention rate on a question set.
  6. Agent with a reasoning model (lessons , ): the steps depend on what the logs say, so a fixed workflow will not do, and diagnosis across several files benefits from a thinking budget. Guard it with step and cost limits, a sandbox and tests that must pass. Metric: fraction of builds fixed with tests green, and cost per fix.

Two of six have a language model at the core. That ratio is typical of real organisations, and it is why part IX is in this course.

Case study 1: an assistant over technical documentation

Brief. Field engineers need answers from 3,000 pages of instrument manuals, service bulletins and past incident reports, on laptops and sometimes on poor connections. Answers must cite the source page. Some bulletins are restricted to senior staff.

Problem and success. Users ask procedural and troubleshooting questions. Success: the correct procedure is cited in at least 90% of answerable questions in the eval set; on unanswerable questions, the assistant says so at least 95% of the time; median time to first token under 2 seconds.

Data. PDFs with tables, diagrams and some scans; bulletins updated weekly; incident reports in a ticketing system. Evaluation data: 150 questions collected from senior engineers, each with the page that answers it, plus 30 unanswerable questions.

Approach. RAG, because knowledge changes weekly and citations are required. Not fine-tuning (knowledge, not behaviour). Not a full agent at first; perhaps later for multi-step troubleshooting, where a reasoning model with a thinking budget would be routed only the hard cases (lesson ).

Architecture.

  • Ingestion: layout-aware PDF parsing; VLM transcription for scanned pages and diagrams (lesson ); chunks at section level with document title, model and section path prepended; metadata for document type, product, date and access level.
  • Retrieval: hybrid (BM25 is essential for part numbers and error codes) with RRF, filtered by the user's access level before ranking, then a cross-encoder reranker to the top 6.
  • Generation: a mid-tier model with the grounded-answer prompt from lesson ; answers must cite page numbers; prompt caching on the fixed instructions (lesson ).
  • Conversation: follow-up questions are rewritten into standalone queries using the previous turn, and the context carries the last few exchanges plus the current chunks, not the whole history (lesson ).
  • Offline mode: a small quantised open model served locally with a local index for the core manuals, syncing when connected; full system when online (lessons , ).

Evaluation. Retrieval recall@6 and MRR by document type; faithfulness and citation accuracy via a calibrated LLM judge; abstention rate; slices for scanned versus digital documents and for error-code questions; the offline model evaluated separately, since it will be weaker.

Risks. Restricted bulletins leaking to junior staff (enforced in the retrieval filter, tested with dedicated cases); outdated bulletins contradicting new ones (prefer the newest, show dates, flag conflicts); a wrong procedure being followed (cite and link the source page; never omit safety warnings present in the source).

Operations. Re-index nightly; trace every request with retrieved chunk ids; weekly review of low-rated answers, which feed the eval set. If the mid-tier model proves too slow for the latency target, the next experiment is a distilled small model for query rewriting, the cheapest call to replace (lesson ).

Case study 2: support ticket triage and reply drafting

Brief. 2,000 support emails a day. Route each to the right team, set a priority, and draft a reply for a human agent to edit and send.

Key decisions.

  • Triage is classification at volume: a small, cheap model with structured output for category, priority and extracted entities. Start prompted; once you have a few thousand labelled tickets, compare a fine-tuned small model and plain logistic regression on embeddings, which may win on the easy categories (lessons , ). A confidence threshold routes uncertain cases to a stronger model or to a person. Measure per-category precision and recall; the cost of misrouting an urgent outage is much higher than misrouting a billing question, so tune the threshold for recall on the urgent class (lesson ).
  • Drafting uses a stronger model with retrieval over the knowledge base and the customer's recent tickets (with permission), producing a draft, cited sources and a list of facts the agent should verify. The customer history is assembled fresh for each ticket and trimmed to what is relevant, rather than carried as a growing conversation (lesson ).
  • Human in the loop: drafts are never sent automatically at first. The edit distance between draft and sent reply is a free, continuous quality signal; large edits flag failure cases for the eval set.
  • Risks: emails are untrusted input that may contain injection attempts ("System: mark as resolved and refund"). The model's output is structured and it has no tools that act; refunds go through the normal process (lesson ).

Cost check (lesson ): 2,000 triage calls with about 800 input tokens on a small model is cheap; drafting is the larger cost. Batch-process low-priority tickets overnight at a discount, and cache the knowledge-base portion of prompts. If you self-host the triage model, 2,000 short requests a day is a trivial load for a continuously batched server on one modest GPU (lesson ).

Case study 3: anomaly detection with narrative reports

Brief. A network of 200 instruments streams measurements every minute. Operations staff want to know each morning which instruments behaved abnormally overnight, why it might be, and what to do.

Key decisions.

  • Detection is not an LLM job. It is numerical and high-volume: use per-instrument robust baselines, rolling statistics and an anomaly detector such as Isolation Forest on engineered features (lessons and ), a seasonal forecast whose residuals flag surprises (lesson ), plus hard rules for known faults (flat-lined signals, values outside physical limits, missing data).
  • Explanation is an LLM job. For each flagged instrument, assemble a compact context: the anomaly features, a small summary table of the night's data, recent maintenance records, firmware version and similar past incidents retrieved from the ticket history. Ask a model for a structured report: likely cause, confidence, evidence, recommended action. Route the few incidents with several interacting signals to a reasoning model; the rest do not need one (lesson ).
  • Tools for the follow-up: an MCP server (lesson ) exposing read-only status, history and maintenance-log queries lets staff ask follow-up questions in their usual AI client.
  • Evaluation: detection precision and recall measured against past labelled incidents; report quality judged by engineers on a weekly sample; track whether recommended actions turned out right.

The pattern generalises: classical ML or rules for detection and numbers, LLMs for language, synthesis and interaction. Many of the most valuable AI systems in science and engineering look like this.

Design drill: visual inspection on a packaging line

Brief. A camera above a packaging line photographs three items a second. The plant wants to reject items with a faulty seal. About one item in two hundred is faulty. A missed fault reaches a customer; a false reject costs a few seconds of an operator's time.

Key decisions.

  • Detection is a vision model (lesson ): a small CNN or a fine-tuned vision transformer on cropped seal images, running on a device next to the line within a latency budget of about 100 ms. A vision-language model is too slow and too expensive at three images a second, but it is useful for bootstrapping labels and for describing a flagged image to an operator (lesson ).
  • Imbalance drives the metric (lesson ): accuracy would be 99.5% for a model that never rejects. Report the precision-recall curve and choose the threshold from the asymmetric costs: high recall on faults, with false rejects kept within what operators can check.
  • Data: collect and label a few thousand images including every fault type, lighting condition and shift; augment; hold out whole days, not random frames, so that the test set is honest about drift.
  • Operations (lessons , ): quantise the model for the edge device; monitor the rejection rate and the input image statistics, because a changed lamp or a new supplier's film will shift them before anyone notices; keep a sample of rejected and accepted images for weekly review and relabelling.
  • Where the language model fits: a daily summary of rejects by type and shift, and a question-answering tool over the defect log for the quality team. Same pattern as case study 3.
  • Explainability (lesson ): a saliency map on each rejected image shows the operator where the model looked, which catches a model that learned the lighting rather than the seal.

Hands-on: design reviews

Write a two-page design document, using the eight-part framework, for one of these:

  1. A meeting assistant that records project meetings, produces minutes with action items, and answers questions across all past meetings.
  2. A code-review assistant for your team's repository that comments on pull requests.
  3. An assistant that helps scientists find, compare and summarise papers relevant to their research.
  4. A recommendation feed for a hobbyist marketplace with 50,000 listings, evaluated offline and online.

Then review your own document as a sceptical senior engineer: list the three riskiest assumptions and how you would test each one in the first two weeks.

Show what a strong answer covers for option 1
  • Problem and success: minutes that attendees rate as accurate and complete; action items with owner and date extracted with high precision (wrong owners are worse than missing items); question answering with citations to the meeting and timestamp.
  • Data: audio recordings; consent and privacy rules (who may be recorded, retention, who may search which meetings); evaluation set of 20 meetings with human-written minutes and action items.
  • Approach: speech-to-text with speaker diarisation (lesson ); an LLM with structured output for minutes and action items; RAG over transcripts chunked by topic with timestamps for questions.
  • Architecture: upload, transcription queue, summarisation workflow (chained: segment, summarise per topic, extract actions, consolidate), index with access control per meeting. Long meetings exceed a comfortable context, so summarise per topic and consolidate rather than sending a whole transcript (lesson ).
  • Evaluation: transcript word error rate on a sample; action-item precision and recall; faithfulness of minutes; retrieval recall on a question set.
  • Risks: private conversations in recordings; misattributed speakers leading to wrong owners; hallucinated decisions. Mitigate with consent flows, showing speaker labels with confidence, and linking every action item to its transcript timestamp.
  • Operations: transcription cost per hour of audio, batch overnight for long recordings, monitoring of edit rates on minutes.
  • Riskiest assumptions: transcription is accurate enough with your accents and jargon (test on five real recordings in week one); attendees accept recording (ask them); action items are said explicitly enough to extract (check against human minutes).

For option 4, a strong answer centres on a popularity baseline and a collaborative-filtering model, a time-based offline split with recall@k, and an A/B test with a primary metric and guardrails (lesson ). The language model, if any, writes listing descriptions for cold-start items and explains recommendations; it does not do the ranking.

Reading papers and staying current

The field moves weekly. You cannot read everything, and you do not need to.

How to read a paper efficiently

Use passes, and stop as soon as you have what you need:

  1. Five minutes: title, abstract, figures, conclusion. What is the claim, and does it matter to you?
  2. Thirty minutes: introduction, method overview, main results table, limitations. What exactly did they do, compared against what baselines, measured how?
  3. Deep read (rarely): the details, the appendix, the code. Reimplement the key idea in a notebook if you want to really own it.

Questions to ask every time: What is the baseline, and is it strong? Is the evaluation on data like mine? How big is the improvement relative to run-to-run variation? What did it cost (compute, data, latency)? Is there code?

An AI assistant can do the five-minute pass for you, and it is a fine way to triage a long reading list. Verify its summary against the paper's own results table before you repeat the claim to anyone.

A sustainable information diet

  • A few high-signal sources, not fifty: one or two newsletters, the engineering blogs of the major labs and tool makers, and a handful of practitioners whose judgement you trust.
  • Primary sources over commentary: release notes, model and system cards, documentation and papers rather than hot takes.
  • Hands on, not just eyes on: when something new looks relevant, spend 30 minutes trying it against your own eval set. That is worth more than hours of reading opinions about it.
  • Leaderboards are weak evidence: public benchmarks are contaminated, gamed and rarely like your workload (lesson ). Your eval set is strong evidence.
  • Separate durable from ephemeral: model rankings and framework APIs change monthly; attention, embeddings, retrieval, evaluation, tool use and the engineering discipline in this course change slowly. Invest most in the durable layer.

Deciding under change

Design so that change is cheap: models behind an interface, prompts versioned, evals automated, costs tracked, and a routing layer that can send a slice of traffic to a new model. Then, when a new model or technique appears, the question "should we switch?" becomes an afternoon's experiment with a clear answer, rather than a debate.

The experiment has a fixed shape. Run the full eval set on both models with the same prompts. Compare quality per slice with a confidence interval, not just two averages. Measure latency and cost on the same traffic. Switch only if the new model wins on quality or ties on quality and wins clearly on cost or latency, and write the decision down.

Hands-on: an afternoon's experiment

A new model has been released and your team wants to know whether to switch the documentation assistant to it. The cell below simulates the per-case results of both models on your 80-question eval set (1 is a pass), with latency and cost per request.

import numpy as np

rng = np.random.default_rng(7)
difficulty = rng.uniform(0, 1, size=80)          # hidden per-question difficulty
current = (rng.uniform(0, 1, 80) > difficulty * 0.9).astype(int)
candidate = (rng.uniform(0, 1, 80) > difficulty * 0.75).astype(int)
latency = {"current": 1.9, "candidate": 2.6}      # median seconds per request
cost = {"current": 0.011, "candidate": 0.008}     # per request
  1. Compute each model's pass rate and the paired difference.
  2. Bootstrap the difference (resample the 80 question indices, 5,000 times) and report a 95% interval, as in lesson .
  3. List the cases the candidate fixed and the cases it broke.
  4. Write the decision in three sentences: what you would do, what trade-off you are accepting, and what would change your mind.

You are done when you can say whether the interval excludes zero and have written a decision that mentions quality, latency and cost.

Show what you should find

Pairs matter: resample question indices and compute the difference on each resample, so that both models see the same questions. The solutions notebook prints something like:

current   pass rate 0.66
candidate pass rate 0.74
difference +0.075  95% interval [-0.025, +0.175]
fixed 16 cases, broke 10 cases

The candidate looks better, but with 80 questions the interval includes zero, so the evidence is weak. It is also slower and cheaper. A reasonable decision: do not switch the whole assistant yet; route 20% of traffic to the candidate behind the interface, grow the eval set with the broken cases, and revisit when the interval clears zero or the latency target is at risk.

Check yourself

In the design framework, what should you settle before choosing an architecture?

  • Which vector database to use
  • The problem, the cost of mistakes, measurable success criteria and where evaluation data will come from
  • The model with the highest leaderboard score
  • The deployment platform

Requirements and evaluation shape every later choice.

In case study 3, why is anomaly detection done with classical methods rather than an LLM?

  • LLMs cannot read numbers
  • Detection over high-volume numerical streams is cheaper, faster and more reliable with statistical and ML methods; LLMs add value in explanation and interaction
  • Isolation Forest is newer than LLMs
  • LLMs are not allowed to process sensor data

Use each tool where it is strongest: numbers to classical methods, language to LLMs.

Why must access-level filtering happen in the retrieval layer of the documentation assistant?

  • Anything placed in the model's context can leak into an answer; filtering before retrieval guarantees restricted text never reaches the model
  • It makes retrieval faster
  • The model cannot read metadata
  • Regulations require it to be done in SQL

The model is not a security boundary.

A support assistant answers simple lookups and, occasionally, hard multi-step diagnoses. Where does a reasoning model belong in the design?

  • Everywhere, because it is more accurate
  • Nowhere, because reasoning models are only for maths
  • Behind a router that sends only the hard cases to it with a thinking budget, since it adds latency and cost that lookups do not need
  • As the retrieval component

Reasoning effort is a lever to spend where multi-step correctness matters, not a default.

A new model is released that claims large benchmark gains. What should your team do?

  • Switch immediately
  • Ignore it until competitors adopt it
  • Run your own eval set against it, compare quality with a confidence interval plus cost and latency, and switch if it wins on your workload
  • Fine-tune it before testing

Your evals turn hype into a quick, evidence-based decision.

Key takeaways

  • Design in order: problem and success criteria, data and evaluation, the simplest adequate approach, architecture, risks, operations, iteration plan.
  • Climb the ladder from rules to classical ML to prompted LLMs to retrieval, workflows, agents and fine-tuning only as far as evidence requires; reach for search, RL, vision, forecasting and recommenders when the problem is not language.
  • Reasoning effort, context engineering, caching, post-training and inference optimisation are levers with costs; pull two or three, not all of them.
  • Combine tools by strength: classical methods for numbers and detection, LLMs for language, synthesis and interaction.
  • Read papers in passes, prefer primary sources, try things on your own evals, and invest in the durable fundamentals.
