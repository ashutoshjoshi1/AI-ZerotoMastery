Why evaluation is the core skill

Traditional software is mostly deterministic: write a unit test, it passes or fails forever. LLM systems are probabilistic, sensitive to wording, and change underneath you when providers update models. Without measurement, every prompt tweak, model swap and chunking change is a guess, and teams end up shipping regressions they never notice.

Experienced AI engineers spend a large share of their time on evaluation, and the best ones start building evals before they build the system. An evaluation set turns arguments ("I think the new prompt is better") into evidence ("it fixes 9 cases and breaks 2, here they are"). It is also what lets you adopt a new, cheaper model with confidence on the day it is released.

Kinds of evaluation

Kind Question it answers When
Unit-style checks Does output satisfy hard rules (valid JSON, required fields, no banned content, length)? Every change, in CI
Offline dataset evals How well does the system do on representative cases with known good answers? Every prompt, model or pipeline change
Component evals Is each stage working (retrieval recall, classifier accuracy, tool-call correctness)? When diagnosing
Trajectory evals Did an agent take sensible steps and leave the world in the right state? Agents and multi-turn systems
Human review Do experts judge the outputs useful, correct and appropriate? Calibrating automated graders; high-stakes launches
Online evaluation How does it behave with real users (feedback, task completion, escalations)? Continuously in production
Red teaming Can it be made to fail badly or be misused? Before launch and periodically (lesson )

Building a golden dataset

A golden dataset (or eval set) is a collection of inputs, ideally with reference outputs or grading criteria, that represents what the system must handle.

Where cases come from:

  • Real usage is best: logged questions, support tickets, documents users uploaded (with appropriate privacy handling).
  • Experts write cases for important or rare situations that real logs do not yet contain.
  • Synthetic generation: an LLM drafts variations, edge cases and adversarial inputs. Always review them; synthetic cases tend to be cleaner and easier than reality.
  • Failures: every bug report and every production failure becomes a new test case. Over time this is the most valuable part of the set.

What good sets contain:

  • The common cases, in roughly their real proportions.
  • Hard and ambiguous cases, deliberately over-represented, since that is where systems differ.
  • Negative cases: questions that should be refused, answered with "I don't know", or escalated.
  • Slices labelled by type (language, product, difficulty) so you can see where a change helps or hurts.

How big? Start with 20 to 50 cases on day one; a small set used daily beats a perfect set that never exists. Grow towards a few hundred. As the statistics section shows, you need hundreds before small differences become detectable.

Graders

A grader turns an output into a score. Use the cheapest grader that measures what matters.

Code-based graders

Fast, free, deterministic. Use them for everything you can express as a rule.

import json, re
from pydantic import BaseModel, ValidationError

def exact_match(output: str, expected: str) -> float:
    return float(output.strip().lower() == expected.strip().lower())

def contains_all(output: str, required: list[str]) -> float:
    return sum(r.lower() in output.lower() for r in required) / len(required)

def numeric_close(output: str, expected: float, rel_tol: float = 0.01) -> float:
    nums = [float(x) for x in re.findall(r"-?\d+(?:\.\d+)?", output)]
    return float(any(abs(n - expected) <= rel_tol * abs(expected) for n in nums))

def valid_schema(output: str, model: type[BaseModel]) -> float:
    try:
        model.model_validate_json(output)
        return 1.0
    except ValidationError:
        return 0.0

def cites_only_given_sources(output: str, n_sources: int) -> float:
    cited = {int(c) for c in re.findall(r"\[(\d+)\]", output)}
    return float(bool(cited) and all(1 <= c <= n_sources for c in cited))

Reference-based text metrics

Classic metrics such as BLEU and ROUGE count word overlap with a reference answer. They are cheap but correlate poorly with quality for open-ended generation: a correct answer phrased differently scores low. Embedding similarity to the reference is somewhat better. For most LLM applications, a well-designed LLM judge beats both.

LLM-as-judge

A capable model grades outputs against a rubric. It scales human-like judgement to thousands of cases, but judges have known biases: they favour longer answers, answers in the first position in pairwise comparisons, and outputs that resemble their own style. They can also be confidently wrong on facts they do not know. Good practice:

  • Grade one specific criterion at a time ("Is every claim supported by the sources?"), not "rate quality 1 to 10".
  • Prefer binary or small categorical scales with explicit definitions over fine-grained numbers.
  • Give the judge what it needs: the sources, the reference answer, the rubric.
  • Ask for reasoning before the verdict, in a structured format your code can parse.
  • For pairwise comparisons, run both orders and count only consistent wins.
  • Calibrate against humans: have people grade 50 to 100 cases, measure agreement with the judge, and refine the rubric until agreement is high. An uncalibrated judge is a random number generator with good manners.
import anthropic
from typing import Literal
from pydantic import BaseModel

client = anthropic.Anthropic()
JUDGE_MODEL = "claude-sonnet-5-5"

class FaithfulnessVerdict(BaseModel):
    unsupported_claims: list[str]          # the evidence comes first, then the verdict
    verdict: Literal["PASS", "FAIL"]

FAITHFULNESS_RUBRIC = """You are grading whether an answer is fully supported by source documents.

<sources>
{sources}
</sources>

<answer>
{answer}
</answer>

Go through the answer claim by claim. A claim is SUPPORTED if the sources state it or it follows
directly from them. Ignore style and completeness; judge only support.
List every unsupported claim, then give the verdict. PASS means there are no unsupported factual claims."""

def judge_faithfulness(answer: str, sources: str) -> dict:
    r = client.messages.parse(
        model=JUDGE_MODEL, max_tokens=1000,
        messages=[{"role": "user", "content": FAITHFULNESS_RUBRIC.format(sources=sources, answer=answer)}],
        output_format=FaithfulnessVerdict,       # structured output: the reply is validated JSON
    )
    return r.parsed_output.model_dump()

Structured output (lesson ) guarantees that the reply matches the schema, so there is nothing to parse by hand and no half-finished JSON to debug. Putting unsupported_claims before verdict in the schema makes the judge list its evidence before it decides. Judges are not deterministic: the model this course uses does not accept a temperature setting, and even at temperature 0 providers do not promise identical outputs. For borderline cases, run the judge two or three times and treat disagreement as a signal to read the case yourself.

Grading agents and multi-turn systems

An agent (lesson ) produces a trajectory, not just a string: a sequence of tool calls, their results and a final state of the world. Grading only the final message misses most of what can go wrong. Three kinds of check:

  • Final-state checks: did the ticket get created, the file change, the right record update? Inspect the environment after the run, not the model's claim about it.
  • Trajectory checks: were the right tools called with sensible arguments, in a reasonable number of steps, without forbidden actions? Code graders over the logged tool calls handle most of this.
  • Rubric judgements for what code cannot check: did it ask for confirmation before the consequential action, did it explain what it did?

Multi-turn conversations need the whole dialogue in the eval case. Two practical patterns: replay a logged conversation up to turn \(k\) and grade only the next reply, or let a second model play a scripted user with a goal and grade the outcome and the number of turns it took. Simulated users are cheap but tidier than real ones, so keep some real transcripts in the set.

Agents are stochastic and run many steps, so run each case several times. Report both pass@k (did any of \(k\) runs succeed; lesson ) and the stricter rate at which all \(k\) runs succeed. The second is what a user who runs the agent once will experience, and it falls fast: a step that works 80% of the time gives a 33% success rate over five mandatory steps.

Hands-on: calibrate a grader against human labels

The notebook has 18 short answers to questions about an instrument manual, each with the source text it should be grounded in and a human PASS or FAIL label for faithfulness.

  1. Write a cheap heuristic grader: an answer FAILS if it contains a number that does not appear in the sources, or a sentence that shares no content word with the sources.
  2. Measure agreement with the human labels: raw accuracy and Cohen's kappa, which corrects for the agreement you would get by chance.
  3. Print the disagreements and classify each one: a grader miss, a grader false alarm, or a human label you now disagree with.
  4. If you have an API key, run judge_faithfulness on the same 18 cases and compute its kappa too.

You are done when you have a kappa for the heuristic grader and a list of disagreements with a reason for each. Expect the heuristic to reach moderate agreement at best; its misses show what only a judge, or a human, can see.

Show a solution 
import re

STOP = {"the", "and", "that", "with", "from", "this", "after", "every", "must", "have",
        "should", "which", "when", "then", "than", "into", "over", "only", "also"}

def content_words(text):
    return {w for w in re.findall(r"[a-z]+", text.lower()) if len(w) >= 4 and w not in STOP}

def heuristic_judge(answer, sources):
    src_nums = set(re.findall(r"\d[\d,.]*", sources))
    if any(n not in src_nums for n in re.findall(r"\d[\d,.]*", answer)):
        return "FAIL"                                      # a number the sources never mention
    src_words = content_words(sources)
    for sentence in re.split(r"(?<=[.!?])\s+", answer):
        if sentence.strip() and not content_words(sentence) & src_words:
            return "FAIL"                                  # a sentence about something else
    return "PASS"

def cohens_kappa(a, b):
    n, labels = len(a), sorted(set(a) | set(b))
    po = sum(x == y for x, y in zip(a, b)) / n
    pe = sum((a.count(l) / n) * (b.count(l) / n) for l in labels)
    return (po - pe) / (1 - pe) if pe < 1 else 1.0

human = [label for _, _, label in CALIBRATION_SET]
heur = [heuristic_judge(ans, src) for src, ans, _ in CALIBRATION_SET]
print(f"accuracy {sum(h == g for h, g in zip(human, heur)) / len(human):.2f}  kappa {cohens_kappa(human, heur):.2f}")
for (src, ans, label), g in zip(CALIBRATION_SET, heur):
    if g != label:
        kind = "miss" if label == "FAIL" else "false alarm"
        print(f"{kind:<11} human={label} grader={g}: {ans}")

The heuristic reaches a kappa of about 0.6: three misses and one false alarm out of 18. The misses are answers made entirely of words that do appear in the sources but combined into a claim the sources do not make ("all firmware versions", "clean with acetone", "day and night"); no overlap statistic can catch those. The false alarm is a correct paraphrase ("1-minute intervals" for "every 60 seconds"). Those four cases are exactly what you want in the calibration set when you move to an LLM judge: if it gets them right you have gained something real, and if it does not, the rubric needs an explicit line about paraphrase and about claims that generalise beyond the source.

An evaluation harness

Put it together: run every case through a system variant, grade it, save everything, and summarise by slice.

import json, time
from collections import defaultdict
from concurrent.futures import ThreadPoolExecutor

def run_eval(system_fn, cases, graders, name, workers=8):
    """system_fn(input) -> output string; graders: {metric: fn(case, output) -> float in [0, 1]}"""
    def run_one(case):
        t0 = time.perf_counter()
        try:
            output, error = system_fn(case["input"]), None
        except Exception as e:
            output, error = "", repr(e)
        latency = time.perf_counter() - t0
        scores = {m: (g(case, output) if error is None else 0.0) for m, g in graders.items()}
        return {"id": case["id"], "tags": case.get("tags", []), "output": output,
                "error": error, "latency": latency, "scores": scores}

    with ThreadPoolExecutor(workers) as pool:
        results = list(pool.map(run_one, cases))

    with open(f"results_{name}.jsonl", "w") as f:              # keep every output: you will want to read them
        for r in results:
            f.write(json.dumps(r) + "\n")

    summary = defaultdict(list)
    for r in results:
        for m, s in r["scores"].items():
            summary[(m, "ALL")].append(s)
            for tag in r["tags"]:
                summary[(m, tag)].append(s)
    for (m, tag), vals in sorted(summary.items()):
        print(f"{name:<12} {m:<14} {tag:<14} {sum(vals) / len(vals):.3f}  (n={len(vals)})")
    return results

Then read the diffs: which cases did the new version fix, and which did it break? The aggregate number tells you whether to look; the individual cases tell you what is going on.

Is the difference real?

With small eval sets, random variation is large. An accuracy of \(p\) measured on \(n\) cases has a 95% margin of error of roughly \(1.96\sqrt{p(1-p)/n}\):

Cases Margin of error at 80% accuracy
20 ± 17.5 points
100 ± 7.8 points
400 ± 3.9 points
1,000 ± 2.5 points

So "75% versus 80% on 100 cases" is not, on its own, evidence of improvement. Two tools help.

Bootstrap confidence intervals resample your per-case scores to estimate uncertainty without formulas:

import numpy as np

def bootstrap_ci(scores, n_boot=10_000, alpha=0.05, seed=0):
    rng = np.random.default_rng(seed)
    scores = np.asarray(scores, dtype=float)
    means = rng.choice(scores, size=(n_boot, len(scores)), replace=True).mean(axis=1)
    return scores.mean(), np.quantile(means, alpha / 2), np.quantile(means, 1 - alpha / 2)

Paired comparison: both systems ran on the same cases, so compare them case by case. Most cases are answered the same way by both; what matters is the cases that changed. A paired bootstrap on per-case differences is much more sensitive than comparing two independent intervals:

def paired_bootstrap(a, b, n_boot=10_000, seed=0):
    """Mean improvement of b over a, and the fraction of resamples where b is not better."""
    rng = np.random.default_rng(seed)
    d = np.asarray(b, float) - np.asarray(a, float)
    diffs = d[rng.integers(0, len(d), size=(n_boot, len(d)))].mean(axis=1)
    return d.mean(), (diffs <= 0).mean()

In a simulation with 100 cases where the new version fixes 5 cases and breaks none, accuracy goes from 75% to 80%. The two separate confidence intervals overlap heavily, yet the paired test gives a "not better" fraction of about 0.005: strong evidence the change helped. If instead the new version fixed 9 cases and broke 4, the same 5-point gain would be far less certain. Always look at fixes and breaks, not just the averages.

Also remember that model outputs vary between runs. For important decisions, run each variant two or three times and check the result is stable.

Hands-on: how many cases do you need?

  1. Simulate a baseline that is right on 75% of cases and a candidate that fixes 5% of all cases and breaks none. For \(n\) of 50, 100, 200, 400 and 800 cases, draw 100 random eval sets and run paired_bootstrap on each (2,000 resamples is enough here).
  2. Count how often the "not better" fraction falls below 0.05. That is the chance your eval set detects a real 5-point improvement.
  3. Repeat for a candidate that fixes 9% and breaks 4%, the same net gain, and print both tables.

You are done when the two tables print. Notice how many cases the noisier 5-point gain needs before you can trust it.

Show a solution 
def detection_rate(n, p_base=0.75, fix=0.05, brk=0.0, sims=100):
    rng = np.random.default_rng(n)
    detected = 0
    for s in range(sims):
        base = rng.random(n) < p_base                                    # which cases the baseline gets right
        cand = base.copy()
        cand[~base] = rng.random((~base).sum()) < fix / (1 - p_base)    # some wrong cases get fixed
        cand[base] = rng.random(base.sum()) >= brk / p_base              # some right cases get broken
        _, not_better = paired_bootstrap(base.astype(float), cand.astype(float), n_boot=2000, seed=s)
        detected += not_better < 0.05
    return detected / sims

for fix, brk in [(0.05, 0.0), (0.09, 0.04)]:
    print(f"candidate fixes {fix:.0%} of cases and breaks {brk:.0%}")
    for n in [50, 100, 200, 400, 800]:
        print(f"   n = {n:<4} detected in {detection_rate(n, fix=fix, brk=brk):.0%} of eval sets")

With fixes only, 100 cases already detect the gain most of the time, because every changed case points the same way. With 9 fixed and 4 broken the detection rate at 100 cases drops sharply and you need several hundred cases for the same confidence, even though the average moved by the same 5 points. The paired test is only as strong as the consistency of the changes, which is why reading the fixed and broken cases matters more than the headline number.

Regression testing and CI

Treat the eval suite like a test suite:

  • Fast checks on every commit: schema validity, a small smoke set of 20 to 50 cases, safety cases. Fail the build on hard-rule violations.
  • Full evaluation before merging prompt or model changes, with the report attached to the review.
  • Thresholds per slice, not just overall: "unanswerable questions must stay above 95% abstention" protects behaviour that a global average would hide.
  • Pin everything: model version, prompt version, retrieval index version, so a result can be reproduced.
  • Re-run on provider model updates before switching.

Tools such as promptfoo, Inspect, DeepEval, or the evaluation features in observability platforms (lesson ) package much of this. A short Python harness like the one above is a perfectly good start.

Public benchmarks and their limits

Model releases quote benchmarks: MMLU and its harder variants for broad knowledge, GPQA for graduate-level science, SWE-bench for real software engineering tasks, coding and maths competition sets, and human-preference leaderboards such as LMArena. They are useful for shortlisting models. They are not a substitute for your own evals, because:

  • Contamination: benchmark questions leak onto the web and into training data, inflating scores.
  • Saturation: once top models score above 90%, the benchmark stops discriminating.
  • Mismatch: your task, data, format and failure costs are not the benchmark's.
  • Optimisation pressure: anything that becomes a target gets gamed, deliberately or not.

The model that wins a leaderboard is often not the best one for your specific workload at your price and latency. Your eval set decides.

Contamination in your own evals

Contamination is not only a benchmark problem. Your own eval cases leak in three common ways: an eval question gets pasted into the few-shot examples of the prompt; eval cases are used as fine-tuning data, or generated by the same script and seed that produced the training data (lesson ); or a retrieval index is tuned on the eval questions until every one of them hits. In each case the score stops measuring generalisation.

Keep eval cases out of prompts and training sets by construction: store them separately, never let a training script read the eval file, and before every fine-tune check for near-duplicates between the two sets (shared word sequences of 8 to 13 words are the usual test). Lesson covers decontamination in depth.

Online evaluation

Offline sets go stale as users and the world change. In production, also measure:

  • Explicit feedback: thumbs up or down, corrections, ratings (sparse and biased towards strong feelings, but valuable).
  • Implicit signals: did the user retry, rephrase, copy the answer, escalate to a human, complete the task?
  • Sampled review: experts grade a random sample of live traffic weekly, with LLM judges extending coverage.
  • A/B tests for significant changes, measuring the outcome the product exists for.
  • Drift monitoring: shifts in input topics, lengths, languages or refusal rates (lesson ).

Then feed what you learn back into the offline eval set. That loop, production to dataset to improvement to production, is how AI products get better rather than just older.

Output-level evals tell you what the model did, not why. Lesson shows attribution and probing techniques that can explain a verdict or flag a problem inside the model before it reaches the output; treat them as a complement to evals, not a replacement.

cases = [json.loads(l) for l in open("eval_cases.jsonl")]

def rag_system(question):                      # return a JSON string so graders can see sources too
    hits = rag.retrieve(question)
    ans = rag.answer(question)["answer"]
    return json.dumps({"answer": ans, "ids": [h["id"] for h in hits],
                       "sources": format_sources(hits)})

def retrieval_hit(case, out):
    if "gold_chunk" not in case:
        return 1.0
    return float(case["gold_chunk"] in json.loads(out)["ids"])

def abstains(case, out):
    if case.get("reference") != "NOT_IN_DOCS":
        return 1.0
    text = json.loads(out)["answer"].lower()
    return float(any(p in text for p in ["not in the", "do not contain", "doesn't contain", "no information"]))

def faithful(case, out):
    o = json.loads(out)
    return float(judge_faithfulness(o["answer"], o["sources"])["verdict"] == "PASS")

a = run_eval(rag_system, cases, graders, "with_rerank")
# ... switch the reranker off, then:
b = run_eval(rag_system_no_rerank, cases, graders, "no_rerank")
sa = [r["scores"]["retrieval_hit"] for r in a]
sb = [r["scores"]["retrieval_hit"] for r in b]
print(paired_bootstrap(sb, sa))
fixed = [x["id"] for x, y in zip(a, b) if x["scores"]["retrieval_hit"] > y["scores"]["retrieval_hit"]]
broken = [x["id"] for x, y in zip(a, b) if x["scores"]["retrieval_hit"] < y["scores"]["retrieval_hit"]]
print("fixed:", fixed, "broken:", broken)

The keyword-based abstention grader is crude and will miss some phrasings; that is fine for a start, and the misses you find when reading outputs tell you how to improve it (or to replace it with a judge). Judge calibration usually needs two or three rubric revisions; the typical early problem is the judge treating reasonable paraphrases as unsupported, or letting general-knowledge claims through.

Check yourself

When should you start building an evaluation set for an LLM feature?

  • Before or alongside building the feature, starting small
  • After launch, once users complain
  • Only once you have 1,000 examples
  • Never; public benchmarks cover it

A small set used from day one guides every decision and grows over time.

Which is the best way to use an LLM as a judge?

  • Ask it to rate overall quality from 1 to 10
  • Grade one specific criterion with a clear rubric and the needed context, and calibrate it against human grades
  • Use the same model that generated the answer, at high temperature
  • Always show it the candidate answers in the same order

Specific criteria, structured verdicts, order-swapping for pairwise, and calibration against humans.

Version B scores 80% and version A 75% on the same 100 cases. What should you do before concluding B is better?

  • Nothing; 5 points is a clear win
  • Look at which cases were fixed and broken, and run a paired comparison
  • Increase the temperature and rerun
  • Switch to a public benchmark

On 100 cases the margin of error is around ±8 points. Paired analysis of fixes and breaks is far more informative.

An agent must complete five tool calls in a row, and each one succeeds 80% of the time. What should your eval report?

  • Only the quality of the final message
  • Final-state and trajectory checks over several runs, including the rate at which every run succeeds, which is about 33% here
  • The average length of the conversation
  • A single run, since agents are deterministic

Multiply the per-step success rates: 0.8 to the power 5 is about 0.33. One run tells you little, and the final message may claim success that never happened.

A production failure is reported. What should happen to it?

  • Fix the prompt and move on
  • Add it to the evaluation set as a test case, then fix it and confirm the fix without breaking others
  • Ignore it unless it happens three times
  • Retrain the model

Every failure becomes a regression test. That is how the eval set becomes valuable.

Key takeaways

  • Evaluation is the core discipline of AI engineering: it turns opinions into evidence and makes model upgrades safe.
  • Build a golden dataset early from real usage, expert cases, reviewed synthetic cases and every failure; include hard, ambiguous and negative cases, tagged by slice.
  • Use code graders wherever possible; use LLM judges with specific rubrics, structured output, order-swapping and human calibration.
  • Grade agents on final state and trajectory over several runs, and grade conversations with replayed or simulated turns.
  • Small sets are noisy. Use bootstrap intervals and paired comparisons, and always read the fixed and broken cases.
  • Run evals in CI with per-slice thresholds and pinned versions; keep eval cases out of prompts and training data; treat public benchmarks as a shortlist; close the loop with online evaluation.
