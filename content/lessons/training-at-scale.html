The idea in one paragraph

Your TinyGPT from lesson fitted on one device. A frontier model has hundreds of billions of parameters, trillions of tokens (lesson ) and thousands of accelerators. At that scale speed is limited by moving data rather than arithmetic, the training state must be split across many devices, and architectures such as FlashAttention, mixture of experts and state-space layers exist largely to make both cheaper. Everything here runs on a laptop CPU.

How an accelerator spends its time

A GPU (like a TPU) is thousands of simple cores with dedicated matrix-multiply units, fed by memories that get bigger and slower further from the cores.

LevelHoldsSpeed (illustrative)
RegistersNumbers being worked on nowFastest
On-chip SRAM, tens of MBTiles of matrices in useRoughly ten times HBM
HBM, about 80 GB or moreWeights, gradients, optimiser state, activationsA few TB/s
Other GPUs in the server (NVLink)Other parts of the modelHundreds of GB/s
Other servers (network)The rest of the clusterTens of GB/s per GPU

The matrix units manage hundreds of teraFLOP/s to a few petaFLOP/s in 16-bit precision. Figures change every generation, but arithmetic has long grown faster than bandwidth: arithmetic is cheap, moving bytes is expensive.

Arithmetic intensity and the roofline

So ask how much work an operation does per byte it moves: its arithmetic intensity \(I\), in FLOPs per byte. Adding two float32 vectors of length \(n\) does \(n\) FLOPs on \(12n\) bytes, \(I = 1/12\). Multiplying two \(n \times n\) matrices does \(2n^3\) FLOPs on \(12n^2\) bytes, \(I = n/6\), growing with size. The roofline model says neither limit can be beaten:

\[ \text{attainable FLOP/s} = \min\left(\text{peak FLOP/s},\; I \times \text{memory bandwidth}\right) \]

The limits cross at the ridge point, peak divided by bandwidth: about 330 FLOPs per byte for an illustrative accelerator with 1,000 TFLOP/s and 3 TB/s. Left of it an operation is memory-bound, right of it compute-bound.

Measure both regimes on your own machine:

import time
import torch

def bench(fn, repeats=10):
    """Best of several timed runs, in seconds (the best is the least noisy)."""
    fn()                                          # warm-up run
    times = []
    for _ in range(repeats):
        start = time.perf_counter()
        fn()
        times.append(time.perf_counter() - start)
    return min(times)

torch.manual_seed(0)
results = []                                      # (name, FLOP/byte, GFLOP/s, GB/s)
for n in [64, 256, 1024, 2048]:
    a, b, c = torch.randn(n, n), torch.randn(n, n), torch.empty(n, n)
    t = bench(lambda: torch.matmul(a, b, out=c))
    flops, nbytes = 2 * n**3, 3 * n * n * 4       # read a and b, write c (fp32)
    results.append((f"matmul {n}", flops / nbytes, flops / t / 1e9,
                    nbytes / t / 1e9))

x, y, z = torch.randn(2**24), torch.randn(2**24), torch.empty(2**24)
t = bench(lambda: torch.add(x, y, out=z))         # 16.8 million additions
flops, nbytes = x.numel(), 3 * x.numel() * 4      # read x and y, write z
results.append(("add", flops / nbytes, flops / t / 1e9, nbytes / t / 1e9))

print(f"{'operation':<13}{'FLOP/byte':>10}{'GFLOP/s':>10}{'GB/s':>8}")
for name, intensity, gflops, gbs in results:
    print(f"{name:<13}{intensity:10.2f}{gflops:10.1f}{gbs:8.1f}")

The addition reaches about 1% of the large matmuls' FLOP/s but moves data over ten times faster: bandwidth sets its speed. The large matmuls approach peak. Their GFLOP/s over the addition's GB/s puts this CPU's ridge point near 10; GPUs sit far to the right. The smallest matmul pays fixed per-call overhead, as GPU kernel launches do.

Two lessons follow. Chains of element-wise operations (bias, GELU, dropout) each reread the tensor; kernel fusion, which torch.compile does for you, makes one pass. And a linear layer's intensity is roughly the number of tokens it processes at once (see the exercise), which is why inference engines batch users together (lesson ).

Number formats and mixed precision

A float spends bits on a sign, an exponent (range) and a mantissa (precision). Fewer bits mean less memory and faster matrix units:

bf16 keeps float32's exponent, so its range, but has only 7 mantissa bits: neighbouring numbers near 1 are 0.008 apart. fp16 is more precise but overflows above 65,504 and loses normal numbers below \(6 \times 10^{-5}\). The 8-bit formats trade the two: E4M3 for weights and activations, E5M2 for gradients. Low precision fails in two ways:

w16 = torch.tensor(1.0, dtype=torch.bfloat16)
for _ in range(1000):
    w32 += 1e-4               # a small update, like learning rate x gradient
    w16 += 1e-4
print(w32.item(), w16.item())

grads = torch.tensor([1e-3, 1e-6, 1e-8])
print(grads.half())                         # fp16: the smallest underflows to 0
print(grads.bfloat16())                     # bf16: fine range, coarse precision
scale = 2.0 ** 16                           # loss scaling: scale up first...
print((grads * scale).half().float() / scale)   # ...unscale in fp32: no loss
1.1000165939331055 1.0
tensor([1.0004e-03, 1.0133e-06, 0.0000e+00], dtype=torch.float16)
tensor([9.9945e-04, 9.9838e-07, 1.0012e-08], dtype=torch.bfloat16)
tensor([1.0004e-03, 1.0002e-06, 9.9972e-09])

First, lost updates: adding \(10^{-4}\) to 1.0 in bf16 rounds back to 1.0 every time, so mixed-precision training keeps a float32 master copy of the weights for the optimiser and computes with bf16 copies. Second, underflow: in fp16 a gradient of \(10^{-8}\) becomes zero. Loss scaling multiplies the loss before the backward pass and divides it out in float32; torch.amp.GradScaler picks the factor and skips steps that overflow. bf16 needs none, one reason it is the default (lesson used torch.autocast). Sums of products, softmax, normalisation and the loss stay in float32.

The memory budget of training

Training holds weights, gradients, optimiser state and the activations saved for the backward pass. Mixed-precision Adam costs 16 bytes per parameter (lesson ): 2 for bf16 weights, 2 for gradients, 12 for float32 master weights and Adam's two moments. Activations take about 34 bytes per token per unit of width per layer, a common estimate (Korthikanti et al., 2022) for 16-bit activations and fused attention.

def training_memory_gb(n_params, n_layers, d_model, seq_len, micro_batch,
                       checkpointing=False):
    """Rough memory to train on ONE device with mixed-precision Adam."""
    states = 16 * n_params   # bf16 weights 2 + bf16 grads 2 + fp32 master, Adam 12
    tokens = seq_len * micro_batch
    if checkpointing:   # keep each layer's bf16 input, rebuild one layer at a time
        acts = (2 * n_layers + 34) * tokens * d_model
    else:               # about 34 bytes per token per unit of width, in every layer
        acts = 34 * n_layers * tokens * d_model
    return states / 1e9, acts / 1e9

models = {"1B": (1e9, 16, 2048), "7B": (7e9, 32, 4096), "70B": (70e9, 80, 8192)}
print(f"{'model':<6}{'states GB':>10}{'activations GB':>16}{'checkpointed GB':>17}")
for name, (n, layers, d) in models.items():
    states, acts = training_memory_gb(n, layers, d, seq_len=4096, micro_batch=1)
    _, acts_ckpt = training_memory_gb(n, layers, d, 4096, 1, checkpointing=True)
    print(f"{name:<6}{states:10.0f}{acts:16.1f}{acts_ckpt:17.1f}")

Activation checkpointing

Gradient checkpointing keeps only each layer's input in the forward pass and reruns the layer during the backward pass to rebuild its internals. That costs one extra forward pass, about a third more compute.

import torch.nn as nn
from torch.utils.checkpoint import checkpoint

class MLPStack(nn.Module):
    def __init__(self, d=256, n_layers=8, use_checkpoint=False):
        super().__init__()
        self.layers = nn.ModuleList(
            nn.Sequential(nn.Linear(d, 4 * d), nn.GELU(), nn.Linear(4 * d, d))
            for _ in range(n_layers))
        self.use_checkpoint = use_checkpoint

    def forward(self, x):
        for layer in self.layers:
            if self.use_checkpoint:   # drop the insides, recompute in backward
                x = x + checkpoint(layer, x, use_reentrant=False)
            else:
                x = x + layer(x)
        return x

def backward_and_measure(model, x):
    """Run forward and backward; return gradients and MB saved for backward."""
    saved = 0
    def pack(t):
        nonlocal saved
        if not isinstance(t, nn.Parameter):       # count activations, not weights
            saved += t.numel() * t.element_size()
        return t
    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        loss = model(x).pow(2).mean()
    loss.backward()
    return [p.grad for p in model.parameters()], saved / 1e6

torch.manual_seed(0)
x = torch.randn(512, 256)
plain = MLPStack()
ckpt = MLPStack(use_checkpoint=True)
ckpt.load_state_dict(plain.state_dict())          # identical weights
g1, mb1 = backward_and_measure(plain, x)
g2, mb2 = backward_and_measure(ckpt, x)
print(f"saved for backward: {mb1:.1f} MB plain, {mb2:.1f} MB checkpointed")
print("identical gradients:", all(torch.equal(a, b) for a, b in zip(g1, g2)))
saved for backward: 54.0 MB plain, 4.7 MB checkpointed
identical gradients: True

Gradients are bit-identical because the same operations rerun (PyTorch restores the random state for dropout). Large runs often checkpoint selectively: only what is cheap to redo but costly to store.

Gradient accumulation

Pretraining batches hold millions of tokens. Gradient accumulation runs several micro-batches, lets gradients add up in .grad, and steps once. Divide each loss by the number of micro-batches:

import copy
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, 1))
X, y = torch.randn(256, 20), torch.randn(256, 1)
loss_fn = nn.MSELoss()                            # a mean over the batch

model.zero_grad()
loss_fn(model(X), y).backward()                   # one batch of 256
full = [p.grad.clone() for p in model.parameters()]

model.zero_grad()
steps = 4
for Xm, ym in zip(X.chunk(steps), y.chunk(steps)):    # four micro-batches of 64
    (loss_fn(model(Xm), ym) / steps).backward()       # .grad keeps adding up
accum = [p.grad.clone() for p in model.parameters()]
print("max difference:",
      max((a - b).abs().max().item() for a, b in zip(full, accum)))
max difference: 1.043081283569336e-07

The difference is rounding. Common mistakes: forgetting the division, which scales the learning rate, and averaging per-sequence losses over unequal lengths; divide summed token losses by the total token count.

Data parallelism

In data parallelism every GPU holds the whole model and a different slice of the batch; an all-reduce averages their gradients so every replica takes the same step. Simulate four workers:

n_workers = 4
workers = [copy.deepcopy(model) for _ in range(n_workers)]   # a full replica each
for w, Xs, ys in zip(workers, X.chunk(n_workers), y.chunk(n_workers)):
    w.zero_grad()
    loss_fn(w(Xs), ys).backward()    # each worker sees only its shard of the batch

# all-reduce: every worker ends up with the average of all workers' gradients
for params in zip(*(w.parameters() for w in workers)):
    avg = torch.stack([p.grad for p in params]).mean(dim=0)
    for p in params:
        p.grad = avg.clone()

dp = [p.grad for p in workers[0].parameters()]
print("max difference from full batch:",
      max((a - b).abs().max().item() for a, b in zip(full, dp)))
max difference from full batch: 1.043081283569336e-07

Equal up to rounding. This relies on equal shards and a mean loss; batch norm, note, sees only each worker's shard.

How an all-reduce works

Funnelling gradients through one GPU makes its link the bottleneck. A ring splits each gradient into \(N\) chunks passed between neighbours: \(N-1\) steps of reduce-scatter sum each chunk on its way round, then \(N-1\) steps of all-gather share the results.

import numpy as np

def ring_all_reduce(arrays):
    """Sum equal-length arrays held by n workers by passing chunks round a ring."""
    n = len(arrays)
    chunks = [np.array_split(a.astype(float), n) for a in arrays]
    sent = 0
    # 1. reduce-scatter: after n-1 steps, worker i owns the total of chunk (i+1) % n
    for step in range(n - 1):
        msgs = [(i, (i - step) % n) for i in range(n)]
        data = [chunks[i][c].copy() for i, c in msgs]   # everyone sends at once
        for (i, c), d in zip(msgs, data):
            chunks[(i + 1) % n][c] += d                 # the neighbour adds it in
            sent += d.size
    # 2. all-gather: pass each finished chunk round the ring
    for step in range(n - 1):
        msgs = [(i, (i + 1 - step) % n) for i in range(n)]
        data = [chunks[i][c].copy() for i, c in msgs]
        for (i, c), d in zip(msgs, data):
            chunks[(i + 1) % n][c] = d                  # the neighbour copies it
            sent += d.size
    return [np.concatenate(c) for c in chunks], sent / n    # values sent per worker

rng = np.random.default_rng(0)
size = 120_000                                    # gradient values per worker
for n in [2, 4, 8, 64]:
    grads = [rng.normal(size=size) for _ in range(n)]
    total = np.sum(grads, axis=0)
    result, per_worker = ring_all_reduce(grads)
    ok = all(np.allclose(r, total) for r in result)
    print(f"{n:>3} workers: correct={ok}, "
          f"each sends {per_worker / size:.2f} x its gradient")

Each worker sends about twice its gradient whatever the worker count, so time depends on gradient size and link speed. PyTorch's DistributedDataParallel (DDP) also all-reduces buckets of gradients while the backward pass is still running.

ZeRO and FSDP: stop storing everything N times

Data parallelism stores all 16 bytes per parameter on every GPU. ZeRO (Rajbhandari et al., 2020) shards them: stage 1 the optimiser state, stage 2 also the gradients (via reduce-scatter), stage 3 also the weights, all-gathering each layer just before it runs. PyTorch's FSDP (fully_shard in FSDP2) is stage 3; DeepSpeed implements all three.

def zero_memory_gb(n_params, n_gpus, stage):
    """Training-state memory per GPU (bf16 weights and grads, fp32 Adam)."""
    weights, grads, optim = 2 * n_params, 2 * n_params, 12 * n_params
    if stage >= 1: optim /= n_gpus       # ZeRO-1: shard the optimiser state
    if stage >= 2: grads /= n_gpus       # ZeRO-2: ...and the gradients
    if stage >= 3: weights /= n_gpus     # ZeRO-3 (FSDP): ...and the weights too
    return (weights + grads + optim) / 1e9

Model parallelism: splitting the model itself

Tensor parallelism

Tensor parallelism splits each layer's matrices across GPUs. The Megatron-LM layout needs one all-reduce per MLP: split the first matrix by columns, so each GPU applies GELU to its own hidden units, and the second by rows, giving partial sums.

import torch.nn.functional as F
torch.manual_seed(0)
tokens, d, d_ff, n_gpus = 6, 16, 64, 4
X = torch.randn(tokens, d)
A, B = torch.randn(d, d_ff), torch.randn(d_ff, d)    # the MLP's two weight matrices
full = F.gelu(X @ A) @ B                             # one device does it all

A_parts = A.chunk(n_gpus, dim=1)    # column split: each GPU gets d_ff/4 hidden units
B_parts = B.chunk(n_gpus, dim=0)     # row split: the matching rows of B
partial = [F.gelu(X @ a) @ b for a, b in zip(A_parts, B_parts)]  # no talking needed
out = torch.stack(partial).sum(dim=0)                # one all-reduce at the end
print("column-then-row split matches:", torch.allclose(out, full, atol=1e-4))

# Splitting A by rows instead gives partial sums of X @ A, and GELU of a partial
# sum is not part of the answer: you would need an all-reduce before the GELU.
X_parts, A_rows = X.chunk(n_gpus, dim=1), A.chunk(n_gpus, dim=0)
wrong = sum(F.gelu(xp @ ar) for xp, ar in zip(X_parts, A_rows))
print("GELU of partial sums matches:",
      torch.allclose(wrong, F.gelu(X @ A), atol=1e-4))
column-then-row split matches: True
GELU of partial sums matches: False

The order matters: GELU of a partial sum is not part of the answer. Attention splits by heads. Tensor parallelism communicates inside every layer while GPUs wait, so it stays within a server, on NVLink, usually at most 8 GPUs.

Pipeline parallelism

Pipeline parallelism gives each GPU a stage of consecutive layers, passing small activation messages between neighbours, even across servers. The cost is idle time: with \(p\) stages and \(m\) micro-batches the bubble is \((p-1)/(m+p-1)\).

def bubble_fraction(stages, micro_batches):
    return (stages - 1) / (micro_batches + stages - 1)

for m in [1, 4, 16, 64]:
    print(f"4 stages, {m:>2} micro-batches: {bubble_fraction(4, m):.0%} idle")

def gpipe_schedule(stages, micro_batches):
    """Print who works when: F = forward, B = backward, . = idle."""
    slots = 2 * (micro_batches + stages - 1)
    for s in range(stages):
        row = ["."] * slots
        for j in range(micro_batches):
            row[s + j] = f"F{j}"                        # forwards flow down
            back = micro_batches + stages - 1 + (stages - 1 - s) + j
            row[back] = f"B{j}"                         # backwards flow up
        print(f"GPU {s}  " + " ".join(f"{c:<2}" for c in row).rstrip())

Sequence and context parallelism

Sequence parallelism splits layer norm and dropout along the sequence inside tensor-parallel groups. Context parallelism splits a long sequence across GPUs and passes key and value blocks round a ring, combining them with the online softmax of session 3.

Putting it together: 3-D parallelism

Real runs combine them, putting the chattiest parallelism on the fastest wires (links inside a server are roughly ten times faster than the network): tensor parallelism inside 8-GPU servers, pipeline stages across servers, sharded data parallelism across the rest. For example, 1,024 GPUs as 8-way tensor times 4 stages times 32 replicas.

The tools are PyTorch's DDP and FSDP2 (launched with torchrun), DeepSpeed, Megatron-LM and torchtitan. You need the mental model, so that "TP=8, PP=4, DP=32 with ZeRO-1" tells you what each GPU stores and when it talks.

Compute budgets and MFU

Training a dense transformer costs about \(6ND\) FLOPs (lesson ), so

\[ \text{training time} \approx \frac{6ND}{\text{GPUs} \times \text{peak FLOP/s per GPU} \times \text{MFU}} \]

MFU, model FLOPs utilisation, is the share of peak spent on the model's own arithmetic; communication, bubbles, memory-bound work and recomputation lower it. Well-tuned large runs commonly report 30 to 50 per cent. With an illustrative 1 petaFLOP/s per GPU and 40 per cent MFU:

def training_time(n_params, n_tokens, n_gpus, peak_flops=1e15, mfu=0.4):
    """FLOPs, days and GPU-hours for a dense transformer, from C = 6 N D."""
    flops = 6 * n_params * n_tokens
    seconds = flops / (n_gpus * peak_flops * mfu)
    return flops, seconds / 86400, n_gpus * seconds / 3600

What goes wrong at scale

  • Loss spikes. Defences include gradient clipping, warm-up and normalisation inside attention; the PaLM team restarted from a checkpoint before each spike and skipped the batches that followed.
  • Hardware failures. Meta's Llama 3 report describes hundreds of unexpected interruptions in under two months; runs restart automatically from checkpoints.
  • Big checkpoints. A 70B model's training state exceeds a terabyte; GPUs write their shards in parallel, with data position and random states.
  • Stragglers and silent errors. One slow GPU slows every synchronised step; a faulty chip can compute wrong numbers without crashing.
  • Determinism. Floating-point addition is not associative, so changing the GPU count changes the last bits.

FlashAttention: attention that respects the memory hierarchy

Standard attention writes a \(T \times T\) score matrix to HBM and reads it back for the softmax and again for the values: memory-bound steps, with memory growing as \(T^2\). FlashAttention (Dao et al., 2022) gets exactly the same result without writing that matrix. It holds a block of queries in SRAM and streams blocks of keys and values past it, using the online softmax: a running maximum \(m\), sum \(\ell\) and output \(o\) per row, rescaled when a new block of scores \(s_j\) raises the maximum:

\[ m' = \max\big(m, \max_j s_j\big), \quad \ell' = e^{m - m'}\,\ell + \sum_j e^{s_j - m'}, \quad o' = e^{m - m'}\,o + \sum_j e^{s_j - m'}\, v_j \]

After the last block, \(o/\ell\) is the exact output.

def naive_attention(q, k, v):
    scores = q @ k.T / q.shape[-1] ** 0.5        # (T, T): the whole matrix exists
    return scores.softmax(dim=-1) @ v

def tiled_attention(q, k, v, block=128):
    """Exact attention, holding one (block x block) tile of scores at a time."""
    T, d = q.shape
    out = torch.empty_like(q)
    for i in range(0, T, block):                 # a block of queries stays on chip
        qi = q[i:i + block] / d ** 0.5
        m = torch.full((len(qi), 1), float("-inf"))   # running max of each row
        l = torch.zeros(len(qi), 1)                   # running sum of exp(s - m)
        o = torch.zeros(len(qi), d)                   # running weighted sum of v
        for j in range(0, T, block):             # stream key/value blocks past it
            s = qi @ k[j:j + block].T            # the only scores we ever hold
            m_new = torch.maximum(m, s.max(dim=-1, keepdim=True).values)
            rescale = torch.exp(m - m_new)       # correct what was summed so far
            p = torch.exp(s - m_new)
            l = l * rescale + p.sum(dim=-1, keepdim=True)
            o = o * rescale + p @ v[j:j + block]
            m = m_new
        out[i:i + block] = o / l                 # normalise once, at the end
    return out

The largest intermediate shrinks from four million numbers to sixteen thousand. The backward pass recomputes scores from the saved \(m\) and \(\ell\), checkpointing again. FLOPs stay quadratic, but memory traffic falls sharply and memory grows linearly with \(T\). The gain needs a fused GPU kernel (in Python on a CPU this loop is slower), which F.scaled_dot_product_attention uses when available. With a causal mask, wholly future tiles are skipped, roughly halving the work.

Mixture of experts

A mixture of experts (MoE) layer replaces the MLP with many expert MLPs and a router, a linear layer that sends each token to its top \(k\) experts and weights their outputs (Shazeer et al., 2017). Parameters grow with the number of experts, compute per token only with \(k\).

class MoE(nn.Module):
    """A mixture-of-experts MLP: each token goes to its top-k experts."""
    def __init__(self, d=64, d_ff=256, n_experts=8, k=2):
        super().__init__()
        self.k, self.n_experts = k, n_experts
        self.router = nn.Linear(d, n_experts, bias=False)
        self.experts = nn.ModuleList(
            nn.Sequential(nn.Linear(d, d_ff), nn.GELU(), nn.Linear(d_ff, d))
            for _ in range(n_experts))

    def forward(self, x):                                   # x: (tokens, d)
        probs = self.router(x).softmax(dim=-1)              # (tokens, n_experts)
        weight, chosen = probs.topk(self.k, dim=-1)         # k experts per token
        weight = weight / weight.sum(dim=-1, keepdim=True)
        out = torch.zeros_like(x)
        for e, expert in enumerate(self.experts):
            token, slot = (chosen == e).nonzero(as_tuple=True)   # who picked e?
            if len(token):
                y_e = weight[token, slot, None] * expert(x[token])
                out.index_add_(0, token, y_e)
        # load-balancing loss (Switch Transformer): the fraction of tokens sent to
        # each expert times its mean router probability; 1.0 when perfectly even
        self.load = torch.bincount(chosen.flatten(), minlength=self.n_experts)
        frac = self.load / chosen.numel()
        self.aux_loss = self.n_experts * (frac * probs.mean(dim=0)).sum()
        return out

moe = MoE()
tokens = torch.randn(1000, 64)

total = sum(p.numel() for p in moe.parameters())

      f"({active / total:.0%})")

Routers tend to collapse onto a few experts, which then train faster and attract more tokens. The Switch Transformer's load-balancing loss (Fedus et al., 2021), the fraction of tokens per expert times its mean router probability, summed, is 1.0 for an even load and rises otherwise; it joins the training loss with a small weight. Experts usually sit on different GPUs (expert parallelism), so tokens travel to them and back in an all-to-all exchange. A model with about 47B parameters in total and 13B active (roughly Mixtral 8x7B) needs memory for 47B but compute for 13B: use the active count in \(6ND\).

Long context and state-space models

Per layer, linear layers cost about \(24Td^2\) forward FLOPs and attention about \(4T^2d\), a ratio of \(T/(6d)\): at width 4,096, attention dominates beyond about 25,000 tokens. So models are pretrained mostly on shorter sequences and extended at the end. Positions beyond the training length give RoPE (lesson ) unseen rotation angles; RoPE scaling methods such as position interpolation and YaRN rescale its frequencies.

A state-space model (SSM) carries a fixed-size state with a linear recurrence, \(h_t = \bar{A}_t \odot h_{t-1} + \bar{B}_t x_t\), \(y_t = C_t h_t\). Linearity allows a parallel scan, which made SSMs trainable where classic RNNs struggled. Mamba (Gu and Dao, 2023) makes \(\bar{A}_t\), \(\bar{B}_t\) and \(C_t\) depend on the input, so the model chooses what to keep, and runs the scan in a hardware-aware kernel.

def selective_scan(x, delta, A, B, C):
    """h_t = exp(delta_t A) h_(t-1) + delta_t B_t x_t, then y_t = h_t C_t."""
    decay = torch.exp(delta[:, :, None] * A)              # (T, d, n), in (0, 1)
    h = delta[:, :, None] * B[:, None, :] * x[:, :, None]  # (T, d, n) inputs
    for t in range(1, len(x)):                             # the sequential part
        h[t] += decay[t] * h[t - 1]
    return torch.einsum("tdn,tn->td", h, C)                # read each state out

torch.manual_seed(0)
d, n = 64, 16                          # 64 channels, a 16-number state for each
A = -torch.rand(d, n) - 0.5                      # negative, so the state decays
W_delta, W_B, W_C = (torch.randn(d, k_out) / 8 for k_out in (d, n, n))

def ssm_layer(x):          # "selective": decay, input and readout all depend on x
    return selective_scan(x, F.softplus(x @ W_delta), A, x @ W_B, x @ W_C)

The Python loop is slow, so watch the growth: each doubling of \(T\) multiplies attention's time by about four to five and the scan's by about two. When generating, an SSM keeps only its latest state, here 1,024 numbers, while a KV cache grows with every token (lesson ). A fixed-size state recalls distant details less precisely, so many long-context models are hybrids of SSM or linear-attention layers with a few attention layers (AI21's Jamba was an early example).

Smaller caches and lower precision

Grouped-query attention (lesson ) shares key and value heads; multi-head latent attention (MLA), from DeepSeek-V2, caches one compressed latent per token and projects keys and values from it. And FP8 matrix multiplication, with per-tensor or per-block scales, increasingly carries the bulk of training compute (DeepSeek-V3's report describes it at scale), while master weights, optimiser state and accumulation stay in higher precision.

Check yourself

An element-wise addition runs at a tiny fraction of an accelerator's peak FLOP/s. Why?

  • Accelerators have no dedicated addition units
  • Its arithmetic intensity is very low, so memory bandwidth limits it
  • Additions must run in float32
  • It cannot be split across enough cores

About one FLOP per 12 bytes moved puts it far left of the ridge point. Fusing it with neighbouring operations is the fix.

About how much memory do the weights, gradients and Adam states of a 7B model need for mixed-precision training, before activations?

  • 14 GB
  • 28 GB
  • 112 GB
  • 1.1 TB

16 bytes per parameter: 2 for bf16 weights, 2 for bf16 gradients and 12 for float32 master weights and Adam's two moments.

Why is tensor parallelism usually kept within a single server?

  • It only works with exactly 8 GPUs
  • It copies the optimiser state to every GPU
  • It communicates inside every layer, so it needs the fastest links
  • It changes the maths of the model

Its all-reduces sit on the critical path of every layer in both passes; over the slower network the GPUs would mostly wait.

What does FlashAttention change?

  • It approximates attention with low-rank matrices
  • It reduces attention's FLOPs from quadratic to linear
  • It computes exact attention tile by tile in on-chip memory, never writing the full score matrix to HBM
  • It only speeds up inference, not training

Same result and the same FLOPs, but far less memory traffic, and memory that grows linearly with context.

A mixture-of-experts model has 64 experts per layer and sends each token to 2. Compared with a dense model of the same total size, it needs...

  • much less memory and much less compute per token
  • about the same memory, but much less compute per token
  • more compute per token, because of the router
  • the same memory and the same compute

All experts must be held in memory, but each token runs through only the active ones, so use the active count in 6ND.

Key takeaways

  • Accelerators are usually limited by moving bytes. The roofline says which limit applies: big matmuls are compute-bound, element-wise work memory-bound.
  • Mixed-precision Adam needs about 16 bytes per parameter before activations. Checkpointing trades compute for activation memory; accumulation builds big batches from small ones.
  • Data parallelism copies the model and all-reduces gradients; ZeRO and FSDP shard the state; tensor parallelism splits layers over fast links; pipeline parallelism splits the stack and pays a bubble.
  • Training time is about \(6ND\) over GPUs, peak FLOP/s and MFU. At scale, plan for spikes, failures and terabyte checkpoints.
  • FlashAttention, MoE, GQA and MLA, state-space layers and low precision all buy more model per byte moved, byte stored or FLOP spent.
