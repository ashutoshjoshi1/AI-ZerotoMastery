The idea in one paragraph

The TinyGPT you trained in lesson had a few million parameters and fitted easily on one device. A frontier model has hundreds of billions of parameters, sees trillions of tokens (lesson ) and trains on thousands of accelerators for weeks. Three things change at that scale. Speed is limited by moving data rather than by arithmetic, so you need a picture of the hardware. The model, its gradients and its optimiser no longer fit on one device, so they are split across many, in several ways at once. And many architecture choices you meet in model cards, such as FlashAttention, mixture of experts and state-space layers, exist mainly to make all this cheaper. You will not need a cluster: every idea here is measured or simulated on a laptop CPU.

How an accelerator spends its time

A GPU is thousands of simple arithmetic cores, grouped into units that each have dedicated matrix-multiply hardware (tensor cores, on NVIDIA GPUs). TPUs and other accelerators differ in detail but share the shape: enormous arithmetic throughput, fed by a hierarchy of memories that get bigger and slower the further they sit from the cores.

LevelWhat lives thereSpeed (illustrative)

Meanwhile the matrix units of a current data-centre accelerator perform hundreds of teraFLOP/s to a few petaFLOP/s in 16-bit precision. The exact figures change with every hardware generation, but arithmetic has been getting faster more quickly than memory for years, so the gap keeps widening: arithmetic is cheap, moving bytes is expensive.

Arithmetic intensity

The question to ask of any operation is how much work it does per byte it moves. That ratio is its arithmetic intensity:

\[ I = \frac{\text{FLOPs performed}}{\text{bytes read and written}} \]

Adding two vectors of \(n\) float32 numbers does \(n\) additions but reads \(8n\) bytes and writes \(4n\), so \(I = 1/12\). Multiplying two \(n \times n\) matrices does \(2n^3\) FLOPs on \(12n^2\) bytes of inputs and output, so \(I = n/6\), growing with size. Matrix multiplication is the common operation whose intensity grows like that, which is why accelerators are built around it, and why transformers, which are mostly matrix multiplications, run well on them.

The roofline model

The roofline model turns this into a prediction. An operation can go no faster than the arithmetic units allow, and no faster than memory can deliver its bytes:

\[ \text{attainable FLOP/s} = \min\left(\text{peak FLOP/s},\; I \times \text{memory bandwidth}\right) \]

The two limits cross at the ridge point, peak divided by bandwidth. For an illustrative accelerator with 1,000 TFLOP/s and 3 TB/s, that is about 330 FLOPs per byte. An operation to the left of the ridge is memory-bound: faster arithmetic would not help it. One to the right is compute-bound.

You can see both regimes on your own machine. This code times matrix multiplications of growing size and one large element-wise addition, then converts the times into achieved GFLOP/s and GB/s.

import time
import torch

def bench(fn, repeats=10):
    """Best of several timed runs, in seconds (the best is the least noisy)."""
    fn()                                          # warm-up run
    times = []
    for _ in range(repeats):
        start = time.perf_counter()
        fn()
        times.append(time.perf_counter() - start)
    return min(times)

torch.manual_seed(0)
results = []                                      # (name, FLOP/byte, GFLOP/s, GB/s)
for n in [64, 256, 1024, 2048]:
    a, b, c = torch.randn(n, n), torch.randn(n, n), torch.empty(n, n)
    t = bench(lambda: torch.matmul(a, b, out=c))
    flops, nbytes = 2 * n**3, 3 * n * n * 4       # read a and b, write c (fp32)
    results.append((f"matmul {n}", flops / nbytes, flops / t / 1e9,
                    nbytes / t / 1e9))

x, y, z = torch.randn(2**24), torch.randn(2**24), torch.empty(2**24)
t = bench(lambda: torch.add(x, y, out=z))         # 16.8 million additions
flops, nbytes = x.numel(), 3 * x.numel() * 4      # read x and y, write z
results.append(("add", flops / nbytes, flops / t / 1e9, nbytes / t / 1e9))

print(f"{'operation':<13}{'FLOP/byte':>10}{'GFLOP/s':>10}{'GB/s':>8}")
for name, intensity, gflops, gbs in results:
    print(f"{name:<13}{intensity:10.2f}{gflops:10.1f}{gbs:8.1f}")

Read it as a roofline. The addition does almost no arithmetic per byte and reaches about 1% of the large matmuls' FLOP/s, yet it moves data more than ten times faster than any of them: its speed is set by memory bandwidth. The large matrix multiplications are compute-bound and approach the CPU's peak. Dividing the best GFLOP/s by the addition's GB/s gives this CPU's ridge point, around 10 FLOPs per byte; GPUs sit much further to the right. The smallest matmul is slow for a third reason, fixed overhead per call, which GPUs share: launching each kernel costs a few microseconds. The notebook plots your points against a roofline built from your own measurements.

Two practical lessons follow. First, a chain of element-wise operations (add a bias, apply GELU, apply dropout) reads and writes the whole tensor at every step. Kernel fusion does them all in one pass over memory, and torch.compile does it for you. Second, small matrix multiplications waste an accelerator. The exercise shows that a linear layer's intensity is roughly the number of tokens it processes at once, which is why training uses big batches and why serving batches many users together (lesson ).

Number formats and mixed precision

A floating-point number spends its bits on a sign, an exponent, which sets the range, and a mantissa, which sets the precision. Fewer bits mean less memory, less bandwidth and faster matrix units, so training uses the smallest formats it can get away with. PyTorch will tell you what each one can represent:

bf16 (bfloat16) keeps float32's 8 exponent bits, so it has the same huge range, but only 7 mantissa bits: the gap between 1 and the next number is about 0.008, two to three significant digits. fp16 has more precision but tops out at 65,504 and has no normal numbers below about \(6 \times 10^{-5}\). The two 8-bit formats split the difference: E4M3 for weights and activations, E5M2, with more range, for gradients.

Low precision fails in two characteristic ways, both easy to reproduce:

w32 = torch.tensor(1.0)
w16 = torch.tensor(1.0, dtype=torch.bfloat16)
for _ in range(1000):
    w32 += 1e-4               # a small update, like learning rate x gradient
    w16 += 1e-4
print(w32.item(), w16.item())

grads = torch.tensor([1e-3, 1e-6, 1e-8])
print(grads.half())                         # fp16: the smallest underflows to 0
print(grads.bfloat16())                     # bf16: fine range, coarse precision
scale = 2.0 ** 16                           # loss scaling: scale up first...
print((grads * scale).half().float() / scale)   # ...unscale in fp32: no loss
1.1000165939331055 1.0
tensor([1.0004e-03, 1.0133e-06, 0.0000e+00], dtype=torch.float16)
tensor([9.9945e-04, 9.9838e-07, 1.0012e-08], dtype=torch.bfloat16)
tensor([1.0004e-03, 1.0002e-06, 9.9972e-09])

The first line is the lost update. Near 1.0, bf16 numbers are about 0.008 apart, so adding \(10^{-4}\) rounds back to 1.0 every time, and a thousand steps change nothing. This is why mixed-precision training keeps a float32 master copy of the weights for the optimiser to update, and uses bf16 copies for the forward and backward passes. The second problem is underflow: in fp16, a gradient of \(10^{-8}\) becomes zero. Loss scaling multiplies the loss by a large factor before the backward pass, lifting every gradient into fp16's range, and divides it out in float32 before the update. PyTorch's torch.amp.GradScaler does this dynamically, lowering the factor and skipping the step whenever it finds an infinity. bf16 does not need it, one reason it became the default for training (lesson showed torch.autocast).

Inside the matrix units, products of bf16 numbers are summed in float32, and sensitive operations such as softmax, normalisation and the loss usually run in float32 too. That is what "mixed" means: low precision where it is safe and cheap, high precision where errors would pile up.

The memory budget of training

Training holds four things in memory: the weights, their gradients, the optimiser state, and the activations saved in the forward pass for the backward pass to use. With Adam in mixed precision, the first three cost a fixed 16 bytes per parameter, the rule of thumb from lesson : 2 for bf16 weights, 2 for bf16 gradients, and 12 for the float32 master weights and Adam's two moment estimates. Activations depend on how many tokens you process at once. A widely used estimate (Korthikanti et al., 2022) is about 34 bytes per token, per unit of model width, per layer, with 16-bit activations and a fused attention kernel:

def training_memory_gb(n_params, n_layers, d_model, seq_len, micro_batch,
                       checkpointing=False):
    """Rough memory to train on ONE device with mixed-precision Adam."""
    states = 16 * n_params   # bf16 weights 2 + bf16 grads 2 + fp32 master, Adam 12
    tokens = seq_len * micro_batch
    if checkpointing:   # keep each layer's bf16 input, rebuild one layer at a time
        acts = (2 * n_layers + 34) * tokens * d_model
    else:               # about 34 bytes per token per unit of width, in every layer
        acts = 34 * n_layers * tokens * d_model
    return states / 1e9, acts / 1e9

models = {"1B": (1e9, 16, 2048), "7B": (7e9, 32, 4096), "70B": (70e9, 80, 8192)}
print(f"{'model':<6}{'states GB':>10}{'activations GB':>16}{'checkpointed GB':>17}")
for name, (n, layers, d) in models.items():
    states, acts = training_memory_gb(n, layers, d, seq_len=4096, micro_batch=1)
    _, acts_ckpt = training_memory_gb(n, layers, d, 4096, 1, checkpointing=True)
    print(f"{name:<6}{states:10.0f}{acts:16.1f}{acts_ckpt:17.1f}")

The assumptions matter, so state them: one sequence of 4,096 tokens, layer counts and widths typical of open models of these sizes, and nothing for temporary buffers or the output logits, so treat the numbers as lower bounds. The conclusion is still stark. A 7B model needs about 112 GB before a single activation, more than one 80 GB accelerator holds, and a 70B model needs over a terabyte. No batch size or setting fixes that: the state itself must be split across devices, which is session 2. Activations, though, can be traded against compute.

Activation checkpointing

Gradient checkpointing (also called activation checkpointing) keeps only each layer's input during the forward pass and discards the layer's internals. In the backward pass it reruns that layer's forward just before the internals are needed. Activation memory falls from every layer's internals to one input per layer plus one layer's internals at a time. The price is roughly one extra forward pass, about a third more compute, since a backward pass costs about twice a forward. The code counts the bytes autograd saves for the backward pass, with and without checkpointing, and compares the gradients:

import torch.nn as nn
from torch.utils.checkpoint import checkpoint

class MLPStack(nn.Module):
    def __init__(self, d=256, n_layers=8, use_checkpoint=False):
        super().__init__()
        self.layers = nn.ModuleList(
            nn.Sequential(nn.Linear(d, 4 * d), nn.GELU(), nn.Linear(4 * d, d))
            for _ in range(n_layers))
        self.use_checkpoint = use_checkpoint

    def forward(self, x):
        for layer in self.layers:
            if self.use_checkpoint:   # drop the insides, recompute in backward
                x = x + checkpoint(layer, x, use_reentrant=False)
            else:
                x = x + layer(x)
        return x

def backward_and_measure(model, x):
    """Run forward and backward; return gradients and MB saved for backward."""
    saved = 0
    def pack(t):
        nonlocal saved
        if not isinstance(t, nn.Parameter):       # count activations, not weights
            saved += t.numel() * t.element_size()
        return t
    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        loss = model(x).pow(2).mean()
    loss.backward()
    return [p.grad for p in model.parameters()], saved / 1e6

torch.manual_seed(0)
x = torch.randn(512, 256)
plain = MLPStack()
ckpt = MLPStack(use_checkpoint=True)
ckpt.load_state_dict(plain.state_dict())          # identical weights
g1, mb1 = backward_and_measure(plain, x)
g2, mb2 = backward_and_measure(ckpt, x)
print(f"saved for backward: {mb1:.1f} MB plain, {mb2:.1f} MB checkpointed")
print("identical gradients:", all(torch.equal(a, b) for a, b in zip(g1, g2)))
saved for backward: 54.0 MB plain, 4.7 MB checkpointed
identical gradients: True

The gradients are identical, bit for bit, because exactly the same operations are rerun (PyTorch even restores the random-number state so dropout masks match). Large runs often checkpoint selectively: they recompute only parts that are cheap to redo but expensive to store, such as attention's internals, and keep the rest.

Gradient accumulation

Pretraining uses batches of millions of tokens, far more than fit in memory at once. Gradient accumulation runs several micro-batches through forward and backward, lets the gradients add up in .grad, and takes one optimiser step at the end. Divide each micro-batch's loss by the number of micro-batches and you get exactly the big batch's gradient:

import copy
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, 1))
X, y = torch.randn(256, 20), torch.randn(256, 1)
loss_fn = nn.MSELoss()                            # a mean over the batch

model.zero_grad()
loss_fn(model(X), y).backward()                   # one batch of 256
full = [p.grad.clone() for p in model.parameters()]

model.zero_grad()
steps = 4
for Xm, ym in zip(X.chunk(steps), y.chunk(steps)):    # four micro-batches of 64
    (loss_fn(model(Xm), ym) / steps).backward()       # .grad keeps adding up
accum = [p.grad.clone() for p in model.parameters()]
print("max difference:",
      max((a - b).abs().max().item() for a, b in zip(full, accum)))
max difference: 1.043081283569336e-07

The difference is float32 rounding, not a bug. Two mistakes are common: forgetting the division, which silently multiplies your learning rate, and averaging per-sequence losses when sequences hold different numbers of tokens, which over-weights short ones. Sum the token losses and divide by the total token count across all micro-batches instead.

Data parallelism

The simplest way to use many GPUs is data parallelism: every GPU holds a complete copy of the model, each processes a different slice of the batch, and before the optimiser step they average their gradients with an operation called an all-reduce. Every replica then applies the same update to the same weights, so they stay identical. Simulate four workers in one process, with the model and data from the previous section, and check this gives exactly the full-batch gradient:

n_workers = 4
workers = [copy.deepcopy(model) for _ in range(n_workers)]   # a full replica each
for w, Xs, ys in zip(workers, X.chunk(n_workers), y.chunk(n_workers)):
    w.zero_grad()
    loss_fn(w(Xs), ys).backward()    # each worker sees only its shard of the batch

# all-reduce: every worker ends up with the average of all workers' gradients
for params in zip(*(w.parameters() for w in workers)):
    avg = torch.stack([p.grad for p in params]).mean(dim=0)
    for p in params:
        p.grad = avg.clone()

dp = [p.grad for p in workers[0].parameters()]
print("max difference from full batch:",
      max((a - b).abs().max().item() for a, b in zip(full, dp)))
max difference from full batch: 1.043081283569336e-07

Equal up to float32 rounding, because the additions happen in a different order. Averaging matches the full batch only because every shard is the same size and the loss is a mean; unequal shards need weighting. Batch normalisation is another trap, since each worker computes statistics over its own shard only.

How an all-reduce works

Sending every gradient to one GPU, summing and sending back would make that GPU's link the bottleneck. The classic alternative is a ring. Arrange the workers in a circle, split each gradient into \(N\) chunks, and pass chunks to the next neighbour. During the first \(N-1\) steps, the reduce-scatter, each passing chunk is added to, until every worker holds the finished sum of one chunk. During the next \(N-1\) steps, the all-gather, the finished chunks travel round so everyone has all of them.

import numpy as np

def ring_all_reduce(arrays):
    """Sum equal-length arrays held by n workers by passing chunks round a ring."""
    n = len(arrays)
    chunks = [np.array_split(a.astype(float), n) for a in arrays]
    sent = 0
    # 1. reduce-scatter: after n-1 steps, worker i owns the total of chunk (i+1) % n
    for step in range(n - 1):
        msgs = [(i, (i - step) % n) for i in range(n)]
        data = [chunks[i][c].copy() for i, c in msgs]   # everyone sends at once
        for (i, c), d in zip(msgs, data):
            chunks[(i + 1) % n][c] += d                 # the neighbour adds it in
            sent += d.size
    # 2. all-gather: pass each finished chunk round the ring
    for step in range(n - 1):
        msgs = [(i, (i + 1 - step) % n) for i in range(n)]
        data = [chunks[i][c].copy() for i, c in msgs]
        for (i, c), d in zip(msgs, data):
            chunks[(i + 1) % n][c] = d                  # the neighbour copies it
            sent += d.size
    return [np.concatenate(c) for c in chunks], sent / n    # values sent per worker

rng = np.random.default_rng(0)
size = 120_000                                    # gradient values per worker
for n in [2, 4, 8, 64]:
    grads = [rng.normal(size=size) for _ in range(n)]
    total = np.sum(grads, axis=0)
    result, per_worker = ring_all_reduce(grads)
    ok = all(np.allclose(r, total) for r in result)
    print(f"{n:>3} workers: correct={ok}, "
          f"each sends {per_worker / size:.2f} x its gradient")
  2 workers: correct=True, each sends 1.00 x its gradient
  4 workers: correct=True, each sends 1.50 x its gradient
  8 workers: correct=True, each sends 1.75 x its gradient
 64 workers: correct=True, each sends 1.97 x its gradient

Each worker sends \(2(N-1)/N\) times its gradient, which approaches twice the gradient size however many workers you add. The time is set by the gradient size and the link speed, not the number of GPUs (each step adds a little latency, which is why libraries such as NCCL also use trees). PyTorch's DistributedDataParallel (DDP) adds one more trick: it groups gradients into buckets and starts all-reducing each bucket as soon as the backward pass produces it, hiding communication behind computation. Keep reduce-scatter and all-gather in mind; they are the building blocks of what follows.

ZeRO and FSDP: stop storing everything N times

Plain data parallelism is wasteful: every GPU stores the full 16 bytes per parameter. ZeRO (Rajbhandari et al., 2020) removes the redundancy in three stages. Stage 1 shards the optimiser state: each GPU keeps Adam's statistics and master weights for only \(1/N\) of the parameters, and updates only that slice. Stage 2 also shards the gradients, using a reduce-scatter instead of an all-reduce so each GPU receives just the slice it needs. Stage 3 shards the weights too: each layer's weights are all-gathered just before the layer runs, in the forward and again in the backward pass, then freed. PyTorch's FSDP (fully sharded data parallel, now the fully_shard API of FSDP2) is ZeRO stage 3; DeepSpeed implements all three stages.

def zero_memory_gb(n_params, n_gpus, stage):
    """Training-state memory per GPU (bf16 weights and grads, fp32 Adam)."""
    weights, grads, optim = 2 * n_params, 2 * n_params, 12 * n_params
    if stage >= 1: optim /= n_gpus       # ZeRO-1: shard the optimiser state
    if stage >= 2: grads /= n_gpus       # ZeRO-2: ...and the gradients
    if stage >= 3: weights /= n_gpus     # ZeRO-3 (FSDP): ...and the weights too
    return (weights + grads + optim) / 1e9

Model parallelism: splitting the model itself

Tensor parallelism

Tensor parallelism splits each layer's weight matrices across GPUs, so the GPUs compute every layer together. The standard layout, from the Megatron-LM papers, needs only one all-reduce for a transformer MLP. Split the first matrix by columns, so each GPU owns some of the hidden units; GELU acts on each hidden unit separately, so each GPU applies it locally. Split the second matrix by rows to match, and each GPU produces a partial result that only needs summing:

import torch.nn.functional as F
torch.manual_seed(0)
tokens, d, d_ff, n_gpus = 6, 16, 64, 4
X = torch.randn(tokens, d)
A, B = torch.randn(d, d_ff), torch.randn(d_ff, d)    # the MLP's two weight matrices
full = F.gelu(X @ A) @ B                             # one device does it all

A_parts = A.chunk(n_gpus, dim=1)    # column split: each GPU gets d_ff/4 hidden units
B_parts = B.chunk(n_gpus, dim=0)     # row split: the matching rows of B
partial = [F.gelu(X @ a) @ b for a, b in zip(A_parts, B_parts)]  # no talking needed
out = torch.stack(partial).sum(dim=0)                # one all-reduce at the end
print("column-then-row split matches:", torch.allclose(out, full, atol=1e-4))

# Splitting A by rows instead gives partial sums of X @ A, and GELU of a partial
# sum is not part of the answer: you would need an all-reduce before the GELU.
X_parts, A_rows = X.chunk(n_gpus, dim=1), A.chunk(n_gpus, dim=0)
wrong = sum(F.gelu(xp @ ar) for xp, ar in zip(X_parts, A_rows))
print("GELU of partial sums matches:",
      torch.allclose(wrong, F.gelu(X @ A), atol=1e-4))
column-then-row split matches: True
GELU of partial sums matches: False

The second check shows why the order matters. Splitting the first matrix the other way gives partial sums, and GELU of a partial sum is not part of the answer, so an extra all-reduce would be needed before the activation. Attention splits the same way, by heads. The catch is that tensor parallelism communicates inside every layer, in both passes, while the GPUs wait. It needs the fastest links available, so it is nearly always kept within one server, over NVLink, usually across at most 8 GPUs.

Pipeline parallelism

Pipeline parallelism gives each GPU a block of consecutive layers, a stage, and passes activations forward and gradients back between neighbours. The messages are small, so stages can sit in different servers. The problem is idle time: when one batch goes through, the last stage waits for all the others, and on the way back the first stage waits again. Splitting the batch into micro-batches keeps more stages busy at once. With \(p\) stages and \(m\) micro-batches the idle fraction, the bubble, is

\[ \text{bubble} = \frac{p-1}{m+p-1} \] 
def bubble_fraction(stages, micro_batches):
    return (stages - 1) / (micro_batches + stages - 1)

for m in [1, 4, 16, 64]:
    print(f"4 stages, {m:>2} micro-batches: {bubble_fraction(4, m):.0%} idle")

def gpipe_schedule(stages, micro_batches):
    """Print who works when: F = forward, B = backward, . = idle."""
    slots = 2 * (micro_batches + stages - 1)
    for s in range(stages):
        row = ["."] * slots
        for j in range(micro_batches):
            row[s + j] = f"F{j}"                        # forwards flow down
            back = micro_batches + stages - 1 + (stages - 1 - s) + j
            row[back] = f"B{j}"                         # backwards flow up
        print(f"GPU {s}  " + " ".join(f"{c:<2}" for c in row).rstrip())

Sequence and context parallelism

Two more splits deal with long sequences. Sequence parallelism complements tensor parallelism: operations that tensor parallelism leaves duplicated on every GPU, such as layer norm and dropout, are split along the sequence instead, saving activation memory. Context parallelism splits a long sequence across GPUs for attention itself. Each GPU keeps its share of the queries and passes blocks of keys and values around a ring, combining partial results with the online-softmax trick you will implement in session 3. It is one of the main tools for training with very long contexts.

Putting it together: 3-D parallelism

Real runs combine all three, each matched to the links it needs. A typical layout puts tensor parallelism inside each 8-GPU server, where NVLink is fast; pipeline stages across servers, since they exchange only activations; and data parallelism, usually with ZeRO-1 or FSDP sharding, across everything else. As an illustration, 1,024 GPUs could run as 8-way tensor parallel times 4 pipeline stages times 32 data-parallel replicas. Mixture-of-experts models add a fourth axis, expert parallelism, which you will meet in session 3. The rule is to put the chattiest parallelism on the fastest wires: links inside a server are roughly an order of magnitude faster than the network between servers.

You will not write this machinery yourself. PyTorch provides DDP and FSDP2, and launches one process per GPU with torchrun; torch.compile fuses kernels; DeepSpeed provides ZeRO; Megatron-LM and Megatron-style libraries provide tensor and pipeline parallelism; and PyTorch's torchtitan shows them combined. What you need is the mental model, so that a configuration such as "TP=8, PP=4, DP=32 with ZeRO-1" tells you what each GPU stores and when it talks.

Compute budgets and MFU

Lesson gave the rule that training a dense transformer with \(N\) parameters on \(D\) tokens costs about \(6ND\) FLOPs. Divide by what your cluster really delivers and you have a schedule:

\[ \text{training time} \approx \frac{6ND}{\text{GPUs} \times \text{peak FLOP/s per GPU} \times \text{MFU}} \]

MFU, model FLOPs utilisation, is the fraction of the hardware's peak that goes into the model's own arithmetic: \(6N\) times the tokens per second you achieve, divided by the total peak. Communication, pipeline bubbles, memory-bound operations and recomputation all pull it down (recomputed FLOPs do not count, which is why checkpointing lowers MFU). Well-tuned large runs commonly report something like 30 to 50 per cent. The calculator assumes an illustrative 1 petaFLOP/s per GPU and 40 per cent MFU:

def training_time(n_params, n_tokens, n_gpus, peak_flops=1e15, mfu=0.4):
    """FLOPs, days and GPU-hours for a dense transformer, from C = 6 N D."""
    flops = 6 * n_params * n_tokens
    seconds = flops / (n_gpus * peak_flops * mfu)
    return flops, seconds / 86400, n_gpus * seconds / 3600

What goes wrong at scale

  • Loss spikes. The loss suddenly jumps and sometimes never recovers. Causes include bad batches, learning rates near the edge of stability and attention logits growing too large. Defences are gradient clipping, learning-rate warm-up, normalisation inside attention and monitoring that catches spikes early. The PaLM team, for example, restarted from a checkpoint shortly before each spike and skipped the batches that had followed it.
  • Hardware failures. With tens of thousands of GPUs, something breaks every few hours: a GPU, a memory chip, a network link. Meta's Llama 3 report describes hundreds of unexpected interruptions in under two months of pretraining. Runs restart automatically from the latest checkpoint, with spare machines ready.
  • Big checkpoints. At 16 bytes per parameter, a 70B model's training state is over a terabyte. Each GPU writes its own shard, often asynchronously so training does not pause, and the checkpoint includes the data loader's position and random-number states so a restart sees the right data.
  • Stragglers and silent errors. One slow GPU slows every synchronised step, and a faulty chip can produce wrong numbers without crashing. Teams track per-device timings and run health checks.
  • Determinism. Floating-point addition is not associative, so a different GPU count or reduction order changes the last bits of the result, as you saw above. Bit-exact reproducibility is possible but costs speed; most teams settle for a reproducible data order and statistically reproducible loss curves.

FlashAttention: attention that respects the memory hierarchy

Look at standard attention with roofline eyes. It computes a \(T \times T\) score matrix, writes it to HBM, reads it back for the softmax, writes the probabilities, and reads them again to multiply by the values. The softmax does a handful of operations per number, so these steps are memory-bound, and the \(T \times T\) matrices take memory that grows with the square of the context. FlashAttention (Dao et al., 2022) computes exactly the same result without ever writing that matrix to HBM. It loads a block of queries into on-chip SRAM, streams blocks of keys and values past it, and keeps only a running result for each query.

The obstacle is the softmax: each row needs its maximum and its sum over all keys before any weight is known. The online softmax keeps a running maximum \(m\), a running sum \(\ell\) and a running output \(o\) for each row, and rescales them whenever a new block of scores \(s_j\) raises the maximum:

\[ m' = \max\big(m, \max_j s_j\big), \quad \ell' = e^{m - m'}\,\ell + \sum_j e^{s_j - m'}, \quad o' = e^{m - m'}\,o + \sum_j e^{s_j - m'}\, v_j \]

After the last block, \(o / \ell\) is the exact attention output for that row.

def naive_attention(q, k, v):
    scores = q @ k.T / q.shape[-1] ** 0.5        # (T, T): the whole matrix exists
    return scores.softmax(dim=-1) @ v

def tiled_attention(q, k, v, block=128):
    """Exact attention, holding one (block x block) tile of scores at a time."""
    T, d = q.shape
    out = torch.empty_like(q)
    for i in range(0, T, block):                 # a block of queries stays on chip
        qi = q[i:i + block] / d ** 0.5
        m = torch.full((len(qi), 1), float("-inf"))   # running max of each row
        l = torch.zeros(len(qi), 1)                   # running sum of exp(s - m)
        o = torch.zeros(len(qi), d)                   # running weighted sum of v
        for j in range(0, T, block):             # stream key/value blocks past it
            s = qi @ k[j:j + block].T            # the only scores we ever hold
            m_new = torch.maximum(m, s.max(dim=-1, keepdim=True).values)
            rescale = torch.exp(m - m_new)       # correct what was summed so far
            p = torch.exp(s - m_new)
            l = l * rescale + p.sum(dim=-1, keepdim=True)
            o = o * rescale + p @ v[j:j + block]
            m = m_new
        out[i:i + block] = o / l                 # normalise once, at the end
    return out

In the backward pass FlashAttention recomputes the scores block by block from the saved \(m\) and \(\ell\) instead of storing them: checkpointing again, trading cheap FLOPs for expensive bytes. The FLOP count is unchanged, still quadratic in \(T\); the gains are far less memory traffic and memory that grows linearly with \(T\). As a Python loop on a CPU, this version is slower than the naive one. The benefit appears only in a fused GPU kernel, which is what F.scaled_dot_product_attention calls when one is available.

Mixture of experts

A mixture of experts (MoE) layer replaces a transformer's single MLP with many expert MLPs and a small router, a linear layer that scores every expert for every token (Shazeer et al., 2017). Each token goes to its top \(k\) experts, typically 1 to 8 out of dozens or hundreds, and their outputs are mixed using the router's weights. Parameters grow with the number of experts; compute per token grows only with \(k\).

class MoE(nn.Module):
    """A mixture-of-experts MLP: each token goes to its top-k experts."""
    def __init__(self, d=64, d_ff=256, n_experts=8, k=2):
        super().__init__()
        self.k, self.n_experts = k, n_experts
        self.router = nn.Linear(d, n_experts, bias=False)
        self.experts = nn.ModuleList(
            nn.Sequential(nn.Linear(d, d_ff), nn.GELU(), nn.Linear(d_ff, d))
            for _ in range(n_experts))

    def forward(self, x):                                   # x: (tokens, d)
        probs = self.router(x).softmax(dim=-1)              # (tokens, n_experts)
        weight, chosen = probs.topk(self.k, dim=-1)         # k experts per token
        weight = weight / weight.sum(dim=-1, keepdim=True)
        out = torch.zeros_like(x)
        for e, expert in enumerate(self.experts):
            token, slot = (chosen == e).nonzero(as_tuple=True)   # who picked e?
            if len(token):
                y_e = weight[token, slot, None] * expert(x[token])
                out.index_add_(0, token, y_e)
        # load-balancing loss (Switch Transformer): the fraction of tokens sent to
        # each expert times its mean router probability; 1.0 when perfectly even
        self.load = torch.bincount(chosen.flatten(), minlength=self.n_experts)
        frac = self.load / chosen.numel()
        self.aux_loss = self.n_experts * (frac * probs.mean(dim=0)).sum()
        return out

Each token uses a quarter of the parameters. Two problems come with that. Routers tend to collapse: an expert that receives slightly more tokens trains faster, gets better and attracts still more, until a few experts do all the work. The load-balancing loss of the Switch Transformer (Fedus et al., 2021) multiplies the fraction of tokens each expert receives by its mean router probability and sums over experts. It is 1.0 when the load is even, rises when it is not (skewing the inputs towards expert 0 nearly doubled it), and is added to the training loss with a small weight. Some recent models instead nudge a per-expert bias up or down to even out the load. The second problem is systems. Experts usually live on different GPUs (expert parallelism), so every MoE layer sends tokens to their experts and back with an all-to-all exchange, and each expert has a fixed capacity, beyond which extra tokens are dropped and skip the layer through the residual connection.

When a model card says a model has about 47 billion parameters in total but 13 billion active per token (roughly the shape of Mixtral 8x7B), budget memory for 47 billion and compute for 13 billion: use the active count in \(6ND\).

Long context and the cost of attention

Per layer, a transformer's linear layers cost about \(24Td^2\) FLOPs in the forward pass for \(T\) tokens of width \(d\), while attention's two \(T \times T\) matrix multiplications cost about \(4T^2d\). The ratio is \(T/(6d)\): for a model of width 4,096, attention dominates the compute beyond roughly 25,000 tokens. FlashAttention removed the memory wall but not this quadratic cost, and the KV cache adds a serving cost that grows with context (lessons and ). So models are usually pretrained mostly on shorter sequences and extended in a final phase on long ones, with context parallelism when one sequence's activations will not fit.

The positional encoding has to cooperate. With RoPE, each pair of dimensions rotates at its own frequency, and positions far beyond the training length produce combinations of angles the model has never seen. RoPE scaling methods such as position interpolation, NTK-aware scaling and YaRN rescale those frequencies so that long positions look like ones seen in training, usually followed by a short fine-tune at the new length. In a model card, a large RoPE base (theta) or a YaRN factor is the sign of this.

State-space models and hybrids

Attention keeps every past token and compares against all of them. A state-space model (SSM) instead carries a fixed-size state forward through the sequence, like an RNN, updating it with a linear recurrence:

\[ h_t = \bar{A}_t \odot h_{t-1} + \bar{B}_t\, x_t, \qquad y_t = C_t\, h_t \]

Because the recurrence is linear in \(h\), it can be computed with a parallel scan instead of strictly one step at a time, which made SSMs trainable at scale where classic RNNs struggled. Mamba (Gu and Dao, 2023) made the parameters selective: \(\bar{A}_t\), \(\bar{B}_t\) and \(C_t\) depend on the current input, so the model can decide what to keep and what to forget, and a hardware-aware kernel computes the scan with the expanded state held in SRAM. Here is a minimal selective scan, timed against naive attention:

def selective_scan(x, delta, A, B, C):
    """h_t = exp(delta_t A) h_(t-1) + delta_t B_t x_t, then y_t = h_t C_t."""
    decay = torch.exp(delta[:, :, None] * A)              # (T, d, n), in (0, 1)
    h = delta[:, :, None] * B[:, None, :] * x[:, :, None]  # (T, d, n) inputs
    for t in range(1, len(x)):                             # the sequential part
        h[t] += decay[t] * h[t - 1]
    return torch.einsum("tdn,tn->td", h, C)                # read each state out

torch.manual_seed(0)
d, n = 64, 16                          # 64 channels, a 16-number state for each
A = -torch.rand(d, n) - 0.5                      # negative, so the state decays
W_delta, W_B, W_C = (torch.randn(d, k_out) / 8 for k_out in (d, n, n))

def ssm_layer(x):          # "selective": decay, input and readout all depend on x
    return selective_scan(x, F.softplus(x @ W_delta), A, x @ W_B, x @ W_C)

The Python loop is slow in absolute terms (a real kernel runs the scan in parallel on chip), so look at the growth instead. Each doubling of \(T\) quadruples the attention score matrix, and attention's time grows by a factor of about four to five, while the scan's time roughly doubles. At generation time the difference is starker: the SSM keeps only its latest state, here \(64 \times 16 = 1{,}024\) numbers, however long the conversation, while a KV cache grows with every token. The flip side is that a fixed-size state cannot recall an arbitrary detail from long ago as precisely as attention, which can look it up. So many recent long-context models are hybrids: mostly SSM or linear-attention layers, with a few full attention layers mixed in (AI21's Jamba was an early example).

Smaller caches and lower precision

Grouped-query attention, from lesson , shares each key and value head among several query heads, shrinking the KV cache by that factor. Multi-head latent attention (MLA), introduced in DeepSeek-V2, goes further: it caches one compressed latent vector per token and layer, and projects it up into keys and values for every head when needed. Both trade a little modelling freedom for a much smaller cache, which matters most for long contexts and many concurrent users.

On precision, bf16 is today's default for training, and FP8 matrix multiplication is increasingly used for the bulk of the compute, with scale factors kept per tensor or per small block so values stay in range; DeepSeek-V3's technical report, for example, describes FP8 training at large scale. Newer accelerators add block-scaled formats down to 4 bits. The pattern is the one you saw with bf16: cheap formats for the matrix multiplications, higher precision for master weights, optimiser state, accumulation and sensitive operations.

Check yourself

An element-wise addition runs at a tiny fraction of an accelerator's peak FLOP/s. Why?

  • Accelerators have no dedicated addition units
  • Its arithmetic intensity is very low, so memory bandwidth limits it
  • Additions must run in float32
  • It cannot be split across enough cores

About one FLOP per 12 bytes moved puts it far left of the ridge point. Fusing it with neighbouring operations is the fix.

About how much memory do the weights, gradients and Adam states of a 7B model need for mixed-precision training, before activations?

  • 14 GB
  • 28 GB
  • 112 GB
  • 1.1 TB

16 bytes per parameter: 2 for bf16 weights, 2 for bf16 gradients and 12 for float32 master weights and Adam's two moments.

Why is tensor parallelism usually kept within a single server?

  • It only works with exactly 8 GPUs
  • It copies the optimiser state to every GPU
  • It communicates inside every layer, so it needs the fastest links
  • It changes the maths of the model

The all-reduces sit on the critical path of every layer in both passes; over slower network links the GPUs would spend most of their time waiting.

What does FlashAttention change?

  • It approximates attention with low-rank matrices
  • It reduces attention's FLOPs from quadratic to linear in sequence length
  • It computes exact attention tile by tile in on-chip memory, never writing the full score matrix to HBM
  • It only speeds up inference, not training

Same result and the same FLOPs, but far less memory traffic, and memory that grows linearly rather than quadratically with context.

A mixture-of-experts model has 64 experts per layer and sends each token to 2 of them. Compared with a dense model of the same total parameter count, it needs...

  • much less memory and much less compute per token
  • about the same memory, but much less compute per token
  • more compute per token, because of the router
  • the same memory and the same compute

All experts must be held in memory, but each token runs through only the active ones, so use the active count in 6ND.

Key takeaways

  • Accelerators are limited by moving bytes far more often than by arithmetic. Arithmetic intensity and the roofline tell you which limit applies; large matrix multiplications are compute-bound, element-wise work is memory-bound.
  • Mixed-precision training computes in bf16 but keeps float32 master weights and optimiser state: about 16 bytes per parameter before activations. Checkpointing trades compute for activation memory; accumulation builds big batches from small ones.
  • Data parallelism copies the model and all-reduces gradients; ZeRO and FSDP shard optimiser state, gradients and weights; tensor parallelism splits layers over fast links; pipeline parallelism splits the stack and pays a bubble. Big runs combine them.
  • Training time is about \(6ND\) divided by GPUs, peak FLOP/s and MFU. At scale, plan for loss spikes, hardware failures and terabyte checkpoints.
  • FlashAttention, mixture of experts, GQA and MLA, state-space layers and low-precision formats all buy the same thing: more model per byte moved, per byte stored or per FLOP spent.
