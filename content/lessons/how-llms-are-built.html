From TinyGPT to a frontier model

Your TinyGPT from lesson has the same architecture as a frontier LLM, give or take some refinements. The differences are a proper tokeniser, about a million times more parameters, roughly a hundred million times more training data, and a long post-training phase that turns a text predictor into a helpful assistant. This lesson walks through each stage, because each one explains behaviour you will run into as an engineer: odd failures on spelling and arithmetic, the cost of long prompts, why temperature matters, and why models can be confidently wrong.

Tokenisation

Characters make sequences long (attention is quadratic in length); whole words make the vocabulary enormous and cannot handle new words. Modern LLMs use subword tokens: frequent words get a single token, rare words are split into pieces, and anything at all can fall back to raw bytes. Vocabularies are typically 32,000 to 260,000 tokens. In English, one token is roughly four characters, or about three-quarters of a word.

Byte-pair encoding, implemented

BPE starts from the 256 possible byte values and repeatedly merges the most frequent adjacent pair into a new token. Real tokenisers first split text into word-like chunks with a regular expression, so merges never cross word boundaries.

import re
from collections import Counter

PAT = re.compile(r" ?[A-Za-z]+| ?\d+| ?[^\sA-Za-z\d]+|\s+")   # pre-split into word-like chunks

def merge(ids, pair, new_id):
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

def train_bpe(text, vocab_size):
    chunks = [list(c.encode("utf-8")) for c in PAT.findall(text)]
    merges = {}                                  # (id_a, id_b) -> new_id, in the order learned
    for new_id in range(256, vocab_size):
        counts = Counter()
        for ch in chunks:
            counts.update(zip(ch, ch[1:]))
        if not counts:
            break
        pair = max(counts, key=counts.get)       # most frequent adjacent pair
        chunks = [merge(ch, pair, new_id) for ch in chunks]
        merges[pair] = new_id
    return merges

def build_vocab(merges):
    vocab = {i: bytes([i]) for i in range(256)}
    for (a, b), new_id in merges.items():
        vocab[new_id] = vocab[a] + vocab[b]
    return vocab

def encode(text, merges):
    out = []
    for chunk in PAT.findall(text):
        ids = list(chunk.encode("utf-8"))
        while len(ids) >= 2:
            # apply the earliest-learned merge available, exactly as in training
            pair = min(set(zip(ids, ids[1:])), key=lambda p: merges.get(p, float("inf")))
            if pair not in merges:
                break
            ids = merge(ids, pair, merges[pair])
        out.extend(ids)
    return out

def decode(ids, vocab):
    return b"".join(vocab[i] for i in ids).decode("utf-8", errors="replace")

Train it on a paragraph about tokenisers (repeated a few times) with a 400-token vocabulary, then look at what it does:

'The tokenizer splits words.'   27 bytes ->  6 tokens: 'T' 'he' ' tokenizer' ' splits' ' words' '.'
'remodelling'                   11 bytes ->  4 tokens: 're' 'model' 'l' 'ing'
'Tokenization of 3.14159'       23 bytes -> 18 tokens: 'T' 'o' 'k' 'en' 'i' 'z' 'at' 'i' 'on' ' of' ...
'naïve 🚀'                      11 bytes -> 11 tokens: raw bytes for ï and the emoji

Even this toy shows the real behaviours:

  • Frequent words are one token; rare ones fragment. " tokenizer" was common in training text, "Tokenization" with a capital T was not, so it shatters into letters.
  • Shared pieces carry meaning. "remodelling" reuses "model".
  • Numbers tokenise awkwardly. Digits are split inconsistently, which is one reason LLMs can be unreliable at arithmetic and at counting letters ("how many r's in strawberry?"): the model never sees individual characters, only tokens.
  • Unseen text falls back to bytes. Nothing is ever unknown, but non-English text and emoji cost many more tokens, which means more cost and less effective context.

Tokens are the unit of everything

APIs charge per token, context windows are measured in tokens, and latency scales with tokens generated. Use the provider's token counter (or tiktoken for OpenAI-style tokenisers, or a Hugging Face tokeniser for open models) when you estimate costs. Never estimate from word counts in production.

Pretraining

The objective

Exactly what TinyGPT did: minimise cross-entropy on the next token, averaged over every position of every sequence. No labels, no task definitions. To predict the next token of a physics textbook, a chemistry paper, a Python repository and a legal contract, a model has to absorb grammar, facts, reasoning patterns and coding conventions. Capabilities emerge as a by-product of compression.

The data

Pretraining corpora are trillions of tokens. Meta reported training Llama 3 on over 15 trillion tokens, for example. Sources are mostly filtered web crawls (such as Common Crawl), plus code, books, scientific papers, encyclopaedias, and increasingly synthetic data generated by other models. Most of the work is in curation: removing duplicates, spam and boilerplate, filtering for quality (often with classifiers trained to spot educational text), removing personal information, balancing languages and domains, and deciding the mixture. Data quality is now widely regarded as one of the biggest levers on model quality.

Compute and scaling laws

A useful rule of thumb: training a dense transformer with \(N\) parameters on \(D\) tokens costs about

\[ C \approx 6ND \ \text{floating-point operations} \]

(two for the forward pass and four for the backward pass, per parameter per token). A 70-billion-parameter model on 15 trillion tokens is about \(6.3\times10^{24}\) FLOPs: thousands of GPUs for months.

In 2020, Kaplan and colleagues found that loss falls as a smooth power law in parameters, data and compute, over many orders of magnitude. That predictability is why labs can plan huge training runs from small experiments. In 2022 the Chinchilla paper refined the recipe: for a fixed compute budget, the loss-optimal split is roughly 20 training tokens per parameter, so many earlier models were too big for their data. Today most models are trained on far more tokens than that ratio suggests, because a smaller model trained longer is cheaper to serve, and serving costs dominate over a model's lifetime.

Architecture refinements you will see in model cards

  • RMSNorm instead of LayerNorm, applied before each sub-layer (pre-norm).
  • SwiGLU MLPs instead of a plain GELU MLP.
  • RoPE positions and grouped-query attention (lesson ).
  • Mixture of experts (MoE): each MLP is replaced by many "expert" MLPs and a small router that sends each token to only a few of them. Total parameters can be huge while the compute per token stays modest. Several leading open models use MoE.

Post-training: from predictor to assistant

A freshly pretrained base model continues text. Ask it "What is the capital of France?" and it may continue with "What is the capital of Germany?", because lists of quiz questions are common on the web. Post-training turns it into something that follows instructions, holds a conversation, refuses harmful requests and uses tools.

1. Supervised fine-tuning (SFT)

Train further, with the same next-token loss, on curated examples of the desired behaviour: prompts paired with high-quality responses, written by people or generated and filtered. Usually tens of thousands to millions of examples, formatted with a chat template that marks system, user and assistant turns with special tokens. SFT teaches the format and the style of being helpful.

2. Learning from preferences: RLHF

It is easier for people to compare two responses than to write a perfect one. Reinforcement learning from human feedback collects many comparisons ("A is better than B"), trains a reward model to predict which response people prefer, then optimises the LLM with reinforcement learning (classically PPO) to produce responses the reward model scores highly. A KL penalty (lesson ) keeps the model close to its SFT starting point, so it cannot drift into weird text that happens to fool the reward model. InstructGPT (2022) showed that a small RLHF-tuned model could be preferred over a much larger base model.

3. Direct preference optimisation (DPO)

DPO (2023) skips the separate reward model and the RL loop. It turns preference pairs directly into a classification-style loss that raises the likelihood of preferred responses relative to rejected ones, again anchored to a reference model. It is simpler and more stable, and widely used for open models. You will run it in lesson .

4. AI feedback and principles

Human labelling is slow and costly. RLAIF uses a model to judge responses, often against a written set of principles. Anthropic's Constitutional AI is the best-known example: a model critiques and revises its own outputs according to a constitution of principles, and AI-generated preferences train the final model.

5. Reasoning models

A more recent shift: train models with reinforcement learning on problems whose answers can be checked automatically (maths with known answers, code with unit tests), rewarding correct final answers. Models learn to produce long chains of intermediate reasoning, to try approaches, notice mistakes and backtrack. At inference time these models spend extra tokens "thinking" before answering, and accuracy on hard problems improves as they are allowed to think longer. This test-time compute is a second scaling axis next to model size. As an engineer you will see it as a setting (a thinking or reasoning budget) that trades latency and cost for accuracy.

Decoding: turning distributions into text

At each step the model outputs a probability for every token in its vocabulary. How you pick from that distribution changes the output a lot.

  • Greedy: always take the most likely token. Deterministic, but prone to dull, repetitive text.
  • Temperature: divide logits by \(T\) before softmax (you explored this in lesson ). Below 1 sharpens, above 1 flattens.
  • Top-k: sample only among the \(k\) most likely tokens.
  • Top-p (nucleus): sample from the smallest set of tokens whose probabilities add up to \(p\), so the candidate set adapts to how confident the model is.
import numpy as np
rng = np.random.default_rng(0)

def softmax(z):
    z = z - z.max(); e = np.exp(z); return e / e.sum()

def sample(logits, temperature=1.0, top_k=None, top_p=None):
    p = softmax(logits / max(temperature, 1e-6))
    if top_k is not None:
        p = np.where(p >= np.sort(p)[-top_k], p, 0)
    if top_p is not None:
        order = np.argsort(-p)
        keep = order[: np.searchsorted(np.cumsum(p[order]), top_p) + 1]
        p = np.where(np.isin(np.arange(len(p)), keep), p, 0)
    p = p / p.sum()
    return rng.choice(len(p), p=p), p.round(3)

logits = np.array([3.0, 2.5, 1.0, 0.2, -1.0])
print(sample(logits))                    # full distribution [0.549 0.333 0.074 0.033 0.01 ]
print(sample(logits, top_k=2))           # [0.622 0.378 0.    0.    0.   ]
print(sample(logits, top_p=0.9))         # [0.574 0.348 0.078 0.    0.   ]
print(sample(logits, temperature=0.1))   # [0.993 0.007 0.    0.    0.   ]  nearly greedy

Practical defaults. For extraction, classification, code and anything with one right answer, use low temperature (0 to 0.3). For brainstorming and creative writing, use higher (0.7 to 1.0). Change one of temperature or top-p, not both at once. Note that temperature 0 is not a guarantee of identical outputs from a hosted API; batching and floating-point effects on GPUs can still introduce small differences.

Context windows

The context window is the maximum number of tokens (prompt plus output) the model can attend to. It grew from 2,048 tokens for GPT-3 to hundreds of thousands or more for current models. Three caveats matter in practice:

  • Cost and latency scale with input length. Every request pays for its whole prompt, every time (prompt caching, lesson , helps).
  • Use of long context is uneven. Models often retrieve information placed at the start or end of a long prompt more reliably than information buried in the middle ("lost in the middle"). Test this for your use case rather than assuming.
  • Output length is limited separately, by a maximum output token setting.

Why models make things up

LLMs are trained to produce plausible continuations. When the training data contained an answer and the model learned it well, plausible and true coincide. When it did not, the model can still produce something fluent and confident. This is hallucination (or confabulation). Contributing causes:

  • The objective rewards plausibility, not truth, and pretraining text rarely says "I don't know".
  • Knowledge has a cutoff date; the model knows nothing about later events unless you supply them.
  • Rare facts (a specific paper's page numbers, an obscure API's parameters, a person's exact biography) are weakly learned.
  • Long reasoning chains compound small errors.

Post-training reduces it substantially, but no model eliminates it. Engineering mitigations, which fill much of part VI: give the model the facts (retrieval, lesson ), ask for citations and check them, let it use tools for lookups and arithmetic (lesson ), allow and reward "I don't know", and measure it with evaluations (lesson ).

The model landscape

Closed, API-only (e.g. Claude, GPT, Gemini) Open-weight (e.g. Llama, Mistral, Qwen, DeepSeek, Gemma)
Capability Usually the frontier Strong and improving fast, typically somewhat behind the frontier
Setup An API key GPUs, a serving stack, operations work
Data control Data leaves your network (check the provider's retention and training terms) Can run fully on-premise or offline
Customisation Prompting, some fine-tuning options Full fine-tuning, quantisation, modification
Cost shape Per token, no fixed cost Mostly fixed hardware cost; cheap at high volume

Most real systems mix them: a frontier model for hard reasoning, a small open model for high-volume classification, an embedding model for search. Model names and rankings change every few months, so build systems where the model is a configuration value, and keep an evaluation set (lesson ) to tell you objectively when to switch.

1. English is the most token-efficient; other languages usually need more tokens per character, so they cost more and fit less into the context window. Long numbers are split into chunks of a few digits. 2. A leading space and capitalisation produce different token sequences: " strawberry" and "strawberry" are distinct tokens or splits. The model sees a few opaque ids, not ten letters, so counting the r's requires knowledge it never directly observes. 3. Without pre-splitting, frequent multi-word phrases (including the trailing space and the next word) merge into single tokens. The vocabulary fills with phrase fragments that generalise poorly, and the same word gets different tokens depending on its neighbours.

Check yourself

Why do LLMs often struggle to count the letters in a word?

  • They are trained only on numbers
  • They see tokens, multi-character chunks, rather than individual letters
  • Their context window is too short
  • Letter counting is disabled during post-training

The model has to infer spelling from tokens it never sees broken into characters.

Roughly how many FLOPs does it take to train a 7-billion-parameter model on 140 billion tokens, using C ≈ 6ND?

  • 5.9 × 10^12
  • 5.9 × 10^21
  • 9.8 × 10^20
  • 6 × 10^9

6 × 7e9 × 1.4e11 ≈ 5.9e21. That is the Chinchilla-style budget of 20 tokens per parameter.

What is the role of the KL penalty in RLHF?

  • It speeds up training
  • It keeps the tuned model close to its starting point so it cannot drift into exploiting the reward model
  • It removes the need for human preferences
  • It makes the model's outputs shorter

Without it the policy can find degenerate outputs that score highly on an imperfect reward model.

You need a model to extract invoice fields into JSON reliably. Which decoding setting fits best?

  • Low temperature, such as 0 to 0.2
  • Temperature 1.5 for variety
  • High top-k with high temperature
  • It makes no difference

Tasks with one right answer want the most likely tokens, not creative variation.

What distinguishes reasoning models from standard chat models?

  • They have larger context windows
  • They are trained with RL on checkable problems to produce long reasoning before answering, and improve with more thinking tokens
  • They do not use transformers
  • They cannot hallucinate

Test-time compute is a second scaling axis: more thinking, at higher latency and cost, for better accuracy on hard problems.

Key takeaways

  • Text becomes subword tokens via BPE. Tokens are the unit of cost, context and latency, and they explain quirks with spelling, numbers and non-English text.
  • Pretraining minimises next-token cross-entropy over trillions of curated tokens. Compute is about \(6ND\); loss follows predictable scaling laws.
  • Post-training (SFT, then preference learning with RLHF or DPO, plus AI feedback) turns a text predictor into an assistant. Reasoning models add RL on verifiable tasks and spend test-time compute.
  • Decoding settings matter: low temperature for one-right-answer tasks, higher for creative ones.
  • Hallucination follows from the objective. Mitigate it with retrieval, tools, citations, abstention and evaluation.
