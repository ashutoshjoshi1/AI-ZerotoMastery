Why a capstone

Courses build knowledge; projects build skill and evidence. One well-executed, end-to-end project, with an evaluation set, measured results and an honest write-up, says more to an employer or a team lead than a dozen certificates. It also exposes the gaps you did not know you had, which is the point.

The six sessions of this lesson are a minimum. A good capstone takes two to six weeks of hour-a-day work. Let it.

How to run your capstone

  1. Scope narrowly. One user, one job, done well. "An assistant for everything about our instruments" fails; "answers calibration-procedure questions for model X from the service manual, with page citations" succeeds.
  2. Evaluation set first. Before writing the system, write 30 to 50 test cases with expected outcomes (lesson ). This defines "done".
  3. Walking skeleton. Get the crudest end-to-end version working in the first session, then improve the weakest stage, measuring each change.
  4. Keep a decision log. For each significant choice, write what you chose, the alternatives and the evidence. This becomes the most impressive part of your write-up.
  5. Finish. Deployed, documented and measured beats ambitious and half-built.

The seven capstones

Pick one. Each has a core specification, stretch goals and a rubric. Together they exercise everything in the course, including the wider field of part IX; if you do more than one later, choose ones that cover different parts.

Capstone A: technical documentation assistant (RAG)

Build a question-answering assistant over a real document collection of at least 300 pages (manuals, standards, a project's documentation, public technical reports).

Core requirements

  • Parsing that handles the collection's real formats, including at least tables or scans (lessons , ).
  • Hybrid retrieval with reranking; metadata filters (document type or product).
  • Answers with inline citations to document and page or section; explicit "not in the documents" behaviour.
  • An evaluation set of at least 60 questions (including 10 unanswerable), with retrieval and answer metrics reported for at least three configurations.
  • A streaming API (FastAPI) and a minimal web or command-line interface; request tracing.

Stretch goals: contextual retrieval; conversational follow-ups with query rewriting and a conversation state kept under a token budget (lesson ); an agentic mode for multi-part questions with a cost comparison; offline mode with a quantised local model (lesson ).

Capstone B: operations agent with MCP tools

Build an agent that helps operate something real or realistically simulated: a fleet of devices, a home lab, a cloud project, a data pipeline.

Core requirements

  • An MCP server exposing at least four tools (mostly read-only) and one resource (lesson ).
  • At least one consequential tool protected by human approval showing the exact action.
  • Step and cost limits; complete traces of every run.
  • An evaluation of at least 25 tasks with checkable outcomes, reporting success rate, average steps, cost and latency.
  • An attack set of at least 8 prompt-injection and misuse cases, with results before and after your defences (lesson ).

Stretch goals: a planner that writes and updates an explicit plan; a reasoning model for the hardest tasks, routed by difficulty, with a cost comparison (lesson ); long-term memory of past incidents via retrieval (lesson ); a comparison with a fixed workflow for the most common tasks.

Capstone C: anomaly detection with narrative reports

Build a pipeline over time-series data (your own sensor data, public air-quality or weather station data, server metrics) that detects anomalies and explains them.

Core requirements

  • Data cleaning and feature engineering (lesson ) with documented choices.
  • At least two detection methods (rules plus a statistical or ML detector) evaluated against labelled or injected anomalies with precision and recall (lesson ).
  • An LLM step that turns each detection into a structured report (likely cause, evidence, confidence, recommended action), grounded in the data and any available logs.
  • A judged evaluation of report quality on a sample, with a rubric.
  • A daily scheduled run producing a readable summary.

Stretch goals: a chat interface for follow-up questions using tools over the data; a forecasting model whose residuals become a third detector (lesson ); a feedback loop where confirmed or dismissed alerts improve thresholds.

Capstone D: distil a small model for a structured task

Build a fine-tuned small open model that performs a narrow extraction or classification task nearly as well as a frontier model at a fraction of the cost.

Core requirements

  • A task with a strict output schema and a held-out evaluation set of at least 100 human-checked examples.
  • A training set of at least 500 examples (distilled from a large model, reviewed by sampling).
  • LoRA or QLoRA fine-tuning of a model of 3 billion parameters or fewer, with training and validation curves (lesson ).
  • Comparison of four systems on the eval set: small model prompted, small model fine-tuned, large model prompted, and a routed combination; report accuracy per field, latency and cost per thousand requests.
  • Deployment of the fine-tuned model behind an OpenAI-compatible server (vLLM, Ollama or llama.cpp).

Stretch goals: quantise to 4-bit and measure the quality change (lesson ); a preference-tuning round (DPO or a GRPO-style method) on pairs from your error analysis (lesson ); run it on a CPU-only machine.

Capstone E: evaluation and observability for an LLM feature

Build the evaluation and monitoring layer for an existing LLM feature: one from earlier in the course, an open-source project, or one at work (with permission).

Core requirements

  • A golden dataset of at least 100 cases with slices, sourced from real or realistic usage (lesson ).
  • Code graders plus at least two LLM-judge graders, each calibrated against at least 40 human grades with agreement reported.
  • A harness producing per-slice reports with confidence intervals and fixed/broken case lists between two versions.
  • CI integration that blocks a change on per-slice thresholds.
  • A tracing setup and a dashboard of cost, latency percentiles and judged quality on sampled traffic (lesson ).

Stretch goals: an online feedback loop that turns low-rated traces into candidate eval cases; drift detection on input topics; a red-team suite run nightly.

Capstone F: a fast, cheap inference service for a small model

Build a serving system for a small open model (3 billion parameters or fewer; the one you fine-tuned in Capstone D is ideal) that is as fast and cheap as you can make it without losing measured quality, with an evaluation report that explains every number.

Core requirements

  • A quality eval set of at least 100 cases for the task the model serves, scored by code graders or a calibrated judge (lesson ), run against every configuration below.
  • A load-testing harness that replays realistic traffic at several concurrency levels and reports time to first token, p50 and p95 latency, output tokens per second and requests per second (lessons , ).
  • At least three serving configurations compared on quality, latency, throughput and cost per million tokens: for example 16-bit versus 8-bit versus 4-bit weights, or with and without continuous batching and prefix caching.
  • One decoding optimisation beyond batching, measured: speculative decoding with a small draft model (report acceptance rate and speed-up), or prefix caching for shared prompts (report hit rate and the change in time to first token).
  • An evaluation report: one table of configurations against quality, latency, throughput and cost, the GPU or CPU memory arithmetic that explains the numbers, and a recommendation.
  • Containerised deployment with health checks, metrics and a dashboard.

Stretch goals: distil or fine-tune the model to the task first (Capstone D); compare against a hosted API on cost and quality at your real volume, including prompt caching; serve on CPU with llama.cpp and compare; autoscaling under bursty load.

Capstone G: a recommender with offline and online evaluation

Build a recommender over a real or public interaction dataset (MovieLens, a bookshop's orders, your own listening history, an open e-commerce dataset) that serves recommendations through an API and measures itself both offline and online.

Core requirements

  • A data pipeline with a time-based split (train on earlier interactions, evaluate on later ones) and documented handling of new users and new items (lesson ).
  • At least three recommenders compared: a popularity baseline, a collaborative-filtering model (matrix factorisation or item-to-item), and one more (a two-tower model, gradient boosting on features, or a graph method), reporting recall@k, NDCG@k and catalogue coverage (lessons , ).
  • An API that serves top-k recommendations with p95 latency under 100 ms, using precomputed candidates and an approximate-nearest-neighbour index for embedding models (lesson ).
  • An online evaluation design: an A/B test or interleaving with a primary metric, guardrail metrics, a sample-size estimate and an exposure log; run it with willing users or a simulated user model, and report it honestly (lesson ).
  • An analysis of feedback loops and fairness: popularity bias, exposure of new items, and what a user with no history sees.

Stretch goals: LLM-written explanations for each recommendation; natural-language search over the catalogue with embeddings; a session-based model; a bandit for exploration (lesson ).

Other wider-field variants. If your domain is images, adapt Capstone C's structure into a visual inspection pipeline: a trained classifier or detector on your own labelled images, a precision-recall analysis at the operating threshold, drift monitoring, and an LLM summary of the defect log (lesson ). If it is control, train an RL policy in a simulator with a measured comparison against a hand-written controller (lesson ). Keep the same rubric.

Hands-on: scope your capstone

Write a one-page project brief before writing any code:

  1. One sentence: who it is for and what it does.
  2. Three measurable success criteria.
  3. Your data sources and how you will build the eval set.
  4. The simplest architecture that could work, as a sketch.
  5. The three riskiest assumptions, and how you will test each in the first week.
  6. What you will deliberately not build.
Show an example brief (Capstone A)

Who and what: answers calibration and maintenance questions for one instrument model from its 420-page service manual and 60 service bulletins, with page citations, for field technicians.

Success criteria: (1) correct page in the top 6 retrieved for at least 90% of 60 answerable test questions; (2) faithful, correctly cited answers for at least 85% as judged by a calibrated judge; (3) says "not in the documents" for at least 9 of 10 unanswerable questions; median time to first token under 2 seconds.

Data and eval: the PDF manual and bulletins; 40 questions from two experienced technicians plus 20 reviewed synthetic questions and 10 unanswerable ones; gold page numbers recorded for each.

Architecture: Docling parsing, section-level chunks with title and section path, BM25 plus embeddings with RRF, cross-encoder reranking to 6, a mid-tier model with the grounded prompt, FastAPI streaming, JSON-line traces.

Riskiest assumptions: tables of torque values parse correctly (test 10 tables on day one); technicians phrase questions very differently from the manual (collect real questions early); bulletins that supersede manual sections can be detected (check metadata).

Not building: user accounts, a mobile app, multi-manual support, fine-tuning.

Build the walking skeleton

The goal of this session is one request going through every stage of your system and coming out the other end with a trace, however bad the answer. A walking skeleton is deliberately crude: keyword lookup instead of retrieval, a template instead of a model call, a fixed threshold instead of a trained detector. What matters is that every stage exists and every run is measured.

Set the repository up so that change stays cheap, as lesson argued:

  • One entry point: a pipeline(input) function (or class) that calls each stage in turn. Everything else, including the API and the eval harness, calls it.
  • Configuration in one place: model names, thresholds, top-k values and prompts live in a settings file or module, never inline, so an experiment is a one-line change (lesson ).
  • Traces from day one: each run writes one JSON line with the input, each stage's output, timing and cost. You will debug from these, and they become eval cases (lesson ).
  • Deterministic where possible: fixed seeds, temperature zero for graded calls, pinned package versions.

A minimal harness ties the pipeline to the eval cases you wrote in session 1. It is a dozen lines, and you will run it hundreds of times:

import json
import time


def run_eval(pipeline, grade, cases, trace_path="traces.jsonl"):
    """Run every case through the pipeline, trace it, return the pass rate."""
    passed = 0
    with open(trace_path, "a") as f:
        for case in cases:
            t0 = time.perf_counter()
            result = pipeline(case["input"])
            ok = grade(result, case["expected"])
            passed += ok
            f.write(json.dumps({"id": case["id"], "input": case["input"],
                                "result": result, "passed": ok,
                                "seconds": round(time.perf_counter() - t0, 4)}) + "\n")
    return passed / len(cases)

Then the loop that fills the rest of the session, and the next two weeks: run the harness, open the ten worst traces, find the stage that failed most often, improve only that stage, run again, and write one line in the decision log.

Evaluate, harden and deploy

With the skeleton running, the next sessions are an improvement loop. Three habits separate projects that converge from projects that wander.

One change at a time, with an interval

Change one stage, rerun the whole eval set, and compare. Two pass rates are not enough: with 50 cases, a change of three cases is noise. Use the paired bootstrap from lesson to put an interval on the difference, and list the cases that were fixed and broken, because a change that fixes eight and breaks six has taught you something about two kinds of input.

import numpy as np


def paired_bootstrap(before, after, n=5000, seed=0):
    """Mean change and a 95% interval for the change in pass rate between two
    runs on the same cases."""
    rng = np.random.default_rng(seed)
    before, after = np.asarray(before, float), np.asarray(after, float)
    idx = rng.integers(0, len(before), size=(n, len(before)))
    diffs = after[idx].mean(axis=1) - before[idx].mean(axis=1)
    return (after - before).mean(), np.percentile(diffs, [2.5, 97.5])

Harden

Before anyone else uses it: an attack set of injection and misuse cases run like any other eval (lesson ); step, token and cost limits on every loop; input validation and a defined failure behaviour for every stage (what the user sees when retrieval returns nothing or the model times out); and least privilege for every tool and credential.

Deploy

Deployed means a stranger can try it: a container, a streaming API with health checks, metrics for cost and latency percentiles, and a dashboard you can screenshot for the write-up (lesson ). If you serve a model yourself, this is where the levers of lesson pay off: quantise, batch, cache the shared prefix, and measure again. Cost per request is measured from traces, not estimated.

Hands-on: one measured improvement

  1. Make one real change to the weakest stage of your skeleton (for Capstone A, replace keyword counting with ranking by the fraction of query words matched, or with embeddings from lesson ).
  2. Run the harness again into a second trace file.
  3. From the two trace files, list the fixed and broken case ids and compute paired_bootstrap on the per-case results.
  4. Write the decision-log row: date, decision, alternatives, evidence (the interval), result.

You are done when you have a decision-log row with an interval in it, and can say whether the change is real or noise.

Show what you should find

The solutions notebook ranks paragraphs by the fraction of query words matched after lower-casing, stripping punctuation and dropping stopwords, and abstains when even the best paragraph matches less than half of them. Reading both trace files back and comparing per case prints:

before 0.7  after 0.8
fixed: ['q-009', 'q-010']  broke: ['q-005']
change +0.10  95% interval [-0.2, 0.4]

The change fixed both unanswerable cases (the skeleton now abstains) and broke one paraphrase, because "installing" no longer matches "install" once whole words are compared. That is exactly what the fixed and broken lists are for: the next decision-log row is about stemming or embeddings, not about the overall number. With ten cases the interval spans zero, so the decision-log row should say that the evidence is thin and that the honest next step is more cases, not a bigger model.

Write it up

Your write-up is what most people will see. Structure it like a short engineering report:

  1. The problem in two sentences, and a 60-second demo video or animated GIF at the top.
  2. Results first: a table of your final metrics against the baseline, with intervals.
  3. Architecture: one diagram and a paragraph per component.
  4. What I tried: the decision log, condensed. Include things that did not work and why; this is often the most impressive part.
  5. Limitations and next steps, honestly.
  6. How to run it: setup in under five commands.

Publish the repository, and consider a blog post. Clear writing about a real project is one of the strongest signals of an engineer who can work on a team. If an AI assistant helps you draft it, keep your own voice and check every number against your traces; reviewers notice prose that claims more than the results table shows.

Hands-on: a results-first README

Draft the first screen of your README, the part a reader sees without scrolling:

  1. The problem in two sentences, naming the user.
  2. A results table: baseline versus final on your two or three headline metrics, with the interval or sample size, plus cost per thousand requests and p50 latency.
  3. Three bullet points of "what I tried", each with the evidence and including one thing that did not work.
  4. The five commands to run it.

You are done when a colleague who has never seen the project can say in one minute what it does, how well, and how to try it.

Interview preparation

AI engineering interviews typically combine coding, ML and LLM fundamentals, system design and a discussion of your projects. The concept questions below come up repeatedly. Answer each aloud in under two minutes before opening the suggested answer.

Explain the bias-variance trade-off and how you diagnose it.

Bias is error from overly simple assumptions (underfitting: high training and validation error); variance is error from sensitivity to the particular training data (overfitting: low training error, high validation error). Diagnose by comparing training and validation error; fix underfitting with more capacity or better features, overfitting with more data, regularisation, simpler models or early stopping (lesson ).

Walk through scaled dot-product attention. Why divide by √d_k?

Each token's query is dotted with every key, scaled, softmaxed into weights, and used to average the values: softmax(QKᵀ/√d_k)V. Dot products of random d-dimensional vectors have standard deviation √d, so without scaling large dimensions push softmax into saturation and gradients vanish (lesson ).

What is the KV cache, and why does it matter for serving?

During generation, keys and values of previous tokens are stored so each step only computes the new token's projections. It makes generation efficient but consumes memory proportional to layers × KV heads × head dimension × context length × concurrent sequences, which often limits how many users a GPU can serve; paged allocation and grouped-query attention exist to shrink it (lessons and ).

How do quantisation, batching and speculative decoding make serving cheaper?

Decoding one token reads every weight once, so it is bound by memory bandwidth, not arithmetic. Quantisation stores weights in 8 or 4 bits, cutting memory and the bytes read per token, at a small and measurable quality cost. Continuous batching serves many sequences per weight read, raising throughput without hurting each request much. Speculative decoding lets a small draft model propose several tokens that the large model verifies in one parallel pass, producing the same distribution faster when the acceptance rate is high (lesson ).

When would you use a reasoning model, and what does it cost?

Reasoning models spend extra tokens thinking before they answer, which helps on multi-step problems: maths, code, planning, diagnosis across several pieces of evidence. The cost is latency and output tokens, controlled by a thinking budget. They are not better at everything, so route only the hard cases to them, evaluate on your own set, and keep extraction and lookup on a standard model (lesson ).

What is context engineering, and how does memory work in an agent?

Context engineering is deciding what enters the model's window on each turn: instructions, tools, retrieved documents, recent history and memory, within a token budget. Long conversations are compacted into rolling summaries; durable facts go to an external memory store and are retrieved when relevant rather than carried forever; stable prefixes are ordered first so that prompt caching applies (lesson ).

How would you reduce hallucinations in a customer-facing assistant?

Ground answers in retrieved sources with citations; instruct and allow abstention; use structured outputs and tools for facts and arithmetic; lower temperature for factual tasks; add a faithfulness check step for high-risk answers; evaluate faithfulness and abstention on a golden set and monitor them in production (lessons and ).

RAG versus fine-tuning versus long context: how do you choose?

RAG for knowledge that is large, changing, access-controlled or needs citations. Fine-tuning for behaviour, format, style, or making a small model do a narrow task cheaply. Long context with caching for small, stable collections where simplicity matters. Often combined (lessons , and ).

Explain LoRA. Why does it work, and what does it save?

Freeze the pretrained weights and learn a low-rank update BA (rank r much smaller than the layer dimensions), scaled by α/r, with B initialised to zero. Weight updates during fine-tuning have low intrinsic rank, so this captures most of the benefit while training under 1% of the parameters, cutting optimiser memory dramatically and producing small swappable adapters; QLoRA also stores the base model in 4-bit (lesson ).

How do you evaluate an LLM feature when outputs are open-ended?

A golden dataset from real usage with hard and negative cases; code graders for anything rule-based; LLM judges on specific criteria with clear rubrics, structured verdicts, order swapping for pairwise comparisons, and calibration against human grades; per-slice reporting with confidence intervals and fixed/broken case analysis; online signals in production (lesson ).

What is prompt injection and how do you defend against it?

Instructions embedded in content the model reads (direct from users, or indirect via documents, web pages, tool results) that try to override the system's instructions. No complete fix exists, so defend in depth: separate and label untrusted content, but above all limit impact with least-privilege tools, human approval for consequential actions, output filtering, safe rendering and avoiding agents that combine untrusted input, private data and external communication (lesson ).

Explain RLHF, DPO and the RL methods behind reasoning models.

RLHF: collect human preference comparisons, train a reward model to predict them, then optimise the language model with reinforcement learning (PPO) to maximise reward with a KL penalty that keeps it close to the supervised model. DPO: skip the reward model and RL, and optimise the preference pairs directly with a classification-style loss relative to a frozen reference model; simpler and more stable. Reasoning models are trained with RL against verifiable rewards (a test passes, an answer matches), with group-based methods such as GRPO that drop the separate value model (lessons , and ).

When is a language model the wrong tool?

When the task is numbers, structure or control at volume: tabular prediction (gradient boosting), forecasting (seasonal baselines and boosting on lag features), ranking for users (collaborative filtering), images at scale (a trained CNN or vision transformer), routes and schedules (search and constraint solvers), actions with delayed reward (reinforcement learning). The language model then does the language around it: parsing requests, explaining results, writing reports (lesson and part IX).

How do you evaluate a recommender?

Offline: a time-based split, recall@k and NDCG@k against the held-out interactions, always against a popularity baseline, with coverage to catch a model that only recommends hits. Offline metrics are biased by what the old system showed people, so the decision is made online: an A/B test with a primary metric, guardrail metrics and a sample-size estimate, watching for feedback loops (lesson ).

Your RAG system's answers got worse after a change. How do you debug it?

Reproduce on the eval set and list newly broken cases. For each, check the trace: was the right chunk retrieved (parsing, chunking, embedding, filters)? Was it ranked high enough (reranker)? Was it in the prompt but ignored or contradicted (prompt, model, context length)? Fix the stage responsible, re-run the full eval, and add the cases to the regression set (lessons , and ).

Coding interviews

Expect standard software engineering questions plus ML-flavoured ones. Practise implementing, without libraries and against a timer: softmax and cross-entropy; logistic regression with gradient descent; k-means; a cosine-similarity top-k search; scaled dot-product attention with a causal mask; a BPE merge step; a value-iteration sweep on a small gridworld; a 2D convolution by hand; a token-bucket rate limiter; and an async function that calls an API with retries and a concurrency limit. You have written versions of almost all of these in this course. Many interviews now allow an AI coding assistant; when they do, the interviewer is watching how you specify, test and verify, so narrate that.

Hands-on: a timed coding drill

Set a timer for twenty minutes and, in NumPy only, implement:

  1. top_k_cosine(query, matrix, k): the indices of the k rows of matrix most similar to query by cosine similarity, most similar first.
  2. causal_attention(Q, K, V): scaled dot-product attention with a causal mask, for a single head with shapes (n, d).

Then write three asserts for each: a hand-checkable case, a shape check and an edge case (a zero vector; n equal to 1). You are done when all six asserts pass inside the time limit, and you can explain both functions aloud without looking.

Show what you should find

Normalise the rows and the query, take the dot product, and use argsort on the negative similarities (or argpartition for large matrices). For attention, build the mask with np.triu(..., k=1), set those scores to minus infinity before the softmax, and subtract the row maximum for stability. The solutions notebook prints:

top-3 for the query: [2 0 3]
attention row sums: [1. 1. 1. 1.]
first row attends only to itself: True
all asserts passed

System design interviews

Use the eight-part framework from lesson and practise on prompts such as: a customer-support assistant for a software company; semantic search over a million product listings; a code-review bot; a meeting summariser; content moderation for a forum; an agent that books travel within a company policy; a recommendation feed for a news app; a visual inspection station; demand forecasting for a warehouse. Talk in trade-offs, estimate costs and latency with rough numbers, say which problems do not need a language model, and always say how you would evaluate it.

Talking about your projects

Prepare a three-minute story for your capstone: the problem, your approach, one hard decision and the evidence behind it, the results, and what you would do next. Interviewers listen for measurement and judgement more than for the fanciest technique.

Career paths and the next ninety days

Where this course can take you

Job titles in this field change faster than the work does. In late 2026 these are the directions you will see advertised, under varying names:

  • AI engineer / LLM application engineer: building products on models, including agents. The direct target of this course. Some teams call the customer-facing version of this role forward-deployed engineer: you build with the customer's data and constraints, which rewards exactly the design and evaluation habits in lesson .
  • ML engineer / MLOps / inference and platform engineer: training pipelines, serving infrastructure, model platforms. Go deeper on lessons , , , and , plus distributed systems.
  • Applied scientist / research engineer: new methods and models. Go deeper on maths, papers, lessons and , and large-scale experiments.
  • Evaluation, safety and interpretability: a growing specialism in its own right. Go deeper on lessons , and .
  • Domain expert who builds with AI: often the most valuable profile of all. Deep knowledge of a field (atmospheric science, instrumentation, medicine, law, finance) combined with these skills lets you build things generalists cannot even specify. If you already have a domain, lean into it.

Two cautions. First, do not plan around salary surveys or demand statistics; they go stale within a year and vary enormously by country, and this course deliberately quotes none. Second, hiring in 2026 assumes you use AI coding tools daily; what distinguishes candidates is whether they can specify a problem, build an evaluation and verify what the tools produce. That is the skill this course has been training all along.

  • Contribute to open-source AI tools you use: documentation, examples and bug reports count.

  • Revisit fundamentals yearly: reread your learning log and redo two or three hands-on exercises; you will be surprised what you now see.
  • Pick a lesson from part IX you skipped and do it properly; the breadth is what lets you say "this is not a language-model problem" with confidence.

Hands-on: your ninety-day plan

Write a plan with three 30-day blocks. For each block: one thing to build, one topic to go deeper on, one thing to publish, and one way to get feedback from people more experienced than you. Put it at the top of your learning log, and schedule a review at day 30.

Show an example plan

Days 1 to 30: build Capstone A on the service manuals you use at work (with permission, or on public equivalents); go deeper on retrieval evaluation; publish the repository with a results table; get feedback by demoing to two colleagues who would actually use it.

Days 31 to 60: extend it with an MCP server and an agent mode (Capstone B ideas); go deeper on security and prompt injection; publish a write-up of what worked and what did not; get feedback by asking a security-minded colleague to attack it.

Days 61 to 90: distil the most common query type into a fine-tuned small model and serve it quantised and batched (Capstones D and F); go deeper on inference optimisation; publish a cost-and-quality comparison; get feedback through an open-source contribution or a talk at a local meetup.

Check yourself

What should you build first in a capstone?

  • The user interface
  • The most advanced component
  • The evaluation set, then a crude end-to-end walking skeleton
  • A fine-tuned model

The eval set defines done; the skeleton exposes integration problems early.

What makes a capstone write-up most convincing?

  • Using as many techniques as possible
  • Measured results against a baseline, a decision log including what failed, and honest limitations
  • A long list of libraries used
  • Screenshots of the code

Evidence and judgement are what reviewers and interviewers look for.

In a system design interview, what should you always cover?

  • Which programming language you prefer
  • How you would evaluate the system, alongside trade-offs and rough cost and latency estimates
  • The exact model name to use
  • Only the happy path

Evaluation and trade-offs separate senior answers from junior ones.

Why is deep domain expertise valuable for an AI engineer?

  • It lets you identify problems worth solving, specify what good looks like, and build evaluation sets generalists cannot
  • Domain experts do not need to evaluate systems
  • It replaces the need for engineering skills
  • Models cannot work without it

Knowing the domain turns generic AI capability into specific, valuable systems.

Capstone G asks for both offline and online evaluation of a recommender. Why are offline metrics not enough?

  • Offline metrics cannot be computed for recommenders
  • Held-out interactions only contain what the old system chose to show, so offline gains may not translate into real behaviour; an A/B test measures the actual effect
  • Online tests are cheaper to run
  • NDCG is only defined for search engines

Offline evaluation is biased by past exposure; the decision to ship is made online, with guardrails.

Key takeaways

  • A narrow, finished, measured project is worth more than any number of half-built ambitious ones. Build the eval set first and keep a decision log.
  • The seven capstones together exercise RAG, agents and MCP, classical ML with LLM reporting, fine-tuning and distillation, evaluation and observability, efficient inference, and recommendation with online evaluation.
  • Build a traced walking skeleton, then improve one stage at a time with an interval on every change.
  • Write it up with results first, what you tried, honest limitations and easy setup.
  • Interviews test fundamentals, coding, system design and judgement, including knowing when a language model is the wrong tool; you have built most of what they ask about.
  • Keep building, publishing, teaching and revisiting fundamentals. If you have a domain, combine it with these skills.
