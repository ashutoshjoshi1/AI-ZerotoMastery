Why a capstone

Courses build knowledge; projects build skill and evidence. One well-executed, end-to-end project, with an evaluation set, measured results and an honest write-up, says more to an employer or a team lead than a dozen certificates. It also exposes the gaps you did not know you had, which is the point.

The six sessions of this lesson are a minimum. A good capstone takes two to six weeks of hour-a-day work. Let it.

How to run your capstone

  1. Scope narrowly. One user, one job, done well. "An assistant for everything about our instruments" fails; "answers calibration-procedure questions for model X from the service manual, with page citations" succeeds.
  2. Evaluation set first. Before writing the system, write 30 to 50 test cases with expected outcomes (lesson ). This defines "done".
  3. Walking skeleton. Get the crudest end-to-end version working in the first session, then improve the weakest stage, measuring each change.
  4. Keep a decision log. For each significant choice, write what you chose, the alternatives and the evidence. This becomes the most impressive part of your write-up.
  5. Finish. Deployed, documented and measured beats ambitious and half-built.

The five capstones

Pick one. Each has a core specification, stretch goals and a rubric. They are designed so that together they exercise everything in the course; if you do more than one later, choose ones that cover different parts.

Capstone A: technical documentation assistant (RAG)

Build a question-answering assistant over a real document collection of at least 300 pages (manuals, standards, a project's documentation, public technical reports).

Core requirements

  • Parsing that handles the collection's real formats, including at least tables or scans.
  • Hybrid retrieval with reranking; metadata filters (document type or product).
  • Answers with inline citations to document and page or section; explicit "not in the documents" behaviour.
  • An evaluation set of at least 60 questions (including 10 unanswerable), with retrieval and answer metrics reported for at least three configurations.
  • A streaming API (FastAPI) and a minimal web or command-line interface; request tracing.

Stretch goals: contextual retrieval; conversational follow-ups with query rewriting; an agentic mode for multi-part questions with a cost comparison; offline mode with a local model.

Capstone B: operations agent with MCP tools

Build an agent that helps operate something real or realistically simulated: a fleet of devices, a home lab, a cloud project, a data pipeline.

Core requirements

  • An MCP server exposing at least four tools (mostly read-only) and one resource.
  • At least one consequential tool protected by human approval showing the exact action.
  • Step and cost limits; complete traces of every run.
  • An evaluation of at least 25 tasks with checkable outcomes, reporting success rate, average steps, cost and latency.
  • An attack set of at least 8 prompt-injection and misuse cases, with results before and after your defences.

Stretch goals: a planner that writes and updates an explicit plan; long-term memory of past incidents via retrieval; a comparison with a fixed workflow for the most common tasks.

Capstone C: anomaly detection with narrative reports

Build a pipeline over time-series data (your own sensor data, public air-quality or weather station data, server metrics) that detects anomalies and explains them.

Core requirements

  • Data cleaning and feature engineering (lesson ) with documented choices.
  • At least two detection methods (rules plus a statistical or ML detector) evaluated against labelled or injected anomalies with precision and recall.
  • An LLM step that turns each detection into a structured report (likely cause, evidence, confidence, recommended action), grounded in the data and any available logs.
  • A judged evaluation of report quality on a sample, with a rubric.
  • A daily scheduled run producing a readable summary.

Stretch goals: a chat interface for follow-up questions using tools over the data; forecasting to anticipate problems; a feedback loop where confirmed or dismissed alerts improve thresholds.

Capstone D: distil a small model for a structured task

Build a fine-tuned small open model that performs a narrow extraction or classification task nearly as well as a frontier model at a fraction of the cost.

Core requirements

  • A task with a strict output schema and a held-out evaluation set of at least 100 human-checked examples.
  • A training set of at least 500 examples (distilled from a large model, reviewed by sampling).
  • LoRA or QLoRA fine-tuning of a model of 3 billion parameters or fewer, with training and validation curves.
  • Comparison of four systems on the eval set: small model prompted, small model fine-tuned, large model prompted, and a routed combination; report accuracy per field, latency and cost per thousand requests.
  • Deployment of the fine-tuned model behind an OpenAI-compatible server (vLLM, Ollama or llama.cpp).

Stretch goals: quantise to 4-bit and measure the quality change; a DPO round on preference pairs from your error analysis; run it on a CPU-only machine.

Capstone E: evaluation and observability for an LLM feature

Build the evaluation and monitoring layer for an existing LLM feature: one from earlier in the course, an open-source project, or one at work (with permission).

Core requirements

  • A golden dataset of at least 100 cases with slices, sourced from real or realistic usage.
  • Code graders plus at least two LLM-judge graders, each calibrated against at least 40 human grades with agreement reported.
  • A harness producing per-slice reports with confidence intervals and fixed/broken case lists between two versions.
  • CI integration that blocks a change on per-slice thresholds.
  • A tracing setup and a dashboard of cost, latency percentiles and judged quality on sampled traffic.

Stretch goals: an online feedback loop that turns low-rated traces into candidate eval cases; drift detection on input topics; a red-team suite run nightly.

Hands-on: scope your capstone

Write a one-page project brief before writing any code:

  1. One sentence: who it is for and what it does.
  2. Three measurable success criteria.
  3. Your data sources and how you will build the eval set.
  4. The simplest architecture that could work, as a sketch.
  5. The three riskiest assumptions, and how you will test each in the first week.
  6. What you will deliberately not build.
Show an example brief (Capstone A)

Who and what: answers calibration and maintenance questions for one instrument model from its 420-page service manual and 60 service bulletins, with page citations, for field technicians.

Success criteria: (1) correct page in the top 6 retrieved for at least 90% of 60 answerable test questions; (2) faithful, correctly cited answers for at least 85% as judged by a calibrated judge; (3) says "not in the documents" for at least 9 of 10 unanswerable questions; median time to first token under 2 seconds.

Data and eval: the PDF manual and bulletins; 40 questions from two experienced technicians plus 20 reviewed synthetic questions and 10 unanswerable ones; gold page numbers recorded for each.

Architecture: Docling parsing, section-level chunks with title and section path, BM25 plus embeddings with RRF, cross-encoder reranking to 6, a mid-tier model with the grounded prompt, FastAPI streaming, JSON-line traces.

Riskiest assumptions: tables of torque values parse correctly (test 10 tables on day one); technicians phrase questions very differently from the manual (collect real questions early); bulletins that supersede manual sections can be detected (check metadata).

Not building: user accounts, a mobile app, multi-manual support, fine-tuning.

Write it up

Your write-up is what most people will see. Structure it like a short engineering report:

  1. The problem in two sentences, and a 60-second demo video or animated GIF at the top.
  2. Results first: a table of your final metrics against the baseline.
  3. Architecture: one diagram and a paragraph per component.
  4. What I tried: the decision log, condensed. Include things that did not work and why; this is often the most impressive part.
  5. Limitations and next steps, honestly.
  6. How to run it: setup in under five commands.

Publish the repository, and consider a blog post. Clear writing about a real project is one of the strongest signals of an engineer who can work on a team.

Interview preparation

AI engineering interviews typically combine coding, ML and LLM fundamentals, system design and a discussion of your projects. The concept questions below come up repeatedly. Answer each aloud in under two minutes before opening the suggested answer.

Explain the bias-variance trade-off and how you diagnose it.

Bias is error from overly simple assumptions (underfitting: high training and validation error); variance is error from sensitivity to the particular training data (overfitting: low training error, high validation error). Diagnose by comparing training and validation error; fix underfitting with more capacity or better features, overfitting with more data, regularisation, simpler models or early stopping (lesson ).

Walk through scaled dot-product attention. Why divide by √d_k?

Each token's query is dotted with every key, scaled, softmaxed into weights, and used to average the values: softmax(QKᵀ/√d_k)V. Dot products of random d-dimensional vectors have standard deviation √d, so without scaling large dimensions push softmax into saturation and gradients vanish (lesson ).

What is the KV cache, and why does it matter for serving?

During generation, keys and values of previous tokens are stored so each step only computes the new token's projections. It makes generation efficient but consumes memory proportional to layers × KV heads × head dimension × context length × concurrent sequences, which often limits how many users a GPU can serve (lessons and ).

How would you reduce hallucinations in a customer-facing assistant?

Ground answers in retrieved sources with citations; instruct and allow abstention; use structured outputs and tools for facts and arithmetic; lower temperature for factual tasks; add a faithfulness check step for high-risk answers; evaluate faithfulness and abstention on a golden set and monitor them in production (lessons and ).

RAG versus fine-tuning versus long context: how do you choose?

RAG for knowledge that is large, changing, access-controlled or needs citations. Fine-tuning for behaviour, format, style, or making a small model do a narrow task cheaply. Long context with caching for small, stable collections where simplicity matters. Often combined (lessons and ).

Explain LoRA. Why does it work, and what does it save?

Freeze the pretrained weights and learn a low-rank update BA (rank r much smaller than the layer dimensions), scaled by α/r, with B initialised to zero. Weight updates during fine-tuning have low intrinsic rank, so this captures most of the benefit while training under 1% of the parameters, cutting optimiser memory dramatically and producing small swappable adapters; QLoRA also stores the base model in 4-bit (lesson ).

How do you evaluate an LLM feature when outputs are open-ended?

A golden dataset from real usage with hard and negative cases; code graders for anything rule-based; LLM judges on specific criteria with clear rubrics, structured verdicts, order swapping for pairwise comparisons, and calibration against human grades; per-slice reporting with confidence intervals and fixed/broken case analysis; online signals in production (lesson ).

What is prompt injection and how do you defend against it?

Instructions embedded in content the model reads (direct from users, or indirect via documents, web pages, tool results) that try to override the system's instructions. No complete fix exists, so defend in depth: separate and label untrusted content, but above all limit impact with least-privilege tools, human approval for consequential actions, output filtering, safe rendering and avoiding agents that combine untrusted input, private data and external communication (lesson ).

Explain RLHF and DPO.

RLHF: collect human preference comparisons, train a reward model to predict them, then optimise the language model with reinforcement learning to maximise reward with a KL penalty that keeps it close to the supervised model. DPO: skip the reward model and RL, and optimise the preference pairs directly with a classification-style loss relative to a frozen reference model; simpler and more stable (lessons and ).

Your RAG system's answers got worse after a change. How do you debug it?

Reproduce on the eval set and list newly broken cases. For each, check the trace: was the right chunk retrieved (parsing, chunking, embedding, filters)? Was it ranked high enough (reranker)? Was it in the prompt but ignored or contradicted (prompt, model, context length)? Fix the stage responsible, re-run the full eval, and add the cases to the regression set (lessons , and ).

Coding interviews

Expect standard software engineering questions plus ML-flavoured ones. Practise implementing, without libraries and against a timer: softmax and cross-entropy; logistic regression with gradient descent; k-means; a cosine-similarity top-k search; scaled dot-product attention with a causal mask; a BPE merge step; a token-bucket rate limiter; and an async function that calls an API with retries and a concurrency limit. You have written versions of almost all of these in this course.

System design interviews

Use the eight-part framework from lesson and practise on prompts such as: a customer-support assistant for a software company; semantic search over a million product listings; a code-review bot; a meeting summariser; content moderation for a forum; an agent that books travel within a company policy. Talk in trade-offs, estimate costs and latency with rough numbers, and always say how you would evaluate it.

Talking about your projects

Prepare a three-minute story for your capstone: the problem, your approach, one hard decision and the evidence behind it, the results, and what you would do next. Interviewers listen for measurement and judgement more than for the fanciest technique.

Career paths and the next ninety days

Where this course can take you

  • AI engineer / LLM application engineer: building products on models. The direct target of this course.
  • ML engineer / MLOps: training pipelines, serving infrastructure, model platforms. Go deeper on lessons , and , plus distributed systems.
  • Applied scientist / research engineer: new methods and models. Go deeper on maths, papers and large-scale training.
  • Domain expert who builds with AI: often the most valuable profile of all. Deep knowledge of a field (atmospheric science, instrumentation, medicine, law, finance) combined with these skills lets you build things generalists cannot even specify. If you already have a domain, lean into it.

Keep growing

  • Build in public: a project or write-up every month or two.
  • Contribute to open-source AI tools you use: documentation, examples and bug reports count.
  • Teach: explaining forces understanding. Write the post you wish you had found.
  • Revisit fundamentals yearly: reread your learning log and redo two or three hands-on exercises; you will be surprised what you now see.

Hands-on: your ninety-day plan

Write a plan with three 30-day blocks. For each block: one thing to build, one topic to go deeper on, one thing to publish, and one way to get feedback from people more experienced than you. Put it at the top of your learning log, and schedule a review at day 30.

Show an example plan

Days 1 to 30: build Capstone A on the service manuals you use at work (with permission, or on public equivalents); go deeper on retrieval evaluation; publish the repository with a results table; get feedback by demoing to two colleagues who would actually use it.

Days 31 to 60: extend it with an MCP server and an agent mode (Capstone B ideas); go deeper on security and prompt injection; publish a write-up of what worked and what did not; get feedback by asking a security-minded colleague to attack it.

Days 61 to 90: distil the most common query type into a fine-tuned small model running offline (Capstone D ideas); go deeper on quantisation and serving; publish a cost-and-quality comparison; get feedback through an open-source contribution or a talk at a local meetup.

Check yourself

What should you build first in a capstone?

  • The user interface
  • The most advanced component
  • The evaluation set, then a crude end-to-end walking skeleton
  • A fine-tuned model

The eval set defines done; the skeleton exposes integration problems early.

What makes a capstone write-up most convincing?

  • Using as many techniques as possible
  • Measured results against a baseline, a decision log including what failed, and honest limitations
  • A long list of libraries used
  • Screenshots of the code

Evidence and judgement are what reviewers and interviewers look for.

In a system design interview, what should you always cover?

  • Which programming language you prefer
  • How you would evaluate the system, alongside trade-offs and rough cost and latency estimates
  • The exact model name to use
  • Only the happy path

Evaluation and trade-offs separate senior answers from junior ones.

Why is deep domain expertise valuable for an AI engineer?

  • It lets you identify problems worth solving, specify what good looks like, and build evaluation sets generalists cannot
  • Domain experts do not need to evaluate systems
  • It replaces the need for engineering skills
  • Models cannot work without it

Knowing the domain turns generic AI capability into specific, valuable systems.

Key takeaways

  • A narrow, finished, measured project is worth more than any number of half-built ambitious ones. Build the eval set first and keep a decision log.
  • The five capstones together exercise RAG, agents and MCP, classical ML with LLM reporting, fine-tuning and distillation, and evaluation and observability.
  • Write it up with results first, what you tried, honest limitations and easy setup.
  • Interviews test fundamentals, coding, system design and judgement; you have built most of what they ask about.
  • Keep building, publishing, teaching and revisiting fundamentals. If you have a domain, combine it with these skills.
